### 3.3 ตอน push — `D72`

- 🔴 **`git push` ดัน branch ทั้งอัน ไม่ใช่แค่ commit ของคุณ** (P6 เจอ 25 ส.ค. 2026 · P1 ตัดสินเป็น `D72`)
  วันนั้น P1 push 4 รอบ และแต่ละรอบพา commit ของ **P2 P3 P4 P5 P6 P7 P8 ขึ้น remote ไปด้วย** โดยไม่มีใครถูกถาม
  ⚠️ **`git commit -- <path>` ป้องกันข้อนี้ไม่ได้เลยแม้แต่นิดเดียว** — กติกาข้อบนกันของคนอื่นไม่ให้เข้า *commit ของคุณ*
  แต่ `push` พา *commit ของคนอื่น* ขึ้นไปได้ทั้งชุด **โดยไม่ต้องมี staged อะไรเลย และ `git status` ขึ้นว่าทรีสะอาด**
  · ทุก commit มี author เป็น `pratchata` เหมือนกันหมด — **git แยกไม่ออกว่าใครเป็นเจ้าของ และจะไม่มีวันแยกออก**

  **ตัดสิน (`D72`): push เป็น *การกระทำของทีม* ไม่ใช่ของคนเดียว — และเราจะ push ต่อไป ไม่ใช่หยุด push**
  1. **commit ลง branch ที่ใช้ร่วมกัน = ประกาศว่าพร้อมขึ้น remote แล้ว** · ยังไม่พร้อมก็ยังไม่ต้อง commit
  2. **คน push รับผิดชอบว่า *หัว branch ทั้งหัว* เขียว** — รันชุดเต็ม + `lint` + `guards.sh` ก่อน push ทุกครั้ง
     ไม่ใช่แค่ของตัวเองผ่าน · ถ้าของคนอื่นแดง **หยุดแล้วบอกเจ้าของ อย่า push ทับ อย่าแก้ให้เขา**

     🔴 **แก้ 27 ส.ค. 2026 — สองข้อที่เกิดจริงในวันเดียว:**

     **(ก) "บอกเจ้าของ" กับ "ยืนยันว่าไม่ใช่ของเรา" เป็น *คนละการกระทำ***
     `tsc` แดงค้างบนหัว branch **หลายชั่วโมง** · P3 เห็นมัน **2 รอบ** และรายงานทุกครั้งว่า
     *"ไม่ใช่ของผม ยืนยันด้วย `git diff` แล้ว"* — **ถูกต้องทั้งสองครั้ง แต่ไม่มีใครส่งถึงเจ้าของ**
     🎯 **ทุกคนจำครึ่งหลังของข้อนี้ (อย่าแก้ให้เขา) · ครึ่งแรก (บอกเจ้าของ) หายไป —
     และครึ่งแรกคือครึ่งที่ทำให้มันถูกแก้** · *"ไม่ใช่ของผม"* ตอบคำถาม **"ใครแก้"** ไม่ได้ตอบ **"ใครบอก"**

     **(ข) รันครบ *สามตัว* — `tsc --noEmit` · ชุดเทสต์ · `lint` · ไม่ใช่เลือก**
     สภาพหัว branch วันนั้น: **เทสต์ 843 ผ่าน · `eslint` สะอาด · `guards.sh` exit=0 · `tsc` แดง**
     🔴 **`vitest` ไม่ตรวจชนิด** — "เทสต์เขียว" กับ "คอมไพล์ผ่าน" เป็นคนละคำถาม
     · เกิดกับ P1 ก่อน (29 เคสเขียวขณะ `tsc` แดง 4 บรรทัดในไฟล์เดียวกัน) แล้วเกิดซ้ำกับ P4 ในวันเดียวกัน
  3. **บอกในข้อความถึง P1 ว่า push ถึง commit ไหน** เพื่อให้มีคนรู้ว่า remote ขยับเมื่อไหร่
  4. 🔴 **รายงานสถานะ git ต้องบอก *ปลายทาง* ด้วย ไม่ใช่แค่ `HEAD` กับจำนวน** (P4 เสนอ · P1 ทำพลาดก่อน · 28 ส.ค. 2026)
     ```
     ❌  main · HEAD 7614915 · unpushed 19
     ✅  main · 7614915 → origin/main fc42aa2 · unpushed 18
     ```
     · **"unpushed 18" ตรวจซ้ำไม่ได้ถ้าไม่รู้ว่าเทียบกับอะไร** — คู่ `HEAD ↔ upstream` ทำให้ใครก็ได้รันซ้ำแล้วได้เลขเดียวกัน
     · 🎯 **เป็นข้อเดียวกับ *"เขียวที่ `<sha>`" ไม่ใช่ "หัวเขียว"* ของข้อ 2 — แค่ย้ายจากฝั่งผลทดสอบมาฝั่งสถานะ git**
     · 🔴 **และให้ *นับ* ด้วย `git log --oneline <upstream>..HEAD | wc -l` ห้ามบวกต่อจากเลขเดิมในหัว**
       เกิดจริง: P1 วัด `14` แล้วบวก `+1` ต่อ commit จนได้ `19` (ของจริง `18`) · **บวกซ้ำหนึ่งก้าว และก้าวที่ผิดหน้าตาเหมือนก้าวอื่นทุกประการ**
       · P4 ยกเลขนั้นไปใช้ต่อสองรอบ **โดยรัน `git -C` เฉพาะฝั่ง `platform`** → *วัดครึ่งเดียว รายงานเต็ม*
       · 📌 **หลักฐานที่ไม่มีวิธีทำซ้ำ ไม่ใช่หลักฐาน มันคือความจำ** — เครื่องมือรันซ้ำได้ เลขในหัวมีแค่ผลลัพธ์

  🔴 **แก้ 27 ส.ค. 2026 — ข้อ 2 สั่งให้ยืนยันสิ่งที่หมดอายุก่อนการยืนยันจะเสร็จ (P1 เจอกับตัว 3 รอบติด)**
  ```
  รันชุดเต็มที่ 968ced0 → เขียว 990/990 → พิมพ์รายงาน
                           ระหว่างพิมพ์: มี 2 commit ลง        → รายงานล้าสมัยตอนกด Enter
  รันใหม่ที่ 1f02c32
                           ระหว่างรัน:   มีอีก 1 commit ลง     → กำลังจะล้าสมัยอีก
  ```
  🎯 **ชุดสดใช้เวลา ~4 นาที · 8 เซสชันที่ทำงานพร้อมกันทำให้หัวขยับได้ 2–3 ครั้งในหน้าต่างนั้น**
  · **นี่คือสภาพปกติของวันที่ทีมทำงานจริง ไม่ใช่เคสสุดโต่ง** — และข้อ 2 ไม่ได้พูดถึงมันเลย
  · ⚠️ **ไม่มีขั้นตอนไหนถูกข้ามให้จับได้** — ไล่ครบทุกขั้นแล้วก็ยังผิดได้ ถ้ามีคน commit ระหว่างนั้น
    (ต่างจากความผิดพลาดชนิดอื่นที่ *"ไล่ต่ออีกนิดก็เจอ"* — ตัวนี้ข้าม **เวลา** ไม่ได้ข้าม **ชั้น**)

  **✅ ท่าที่ใช้ — ปักหมุด SHA ตั้งแต่เริ่มยืนยัน แล้ว push *ก้อนที่ยืนยัน* ไม่ใช่ *หัว ณ ตอนกด*** (P2 เสนอ)
  ```bash
  SHA=$(git rev-parse HEAD)                        # ปักหมุด ณ วินาทีที่เริ่ม
  git worktree add --detach /tmp/verify "$SHA"     # ยืนยันก้อนที่ปักหมุด ไม่ใช่ทรีที่ขยับได้
  ln -s <ทรีจริง>/node_modules /tmp/verify/node_modules
  cp .env.local /tmp/verify/.env.local             # 🔴 ลืมแล้วชุดสดถูกข้ามทั้งหมด แล้วอ่านเป็นเขียว
  cd /tmp/verify && set -a && . ./.env.local && set +a && RLS_MATRIX_REQUIRED=1 npx vitest run
  git -C /tmp/verify push origin HEAD:platform     # 🔴 push **จากใน worktree** — ดูเหตุผลข้างล่าง
  git worktree remove --force /tmp/verify           # 🔴 ลบ **หลัง** push เท่านั้น — ลบก่อน = หมุดหาย
  ```
  · commit ที่ลงระหว่างรัน **ไม่หาย** — ไปขึ้นรอบหน้า ซึ่งถูกอยู่แล้วเพราะ *ยังไม่มีใครยืนยันมัน*
  🔴 **แก้ 28 ส.ค. 2026 — กับดักของท่าปักหมุดเอง: `$(git rev-parse HEAD)` ตอน push อ่านแล้ว *ดูเหมือน* หมุด** (P1 ทำ)
  ผมปักหมุด `ffede6c` · ยืนยันครบทุกด่าน · แล้วพิมพ์ `git push origin "$(git rev-parse HEAD):platform"`
  → **หัวขยับไป 2 commit ระหว่างที่ผมรันชุดเต็ม 150 วินาที** → **push ของที่ไม่ได้ยืนยันขึ้น remote**
  · ⚠️ **ไม่มีอะไรฟ้องเลย** — คำสั่งถูกต้องทางไวยากรณ์ · ผลลัพธ์ `15c732c..9276a86` อ่านเหมือนสำเร็จปกติ
    **จับได้เพราะบังเอิญเทียบเลขกับหมุดที่จดไว้** ไม่ใช่เพราะมีด่านไหนเตือน
  · 🎯 **ท่านี้ผมเป็นคนเขียนลงกติกาเอง และผมยังพลาด** — เพราะ `$(git rev-parse HEAD)` **ให้ค่าที่ถูกเสมอสำหรับคำถาม *"หัวอยู่ไหน"* แค่มันเป็นคนละคำถามกับ *"ผมยืนยันอะไรไว้"***
  · ✅ **เก็บหมุดไว้ในตัวแปรตั้งแต่บรรทัดแรก แล้วใช้ตัวแปรนั้นทุกที่** — ถ้าจดไว้ในไฟล์ **ต้องอ่านกลับมาใช้ ไม่ใช่จดไว้เฉย ๆ** (ผมจดไว้ในไฟล์แล้วไม่ได้ใช้มัน)
  · 🔴 **ท่าที่ใช้จริงตั้งแต่ 28 ส.ค. 2026 — `push` จากใน worktree (P4 เสนอ · ยิง `--dry-run` พิสูจน์แล้ว)**
    ```bash
    git -C "$WT" push origin HEAD:platform     # HEAD ที่นี่ = สิ่งที่เพิ่งยืนยัน · **re-derive ไม่ได้**
    git worktree remove --force "$WT"          # ลบ *หลัง* push เท่านั้น
    ```
    🎯 **`worktree --detach` ไม่ตาม branch → `HEAD` ในนั้นขยับไม่ได้ตามนิยาม — *นั่นคือหมุด และมันเป็นวัตถุจริงบนดิสก์ ไม่ใช่เลขในหัวคน***
    · P4 ยิงจริง: กาง worktree ที่ `17de8e4` · ทรีร่วมขยับไป `6e3ff48` ระหว่างทดสอบ · `push --dry-run`
      จาก worktree ยังได้ `9276a86..17de8e4` **ถูกต้อง** — และสภาพนั้นคือสภาพเดียวกับที่กัด P1 พอดี
    🔴 **ต่างจากท่า `$SHA` ตรงจุดที่กัดจริง:** ตัวแปรเชลล์หลุดบริบทในเซสชันยาว ๆ แล้วมือจะเอื้อมไป
      `rev-parse HEAD` ใหม่โดยอัตโนมัติ **เพราะมันให้คำตอบเสมอและหน้าตาถูกต้องเสมอ** ·
      **ท่า worktree ไม่มีอะไรให้ re-derive** — `HEAD` ที่นั่นคือคำตอบเดียวที่มี
    · 🎯 **ผิดไม่ได้ ดีกว่าผิดแล้วจับได้** — รูปเดียวกับที่ P3 ทำกับ `it.fails` (ไม่ได้ทำให้อ่านง่ายขึ้น ทำให้พลิกผิดไม่ได้)
    · 🔴 **รูปเดียวกันอีกใบ: *ห้ามเขียน sha ลงในประกาศ*** (P4 · 28 ส.ค. 2026 · เขาเป็นหลักฐานเอง)
      ```
      ❌  "กำลังจะรันชุดเต็มที่ `449f9d9`"        ← sha อยู่ในของที่เขียน *ก่อน* วัด
      ✅  "กำลังจะรันชุดเต็ม — จะบอก sha ตอนรายงานผล"
      ```
      **ไม่มี sha ในประกาศ = ไม่มีอะไรให้ยกมาผิด** · ตอนเขียนรายงาน แหล่งเดียวที่มี sha คือ `rev-parse` ที่ต้องรันตอนนั้น
      · เกิดจริง: P4 พิมพ์ `449f9d9` ลงประกาศ · หัวขยับเป็น `423a553` ระหว่างพิมพ์ · **เขารอดเพราะนิสัยอ่าน
        `rev-parse` ตอนเริ่มรัน ไม่ใช่เพราะกฎอะไรกันไว้** — ถ้าขี้เกียจก้าวเดียวจะรายงาน sha ที่ไม่ได้รัน
        **และมันจะดูถูกต้องทุกประการ**
      🎯 **ข้อเดียวกับ "push จาก worktree" แค่คนละสื่อ — เอา *ค่าที่ผิดได้* ออกจากขั้นตอน ไม่ใช่ *เตือนให้ระวัง***
    · 🔴 **และคู่กลับด้านของมัน: *คนที่ยืนยันเป็นคนที่สอง ต้องปักหมุดจาก sha ที่คนแรกรายงาน ไม่ใช่จาก `HEAD`*** (P4)
      ```
      ❌  git worktree add --detach $W HEAD           ← HEAD เป็นค่าที่ขยับได้
      ✅  git worktree add --detach $W <sha ที่เขารายงาน>   ← ค่าที่ตายแล้ว · ตรงกันเสมอ ไม่ใช่บังเอิญ
      ```
      · เกิดจริง: P4 รันชุดเต็มที่ `423a553` · P1 กาง worktree ที่ `HEAD` แล้ว**บังเอิญ**ได้ sha เดียวกัน
        → รายงานว่า *"ยืนยันครบทุกด่านที่ sha เดียวกัน"* ซึ่งจริงรอบนั้น · **ถ้าหัวขยับ จะเป็นคนละก้อนโดยไม่มีใครรู้
        และรายงานจะอ่านเหมือนเดิมทุกตัวอักษร**
      🎯 **คู่กับข้อบน: อันบนคือ *อย่าเขียนค่าที่จะถูก re-derive* · อันนี้คือ *อย่า re-derive ค่าที่มีคนเขียนไว้แล้ว***
      · 🔴 **ข้อนี้กันเคสที่ *ทุกคนทำถูกแล้วยังผิด*** — ไม่มีใครพลาดสักขั้น และผลยังผิดได้

  ```
  · เกิดจริง (ก): ดีไซน์ *"ให้เซิร์ฟเวอร์อ่านเจ้าของแล้วส่งเป็น prop"* — **ออฟไลน์หน้าถูกเสิร์ฟจากแคช SW เซิร์ฟเวอร์ไม่ได้รัน → prop คือค่าของเจ้าของคนก่อน**
  · เกิดจริง (ข): `AC4` ออฟไลน์ยิงบน dev server — **SW ปิดใน dev ตามนิยาม** (`ServiceWorkerRegistrar.tsx:14`) → ผลลบไม่มีความหมาย
  🎯 ***ทางที่ดูสะอาดที่สุด ให้คำตอบที่ผิดที่สุด ในเคสเดียวที่เราสนใจ — และมันจะดูถูกต้องทุกรอบตอนทดสอบ***
  ✅ **ท่าที่ใช้: ก่อนเชื่อผลลบ ถามว่า *สภาพที่รันมีคุณสมบัติที่บั๊กต้องใช้ครบไหม*** — ไม่ใช่แค่ *ด่านถูกไหม*

  · ของจริง: **93/93 ใน 9 วินาที** · สนามของผมขาด 3 อย่าง (รันเป็น superuser → **ข้าม RLS → ด่านอ่านว่าพัง** · ไม่มี `auth.jwt()` · ไม่มี hook สองจุด)

  · ✅ **ท่าที่ใช้: ก่อนสร้างเครื่องมือใหม่เพื่อตอบคำถามหนึ่ง ค้นก่อนว่ามีของเดิมไหม แล้ว *รัน* มัน ไม่ใช่ *อ่านสรุปของมัน***
  · 🔴 **แก้วันเดียวกัน (P7 — เขาเป็นคนตั้งชื่อ *"เขียวหลอกเชิงสภาพแวดล้อม"* เอง): คำถามคัดกรองต้องเป็น *สองทาง***

- 🔴 **เกณฑ์รับที่เขียนจากสภาพปลายทาง ล้มได้สองทาง — ทางที่สองเงียบกว่าและอันตรายกว่า** (P8 ร่าง · P1 รับ · 2 ก.ย. 2026)

  |---|---|---|---|
  | ① | บรรยายสภาพ**หลังจบ** → วางเป็นด่าน**ก่อนเริ่ม** | ตรวจไม่ได้ตามนิยาม · บล็อกเงียบ | **ดังเวลาพัง** — งานติด มีคนถาม |
  | ② | บรรยายสภาพ**ก่อนเริ่ม** → วางเป็นเกณฑ์รับ**หลังจบ** | **ผ่านฟรี ติ๊กเขียวโดยไม่มีอะไรถูกพิสูจน์** | **เงียบสนิท** ไหลเข้าสถานะ AC ทันที |

  🎯 **อาการภายนอกของสองทิศเหมือนกันเป๊ะ (`AC` นี้ปิด/ยังไม่ปิด)** — คนที่เจอทิศ ① จะไปทำงานเพิ่มแทนที่จะแก้เกณฑ์ · ทิศ ② ไม่มีใครรู้ตัวเพราะมันไม่ส่งเสียง
  · ✅ **คำถามคัดทิศ ②: *"ถ้าถอดของที่เกณฑ์นี้ควรบังคับออก มีอะไรแดงไหม"*** — ไม่แดง = ไม่ได้วัดเกณฑ์นั้นจริง

  **เกณฑ์ที่เป็นข้อห้าม (*"ห้ามมี X"*) ปิดได้เมื่อครบ 3 ข้อ:**
  ① ด่านแดงจริงเมื่อละเมิด · ② มีเคสควบคุมฝั่งบวก (ยัดของผิดเข้าไป ด่านต้องจับได้จริง) · ③ ด่านที่ยังไม่มีของให้ตรวจ **ต้องแดง ไม่ใช่เขียวเปล่า**
  🔴 **`grep`/สแกนที่ได้ `0` ไม่ใช่หลักฐานพอ** — แยกไม่ออกระหว่าง *"กันไว้แล้ว"* กับ *"ยังไม่มีใครลอง"* กับ *"มองไม่เห็น"*
  · เส้นแบ่งคือ **มีตัวสแกนที่พิสูจน์แล้วว่าแดงเป็น** ไม่ใช่ *"วันนี้ยังไม่มีใครละเมิด"*

  📌 **ตัวอย่างสดวันเดียวกัน — และมันมีสองชั้นที่ต้องแยก ไม่ใช่ชั้นเดียว:**
  ```
  cache-lockdown (ด่าน CI)  ประเมินไฟล์ D87 จริง แล้ว **ผ่านอย่างถูกต้อง**
                            → มันถาม "สิทธิ์เกินที่ประกาศไหม" ซึ่งไฟล์นั้นไม่เกิน · **ด่านไม่ผิด**
  schemaPins (พิน)          **แจงไฟล์ไม่ออก** เพราะ policy ตั้งชื่อเป็นสตริงมีช่องว่าง
                            → เขียวเพราะ **ไม่ถูกมอง** ไม่ใช่เพราะถูกตรวจแล้วผ่าน
  ```
  🎯 **ทางแก้คนละทางกันสิ้นเชิง: ด่านที่ถามคำถามแคบไป → *เพิ่มคำถาม* · ตัวแจงที่อ่านไม่ออก → *แก้ตัวแจง***
  · ⚠️ **ถ้าเขียนรวมว่า *"ผ่านทุกด่านทั้งที่ผิด"* จะพาไปแก้ผิดฝั่ง** — และจะไปรื้อด่านที่ทำงานถูกอยู่แล้ว
  · 🔴 **ชั้นที่สามที่ไม่มีใครถาม: ช่องจริงของวันนั้น (`hotel@<lat>,<lng>` เป็นคีย์แคช) ไม่มีด่านใบไหนถามถึงเลย** — มันไม่มีคำว่า `trip` · ไม่ใช่ UUID · ไม่มี FK · **ช่องอยู่ *ระหว่าง* คำถาม ไม่ได้อยู่ในใบไหน**

  **How to apply:** ถามกับทุก `AC` ที่ยังเปิด — *"เกณฑ์นี้บรรยายสภาพก่อนเฟสเริ่ม หรือหลังเฟสจบ แล้วมันถูกวางไว้ตรงไหน"*

  · ก่อนปิดเกณฑ์ที่เป็นข้อห้าม ถามว่า ***"ด่านนี้เคยแดงจริงไหม"*** ไม่ใช่ *"วันนี้เขียวไหม"*

  · ⚠️ **ฝ่ายที่รออนุมัติทำอะไรไม่ได้เลยตามนิยาม** — เขาแก้ให้ทันได้ แต่แก้เสร็จก็ล้าอีก

  (ที่นี่คือ: หยุดลง migration / หยุดเพิ่มฟังก์ชัน `app.*` · **ย้ายไปทำงานที่ไม่แตะสคีมาแทน**)
  · 🔴 **ไม่ใช่ "รอเฉย ๆ"** — เดินต่อได้ในมิติที่ไม่ผูกกัน · สิ่งที่ต้องหยุดคือ *มิติที่พินวัด* เท่านั้น
  · 📌 **สัญญาณที่ทำให้เห็น: นับว่าตัวเองลงอะไรไปกี่ใบตั้งแต่อีกฝ่ายเริ่มรอ** — P1 นับได้ `6` แล้วจึงเห็นรูป
    **ไม่มีใครบ่น และไม่มีด่านไหนเตือน** · ⚠️ *"เขายังไม่ commit"* เป็นข้อมูลที่ทุกคนเห็น **แต่ *"ผมทำให้เขาไล่ไม่ทัน"* ไม่มีใครเห็น**

- 🔴 **การเทียบ *เจ้าของ* ต้องการ *ตัวตน* ไม่ใช่ *สิทธิ์* — และ API ส่วนใหญ่ตอบเรื่องสิทธิ์** (P7 · 3 ก.ย. 2026)
  ```
  token ที่หมดอายุ   ใช้ยืนยัน **สิทธิ์** ไม่ได้แล้ว
                    แต่ยังบอกได้ว่า **เป็นของใคร** (`sub`)  ← และนั่นคือสิ่งที่การเทียบเจ้าของต้องการ
  ```
  🎯 **ถ้า API ทิ้ง session ที่หมดอายุไปเลย มันกำลังตอบคำถามเรื่องสิทธิ์ ให้กับคำถามเรื่องตัวตน — ผิดคำถาม**
  · 📌 เกิดจริงกับ `E6-AC14`: ด่าน *"ข้อมูลในเครื่องนี้เป็นของใคร"* ถูกออกแบบให้ถาม `auth.getSession()`
    · P7 วัดเบราว์เซอร์จริง: session อยู่ในเครื่อง **อ่านได้โดยไม่ยิงเน็ต** ✅ แต่ **access token อายุ ~1 ชั่วโมง**
    · 🔴 **เปิดแอปออฟไลน์เช้าวันรุ่งขึ้น → token หมด → ต้อง refresh → ออฟไลน์ทำไม่ได้**
      ⇒ ถ้าคืน `null` **เจ้าของตัวจริงจะไม่เห็นอะไรเลย** = `E6-AC4` (ออฟไลน์อ่านได้) พัง
    · 🎯 **และเคสหลังคือเคส *ปกติ* ของออฟไลน์ ไม่ใช่เคสขอบ** — คนใช้ออฟไลน์คือคนที่อยู่บนเครื่องบิน/ใต้ดิน
      **ซึ่งห่างจากครั้งที่ล็อกอินเป็นชั่วโมงหรือเป็นวัน**
  · 🔴 **และ P7 ไม่เขียนโค้ดเพราะเหตุผลที่คมกว่านั้น: เคสที่วัดได้ *วันนี้* คือเคสที่ผ่านพอดี**
    *"ถ้าผมเขียนแล้วยิงทดสอบตอนนี้ มันจะเขียว และเขียวโดยไม่ได้แตะหน้าต่างที่พัง"*
    ⇒ **เขียวหลอกเชิงสภาพแวดล้อมที่มองเห็นล่วงหน้า แล้วเลือกไม่เดินเข้าไป** — ไม่ใช่ตรวจเจอทีหลัง
  · ✅ **ท่าที่ใช้: ถามว่าเครื่องมือที่จะใช้ ตอบคำถาม *ตัวตน* หรือ *สิทธิ์*** ก่อนเลือกมัน
    (คู่กับข้อ *"คิวรีสิทธิ์ตอบคำถามที่แคบกว่าที่เราถาม"* ข้างล่าง — **คนละชั้น รากเดียวกัน**)

- 🔴 **คิวรี *สิทธิ์* ตอบคำถามที่แคบกว่าคำถามที่เราถาม — *"มีสิทธิ์" ไม่ได้แปลว่า "เรียกได้"*** (P4 ตั้งชื่อ · P6+P1 เจอคนละชั้นในวันเดียว · 3 ก.ย. 2026)
  ```
  has_function_privilege(role, fn, 'EXECUTE') = true   ⇒ **มีสิทธิ์เรียกในระดับ SQL**
  ผู้เรียกจริงยังต้องผ่าน:  เส้นทาง (PostgREST expose schema นั้นไหม)
                            การข้าม schema (security definer หรือ grant usage)
  ```
  **เกิดจริงสามชั้นซ้อนในวันเดียว — และแต่ละชั้นแก้แล้ว *ดูเหมือนจบ***
  ```
  ① grant execute on app.…   → has_function_privilege = true   ← P1 ปิดงาน
  ② เรียกจริงจาก CI          → PGRST202 "ไม่พบฟังก์ชัน"        ← P6 ยิงเจอ · `app` ไม่ถูก expose
  ③ เรียกจริงอีกรอบ          → 42501 "permission denied for schema app"  ← P1 ยิงเจอ · ต้อง security definer
  ```
  🎯 **ตระกูลเดียวกับ `information_schema.role_table_grants` ที่เปลี่ยนไปใช้ `has_table_privilege` เมื่อเช้าวันเดียวกัน**
     — คนละฟังก์ชัน โครงเดียวกัน: **เครื่องวัดตอบถูกตามคำถามของมัน แต่มันเป็นคนละคำถามกับที่เราถาม**
  · ✅ **ท่าที่ใช้: ยืนยันด้วย *เส้นทางที่ผู้เรียกจริงใช้*** (`curl POST /rest/v1/rpc/…` → `204`) **ไม่ใช่คิวรีสิทธิ์**
  · 🔴 **และตัวที่หักทั้งสองชั้นคือการยิงจริง ไม่ใช่การอ่านโค้ดให้ละเอียดขึ้น** — ไม่มีชั้นไหนที่การอ่านจะเจอ
  · 📌 **บริบทที่ทำให้มันแย่: ข้อยกเว้นที่ 6 แก้เรื่องนี้ไปแล้วด้วยรูปเดียวกันเป๊ะ** · P1 อ้างมันเป็นแบบอย่าง
    **แล้วลอกมาครึ่งเดียว (ลอก `grant` ไม่ได้ลอก wrapper)** — และจดประโยค *"ฟังก์ชันที่ไม่มีใครเรียกได้ ไม่ใช่ด่าน"*
    ไว้ในไฟล์เดียวกับที่ส่งมอบของที่ยังเรียกไม่ได้

  **🔴 ด่านที่ *เขียนไม่ได้* จากข้อมูลบนดิสก์ — และเหตุผลที่ไม่เขียน (P4)**
  อยากได้ด่านที่ถามว่า *"ฟังก์ชันนี้เรียกได้จริงไหม"* แต่ตัวแยกที่ต้องใช้คือ ***ตั้งใจให้ใครเรียก***
  · ❌ **อ่านจากโค้ดไม่ออก** — `app.*` ที่ตั้งใจให้เรียกจากในฐานอย่างเดียว **หน้าตาเหมือนกันทุกประการ**
  · ⇒ ด่านฝั่งดิสก์จะ **แดงใส่คนที่ทำถูก** = false-red ชนิดที่ทำให้ด่านถูกลบทั้งใบ
  · ✅ **รูปที่ทำได้คือฝั่ง *เป็นจริง* ไม่ใช่ฝั่ง *ห้าม*: ฟังก์ชันที่มี `grant execute` ให้ role ใดก็ตาม
    ต้องมีเคสที่ *เรียกมันจริง* อย่างน้อยหนึ่งครั้ง** — **ทะเบียนมาจาก `grant` ที่มีอยู่ ไม่ใช่จากเจตนาที่เดาไม่ได้**
  · 🎯 **ตัวอย่างที่ดีของการใช้เกณฑ์ ② ปฏิเสธด่านของตัวเอง** — ถามว่า *แดงเฉพาะการละเมิดจริงได้ไหม* ก่อนเขียน แล้วคำตอบคือไม่

- 🔴 **การวินิจฉัยที่ไม่มีกลไกรองรับ = คอมเมนต์ — *และกลไกที่แดงใส่คนที่ทำถูก จะถูกลบทั้งใบ*** (P4 · 3 ก.ย. 2026 · **สองข้อนี้ต้องอ่านคู่กัน**)
  ```
  26 ส.ค.  P4 วินิจฉัย fixture ค้างในคลังครบ · ออกแบบทางแก้ไว้แล้ว (แยกด้วยรหัสประเทศสงวน)
           วัดได้ตอนนั้น 694 แถว · **ไม่มีใครสร้างกลไก**
  3 ก.ย.   วัดใหม่ **916 แถว**       ← โตขึ้นเพราะไม่มีอะไรกวาด
  ```
  🎯 **บันทึกที่ถูกต้องทุกตัวอักษร ไม่ได้หยุดอะไรเลย** — และมันอ่านเหมือนงานที่ทำเสร็จแล้ว
  · 🔴 **ตัววัดที่ใช้ได้: ถามว่า *ถ้าไม่มีใครอ่านบันทึกนี้อีกเลย จะมีอะไรเปลี่ยนไหม*** ถ้าไม่มี = มันคือคอมเมนต์

  **🔴 แต่ข้อจำกัดที่ต้องมาคู่กันเสมอ (P4 กำชับเอง ตอนอนุญาตให้จดข้อบน):**
  ***กลไกที่แดงใส่คนที่ทำถูก จะถูกลบทั้งใบ*** — และตอนถูกลบ **ของที่มันเคยกันไว้ก็หายไปด้วยทั้งหมด**
  · 📌 เกิดจริงวันเดียวกัน: P4 เสนอ *"ห้ามพิมพ์รหัสประเทศสงวนลงโค้ด ให้อ่านจากทะเบียนเสมอ"*
    · P1 ปฏิเสธการทำเป็นด่าน เพราะ **ด่านต้องกันด้วย *รายการรูป*** (สิ่งที่กัดทีมสี่ครั้งในวันเดียว)
      **และ `newCountry.test.ts` พิมพ์รหัสตรง ๆ อย่างถูกต้อง** (ไม่แตะฐานเลย ไม่สร้าง fixture) → ด่านจะแดงใส่มัน
    · ✅ **P4 เห็นด้วยกับการปฏิเสธ** — ตรงกับ *false-red ชนิดที่สอง* ที่ทีมจดไว้เอง
  🎯 **เกณฑ์ที่ได้จากสองข้อรวมกัน — ไม่ใช่ "มีกลไกไหม" แต่คือ:**
  ```
  ① ถ้าไม่มีใครอ่านบันทึกนี้อีก จะมีอะไรเปลี่ยนไหม        ไม่มี → มันคือคอมเมนต์ ต้องมีกลไก
  ② กลไกที่จะสร้าง แดงเฉพาะกับการละเมิดจริงได้ไหม          ไม่ได้ → **อย่าสร้าง** จดเป็นความเสี่ยงที่รับไว้แทน
  ```
  · ⚠️ **ข้อ ① อย่างเดียวพาไปสร้างกลไกกับทุกอย่าง · ข้อ ② อย่างเดียวพาไปไม่สร้างอะไรเลย**
  · ✅ **ทางที่สามที่ใช้ได้เมื่อ ② ตอบว่าไม่ได้: เขียนว่า *ปลอดภัยเพราะอะไร* ให้ชัด**

    🔴 ***ทั้งคู่ปลอดภัยด้วยข้อเท็จจริงที่ไม่เกี่ยวกับตัวมันเอง*** — ซึ่งแปลว่าวันที่ข้อเท็จจริงนั้นเปลี่ยน จะไม่มีอะไรส่งเสียง
    **จดข้อนั้นไว้ ดีกว่าทั้งการสร้างด่านที่แดงผิด และการเงียบ**

- 🔴 **ข้อทักที่ถูก *ถอน* ด้วยการวัดที่ผิด อันตรายกว่าข้อทักที่ไม่เคยถูกส่ง** (P4 สร้างเคส · P1 เกือบรับ · 3 ก.ย. 2026)
  P4 ทักว่าด่านของ P1 อาจแดงปลอม → **ไปวัดเอง แล้วถอนข้อทักตัวเอง** โดยแนบหลักฐาน:

  · 🔴 **แก้คำวินิจฉัย (P4 แก้เอง · P1 ตรวจตัวเลขยืนยัน): กลไกไม่ใช่ *"เครื่องมือค้นแคบจนมองไม่เห็น"***
    เครื่องมือของเขา **เห็นและพิมพ์ออกมาแล้ว** — วัดซ้ำได้ทุกเมื่อ:
    ```
    20260902090000_e6_catalog_youtube_query.sql   7      ← มันอยู่ตรงนั้น

    🎯 **ความต่างนี้เปลี่ยนทางแก้ทั้งหมด** — *"ค้นให้ครอบทุกรูป"* **ไม่ได้กันใบนี้เลย เพราะรูปที่สองถูกค้นเจอแล้ว**
    ✅ **ท่าที่ตรงกับกลไกจริง: *ถ้าผลลัพธ์มีแถวที่ต้อง "อธิบาย" ก่อนจึงจะสรุปได้ แถวนั้นคือข้อสรุป ไม่ใช่ข้อยกเว้น***

  🎯 **สิ่งที่ทำให้มันต้านทานการตรวจน้อยที่สุด คือสามอย่างที่มาพร้อมกัน:**

### 🔴 4 ก.ย. 2026 — **เว็บที่มี auth ทำให้ *"วัดผิดหน้า"* อ่านเหมือน *"ฟีเจอร์ไม่ทำงาน"* — และผลลัพธ์ยัง `200` สวยงาม** (P3 เจอ 2 ครั้ง คนละงาน)

เกิดสองครั้งในวันเดียว **คนละเครื่องมือ คนละฟีเจอร์ รูปเดียวกัน** — ทั้งสองครั้งเกือบถูกรายงานเป็นผล

**① วัดว่าแคชทำงานไหม (`curl` เปล่า)**
```
before  /api/travel-time?…  → 401 {"error":"unauthenticated"}
after   /api/travel-time?…  → 401 {"error":"unauthenticated"}
```
⇒ **ตัวเลขเท่ากันเป๊ะทั้งสองฝั่ง** · ถ้าดูแค่ status จะสรุปว่า *"การแก้ไม่มีผล"* ทั้งที่**ยังไม่เคยวัดอะไรเลย**

**② วัดว่า `title.template` ทำงานไหม (`curl -L`)**
```
/login    → <title>luitrip</title>
/account  → <title>luitrip</title>     ← อ่านเหมือน "template ไม่ทำงาน"
```
ความจริง: `/account` ตอบ `307 → /login?next=%2Faccount` · **`-L` ตามไป ⇒ วัด `/login` สองครั้ง**

🎯 ***`-L` ทำให้ "หน้าที่ขอ" กับ "หน้าที่ได้" กลายเป็นคำเดียวกัน — และไม่มีอะไรในผลลัพธ์บอกว่ามันคนละหน้า***
เพราะปลายทางตอบ `200` จริง มี `<title>` จริง **หน้าตาเหมือนผลที่ถูกต้องทุกประการ**

🔴 **ทำไมมันอันตรายกว่า `401` ธรรมดา:** `401` ยัง *ดู* เหมือนความล้มเหลว จึงมีโอกาสถูกสงสัย
· **`200` ที่มาจากหน้าที่ผิด ไม่มีอะไรให้สงสัยเลย** — ต้องรู้ล่วงหน้าว่าจะได้อะไร ถึงจะรู้ว่าได้ผิด
· ⚠️ และมันกัดแรงที่สุด **ตอนวัด "ก่อน/หลัง"** — สองฝั่ง redirect ไปที่เดียวกัน ⇒ ***เท่ากันเสมอ ไม่ว่าการแก้จะได้ผลหรือไม่***

✅ **ตัวจับที่รันได้ ไม่ใช่คำเตือน:**
```bash
curl -s -o /dev/null -w "%{http_code} → %{redirect_url}\n" <url>   # ไม่ตาม redirect ก่อนเสมอ
```
· ได้ `3xx` = **ยังไม่ได้วัดอะไร** · ของหลัง auth ต้องวัดผ่านเบราว์เซอร์ที่ล็อกอินอยู่จริง
· 📌 ครั้งที่ ② ยืนยันด้วย `document.title` ในแท็บที่มี session → `"บัญชีของฉัน · luitrip"` (ของจริง)

  มาก่อนหน้านั้น แล้วยังทำผิดในชั่วโมงเดียวกัน**
· 🎯 ***index เป็นของกลาง ⇒ เวลาที่ของคุณอยู่ในนั้น คือความเสี่ยงที่คุณยื่นให้คนอื่น ไม่ใช่ความเสี่ยงของคุณเอง***

    ทางแก้ที่ตามมาจะไปกองอยู่ฝั่งคนกดทั้งหมด และ **ฝั่งที่เปิดหน้าต่างจะไม่มีใครแตะเลย**

#### ✅ ท่าที่รับร่วมกัน — `assert` แทน *พิมพ์แล้วอ่านเอง* · แก้ **ทั้งสองฝั่งด้วยกลไกเดียว**
```bash
want='ไฟล์ที่ตั้งใจ ทีละบรรทัด'
got=$(git diff --cached --name-only)
[ "$got" = "$want" ] || { echo "❌ index มีของที่ไม่ได้ตั้งใจ:"; diff <(echo "$want") <(echo "$got"); exit 1; }
```
· **ฝั่งคนอ่าน:** `assert` ตอบคำถามผิดข้อไม่ได้ตามนิยาม — มันเทียบ *ทั้งเซต* ไม่ใช่ *การมีอยู่*
· **ฝั่งคนถือ:** มันบังคับให้ต้องรู้ **ตอนกด** ว่าจะเอาอะไร ⇒ **ไม่มีเหตุผลให้ `add` ทิ้งไว้ล่วงหน้าอีก**
🎯 ***กลไกที่แก้ได้ข้างเดียว จะถูกทำตามข้างเดียว*** — ท่านี้ถูกเลือกเพราะมันแก้ได้ทั้งคู่ ไม่ใช่เพราะมันรัดกุมกว่า

##### ✅ **ยิงทิศแดงแล้ว — และเคสควบคุมมีค่ากว่าทิศแดง** (P7 ยิงให้ · 4 ก.ย. 2026)

**และผมจะไม่สร้างสภาพนั้นเองบนของกลาง**"* · **P7 ยิงในรีโปทิ้ง ไม่แตะของกลางเลยสักคำสั่ง**
```

🔴 ทิศแดง   คนอื่น add ของเขาก่อนเรากด      🔴 ไม่ตรง — ตั้งใจ:[mine] จริง:[mine theirs]     exit=1

##### 🔴 **ราคาที่ *วัดแล้ว* — `rename` ทำให้ท่านี้แดงใส่คนที่ทำถูกได้** ⇒ **ห้ามเป็นค่าเริ่มต้น**
```
git diff --cached --name-only                new.txt              ← ชื่อเดียว
git diff --cached --name-status              R100  old.txt  new.txt
git diff --cached --name-only --no-renames   new.txt  old.txt     ← สองชื่อ
```
เขียน `want="new.txt"` → ✅ · เขียน `want="new.txt old.txt"` → 🔴 **แดงทั้งที่ทำถูกทุกอย่าง**
🎯 ***และแบบหลังคือแบบที่คนจะเขียนโดยธรรมชาติ*** — `git mv` รู้สึกเหมือนแตะสองพาธ และ `git status` ก็แสดงสองบรรทัด

· ✅ อีกสองเคส **ไม่แดงใส่คนทำถูก**: `git rm` ได้ `[doomed.txt]` ตรงสัญชาตญาณ · `add -p` ได้ `[big.txt]`

· ทางลด: `--no-renames` ให้ผลตรงสัญชาตญาณเสมอ **แลกกับ `want` ที่ยาวขึ้นทุกครั้งที่ย้ายไฟล์**

### 🔴 4 ก.ย. 2026 — **"วัดผิด ___" ครบสามใบจากสามคนในวันเดียว — และทั้งสามให้ตัวเลขครบ ไม่มี error** (P1 เสนอให้รวม · P5 เขียน)

**รูปร่วม:** *เครื่องมือถูก · วิธีใช้ถูก · ผลลัพธ์เป็นตัวเลขที่อ่านรู้เรื่อง — แต่ชี้ไปที่สิ่งที่**ไม่มีคุณสมบัติที่กำลังทดสอบ***
⇒ **ไม่มีอะไรใน output บอกว่าอย่าเชื่อ** ⇒ ต้องรู้ล่วงหน้าว่าควรได้อะไร ถึงจะรู้ว่าได้ผิด
