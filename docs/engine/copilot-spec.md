## 1. System prompt architecture

### 1.1 หลักคิด: prompt สามชั้น ชั้นล่างแคชได้ ชั้นบนสด

Copilot จะถูกเรียกซ้ำๆ ในทริปเดียวกันหลายสิบครั้ง ถ้ายัดข้อมูลทริปทั้งก้อนไว้ต้น prompt แคชจะพังทุกครั้งที่แก้แผน
จึงแบ่ง 3 ชั้นตามความถี่ที่เปลี่ยน — เรียงจากนิ่งที่สุดไปสดที่สุด (ลำดับนี้สำคัญ: prompt caching เป็น prefix match
เปลี่ยนไบต์เดียวข้างหน้า ทุกอย่างข้างหลังหลุดแคชหมด):

```
[ชั้น 1 — นิ่ง แคช 1 ชม.]  บทบาท · กติกาเหล็ก · วิธีใช้ tool · สิ่งที่ต้องปฏิเสธ
[ชั้น 2 — ต่อทริป แคช 5 นาที]  ชื่อทริป · ช่วงวันที่ · รายการวัน+เมือง · ที่พักต่อ leg · ตารางความสามารถรายประเทศ
[ชั้น 3 — ต่อเทิร์น ไม่แคช]  "วันนี้คือวันที่เท่าไร" · dayId ที่ผู้ใช้กำลังเปิดดู · คำถาม
```

⚠️ **ห้ามใส่เวลาปัจจุบัน/`Date.now()`/session id ลงชั้น 1 หรือ 2 เด็ดขาด** — ไปไว้ชั้น 3 เท่านั้น
(เป็นข้อผิดพลาดที่พบบ่อยที่สุดและทำให้ค่าใช้จ่ายพุ่ง 5–10 เท่าเงียบๆ)

### 1.2 Copilot รู้อะไรบ้างโดยไม่ต้องเรียก tool

ชั้น 2 ใส่ได้แค่ **โครงของทริป** ไม่ใช่เนื้อทั้งหมด — โครงเปลี่ยนน้อย เนื้อเปลี่ยนตลอด:

- ชื่อทริป ช่วงวันที่ จำนวนวัน
- ตารางวัน: `dayId · วันที่ · เมือง · เมืองที่นอนคืนนั้น · จำนวนจุดแวะ` (ตัวเลขจำนวนจุดเท่านั้น ไม่ใช่รายชื่อ)
- ที่พักต่อ leg: ชื่อ + เมือง (ไม่ใส่พิกัด — โมเดลไม่ต้องคำนวณระยะเอง)
- **ตารางความสามารถรายประเทศ** (หัวข้อ 6) — ต้องอยู่ในชั้น 2 เพราะมันกำหนดว่าโมเดลพูดอะไรได้/ไม่ได้

รายชื่อจุดแวะ เวลาถึง-ออก เวลาเปิด-ปิด เวลาเดินทาง **ไม่อยู่ใน prompt** ต้องเรียก tool เอาเสมอ
เหตุผล: ข้อมูลพวกนี้ sync สดระหว่างคน 2 คนผ่าน Supabase Realtime (`PLAN.md:57`) ถ้าแช่ไว้ใน prompt
จะเก่าทันทีที่อีกคนลากจุดแวะ แล้ว Copilot จะตอบจากภาพเก่าอย่างมั่นใจ ซึ่งแย่กว่าไม่ตอบ

### 1.3 กันไม่ให้หลอนเรื่องเวลาและระยะทาง — 6 กฎในชั้น 1

นี่คือส่วนที่ต้องเขียนละเอียดที่สุดของ prompt เพราะเป็นจุดที่โมเดลพังได้เนียนที่สุด

**กฎ 1 — ตัวเลขเวลาทุกตัวมาจาก tool เท่านั้น**
> ห้ามคำนวณเวลาถึง เวลาออก ระยะทาง หรือเวลาเดินทางเอง แม้จะดูง่ายแค่ไหน
> ถ้าต้องการตัวเลข เรียก tool ถ้า tool ไม่คืนค่า ให้บอกว่ายังไม่รู้ ห้ามเดา

**กฎ 2 — แยก "ของจริง" กับ "ประมาณการ" ทุกครั้งที่พูดถึงเวลาเดินทาง**
ทุก tool ที่คืนเวลาเดินทางจะคืนฟิลด์ `source: "provider" | "estimate"` มาด้วยเสมอ
`estimate` มาจากความเร็วเฉลี่ยตายตัวใน `lib/schedule.ts:29-33` (เดิน 4.5 · ขนส่ง 20 · รถ 30 กม./ชม.
บนระยะเส้นตรง) — ไม่ใช่เวลาจริง
> เมื่อ `source === "estimate"` ต้องพูดว่า "ประมาณ ~X นาที (ค่าประมาณ ไม่ใช่เวลาจริง)" เสมอ
> **ห้ามพูดว่าเวลาเดิน/แท็กซี่ในเกาหลีเป็นเวลาจริงเด็ดขาด** — Google ไม่คืนเส้นทาง WALK/DRIVE
> ในเกาหลีใต้ (`lib/travelProvider.ts:18-19` · `PLAN.md:74-77`)

**กฎ 3 — `null` แปลว่า "ไม่รู้" ไม่ใช่ "ไม่มี"**
`isOpenDuring()` (`lib/openingHours.ts:58-72`) เป็น **สามสถานะ**: `true` เปิด · `false` ปิด · `null` ไม่มีข้อมูล
เช่นเดียวกับ `travelMinutesBetween` ที่คืน `null` ได้ (`lib/schedule.ts:125`)
> `null` ให้พูดว่า "ยังไม่มีข้อมูลเวลาเปิด-ปิดของที่นี่" ห้ามแปลงเป็น "น่าจะเปิด" หรือ "อาจจะปิด"

**กฎ 4 — ลำดับที่เสนอมาจากระยะเส้นตรง ไม่ใช่เวลาจริง**
`suggestOrder()` ทำ nearest-neighbour + 2-opt บน haversine (`lib/optimizeRoute.ts:29-100`)
คอมเมนต์ในโค้ดเขียนไว้ตรงๆ ที่ `lib/optimizeRoute.ts:27` ว่า *"ระยะเส้นตรงเป็นแค่ตัวช่วยเสนอ ไม่ใช่เวลาจริง
จึงต้องให้คนดูก่อนกดใช้เสมอ"*
> ห้ามพูดว่า "ลำดับนี้เร็วที่สุด" — พูดว่า "ลำดับนี้ระยะทางรวมสั้นลง ~X กม."
> และถ้าผู้ใช้จะใช้จริง ให้เรียก `estimate_reorder` เทียบเวลาจริงก่อนเสนอ

**กฎ 5 — ห้ามเชื่อป้ายเมืองของสถานที่**
`lib/citySegments.ts:14-21` บันทึกไว้ว่า `place.city` เพี้ยนได้ 2 ทาง: แถว `kind="hotel"` ถูก hard-code
เป็น `"seoul"` เสมอ และสถานที่ที่เพิ่มเองรับ `city` ของวันที่เพิ่ม (ร้านแถวเมียงดงที่เพิ่มในวัน `d6`
ถูกเก็บเป็นคังนึง)
> ห้ามกรอง/จัดกลุ่มสถานที่ตามชื่อเมืองเอง ให้เรียก `get_day_city_segments` ซึ่งใช้เงื่อนไข
> "เมืองเปลี่ยน **และ** ห่างเกิน 40 กม." (`lib/citySegments.ts:26,94`)

**กฎ 6 — เวลาข้ามเที่ยงคืนใช้นาทีสะสม ไม่ใช่ "HH:MM"**
`arrivalMinutes`/`departureMinutes` (`lib/schedule.ts:95-98`) เป็นนาทีสะสมไม่ wrap 24 ชม. จงใจ
เพราะเคยมีบั๊กจริง (เฟส 7.4) ที่เทียบสตริงที่ห่อรอบแล้วจนได้ค่าติดลบผิด — เคสจริงคือวันบินกลับที่ต้องไป
สนามบินตี 1 (`lib/departureAdvice.ts:33-40`)
> เวลาที่ tool คืนมาเกิน 24:00 (เช่น `1470` = ตี 0:30 ของวันถัดไป) ต้องพูดว่า "ตี 0:30 **ของวันถัดไป**"
> ห้ามตัดเหลือ "00:30" เฉยๆ

**กฎ 7 — "วันนี้" มาจาก tool ไม่ใช่จากนาฬิกาเครื่อง และไม่ใช่จากความรู้ของโมเดล**
นี่คือกฎที่เพิ่มหลังอ่าน `architecture.md §5` และเป็นกฎที่พังแล้วเจ็บที่สุด เพราะ **ทุก tool ทำงานถูกหมด
แต่คำตอบผิดทั้งคำตอบ** — ถ้า Copilot เข้าใจว่าวันนี้คือวันที่ 3 ทั้งที่จริงเป็นวันที่ 4 มันจะไปตอบเรื่อง
ตารางของวันผิดอย่างมั่นใจ และไม่มีอะไรในระบบจับได้
> ห้ามใช้ความรู้ของตัวเองเรื่องวันที่ปัจจุบันเด็ดขาด · ห้ามอนุมานจากคำว่า "พรุ่งนี้" ที่ผู้ใช้พิมพ์
> ให้เรียก `get_now` แล้วใช้ `todayDayId` / `nowMinutes` ที่ได้เท่านั้น
> ถ้า `get_now` คืน `clockSuspect: true` (เวลาเครื่องไม่ตรงกับโซนของวันนั้น) ให้**ถามยืนยันกับผู้ใช้ก่อน**
> ว่า "ตอนนี้คุณอยู่วันไหนของทริป" แทนที่จะเดา

### 1.4 บุคลิกและภาษา

- **ตอบภาษาไทย** (กติกาโปรเจกต์ `PLAN.md:2006`) ชื่อสถานที่เกาหลี/อังกฤษเก็บตามเดิม
- ตอบสั้น ตรงคำถาม — Copilot นี้ถูกใช้บนมือถือกลางถนนที่โซล ไม่ใช่บนจอคอม
- ถ้าเจอปัญหาในแผน ให้บอก **ปัญหา + ทางเลือกที่ทำได้** ไม่ใช่แค่บ่นว่ามีปัญหา
- ห้ามถามซ้ำสิ่งที่หาเองได้จาก tool — ถามคนเฉพาะตอนที่คำตอบเปลี่ยนสิ่งที่จะทำจริงๆ

**streaming ควรอยู่ในสถาปัตยกรรมตั้งแต่คำขอแรก แต่ด้วยเหตุผลด้าน UX ไม่ใช่เพราะถูกบังคับ**

⚠️ **แก้ตัวเลขที่เคยเขียนผิดไว้ในไฟล์นี้:** ฉบับก่อนเขียนว่า Vercel Hobby ตัดที่ **10 วินาที**
และยกให้ streaming เป็น "ข้อบังคับสถาปัตยกรรม" ด้วยเหตุผลนั้น — **ตัวเลขนั้นผิด**
P6 เปิดเอกสารจริงแล้ว: เพดาน Hobby คือ **300 วินาที (5 นาที)** (**D3.1**) · ตาราง 10s/60s ที่เคยอ้างถึง
มีประโยคกำกับเงื่อนไขว่าใช้กับโปรเจกต์ที่ deploy **ก่อน 23 เม.ย. 2025 และไม่ใช้ Fluid compute**
ซึ่งโปรเจกต์นี้ (สร้างปี 2026) ไม่เข้าเงื่อนไขเลย · **300 วินาทีกว้างพอสำหรับ LLM ที่ไม่ stream ด้วยซ้ำ**

**เหตุผลจริงที่ยังควรทำ streaming — ทั้งหมดเป็นเรื่อง UX:**
- ผู้ใช้รอ 30–60 วินาทีโดยไม่มีอะไรขึ้นจอ กับรอเท่ากันแต่เห็นความคืบหน้า **คนละเรื่องกันโดยสิ้นเชิง**
  โดยเฉพาะบนมือถือกลางถนนที่โซล ซึ่งคนจะเดาว่าเน็ตหลุดแล้วกดซ้ำ
- หนึ่งคำถามเรียก tool 3–4 ตัวต่อกัน แต่ละตัวยิง Places API/Routes API จริง — ส่ง event
  ระหว่างทาง ("กำลังดูตารางวันที่ 3…") ทำให้ผู้ใช้รู้ว่าระบบทำอะไรอยู่ ไม่ใช่เงียบจนได้คำตอบสุดท้าย
- ถ้าเขียนเป็น request-response ก่อนแล้วค่อยแปลงทีหลัง ต้องรื้อทั้งเส้น (route handler · tool loop · UI)
  ซึ่งเป็นต้นทุนที่หลีกเลี่ยงได้ฟรีถ้าทำถูกตั้งแต่แรก

🔴 **ทำไมต้องเขียนกำกับว่า "เลือกเอง" ไม่ใช่ "ถูกบังคับ" — สองอย่างนี้ทนต่อการทบทวนไม่เท่ากัน**
ถ้าเอกสารอ้างว่า streaming ถูกบังคับด้วย timeout วันหนึ่งมีคนพบว่าเพดานคือ 300 วินาที
เขาจะสรุปว่าเหตุผลตกไปแล้วและ**รื้อ streaming ทิ้งทั้งที่เหตุผลจริง (UX) ยังอยู่ครบ**
ตรงกับ D21.2: *ถ้าข้ออ้างพังเมื่อตัวเลขเปลี่ยน แปลว่ากำลังเถียงเรื่องขนาด ไม่ใช่เรื่องเหตุผล*
— เหตุผล UX ข้างบนไม่ขึ้นกับเพดานเลย ไม่ว่าจะ 10 หรือ 300 หรือไม่มีเพดาน มันก็ยังจริง

🔴 **ห้ามปิด thinking เพื่อลดค่าใช้จ่าย** — นี่คือกับดักที่จะดึงดูดคนทำ E8 มากที่สุด และเป็นกับดักที่
**พังแบบเงียบสนิท**: ปิดแล้วโมเดลอาจเขียน tool call ออกมาเป็น**ข้อความธรรมดา** ผลคือเทิร์นสำเร็จ
ไม่มี error แต่ **tool ไม่เคยถูกเรียกจริง** — และในลูป agent ข้อความปลอมนั้นค้างอยู่ใน history
ไปกวนเทิร์นถัดไปด้วย · อีกอาการคือแท็ก `<thinking>` หลุดออกมาในคำตอบที่ผู้ใช้เห็น
**ถ้าต้องลดค่าใช้จ่าย ให้ลด `effort` ไม่ใช่ปิด thinking** (ดู 7.2 ลำดับตัวคุมค่าใช้จ่าย)

⚠️ และถ้าจำเป็นต้องปิดจริงๆ ในบางเส้นทาง: `thinking: disabled` **ใช้ได้เฉพาะ `effort` ≤ `high`**
คู่กับ `xhigh`/`max` ได้ **400** และตรวจ**รายคำขอ** — คำขอก่อนหน้าผ่านไม่ได้แปลว่าคำขอถัดไปจะผ่าน

## 2. Tool / function-calling schema

### 2.1 กติกา 4 ข้อของ tool ทุกตัว

1. **ทุก tool รันฝั่งเซิร์ฟเวอร์** — pure function หลายตัวต้องใช้ข้อมูลประกอบที่ไม่ควรส่งให้โมเดล
   เช่น `computeSchedule()` (`lib/schedule.ts:127-133`) รับ `placesById: Map` และ callback
   `travelMinutesBetween` ที่ต้องยิงแคช/Routes API ต่อ · tool wrapper จึงรับแค่ `tripId`/`dayId`
   แล้วประกอบ input เองทั้งหมด
2. **แยกอ่าน/เขียนที่ชื่อ tool** — tool อ่านขึ้นต้น `get_`/`check_`/`find_`/`estimate_`
   tool เขียนขึ้นต้น `propose_` เสมอ **ไม่มี tool ไหนชื่อ `set_`/`update_`/`delete_`**
   (ดู 2.4 — ชื่อนี้จงใจ เพราะ tool เขียนไม่ได้เขียนจริง)
3. **ทุก tool คืน `source` และ `asOf`** เมื่อคืนตัวเลขที่มาจากผู้ให้บริการภายนอก
4. **ทุก tool มี `tripId`** เป็นพารามิเตอร์แรก และเซิร์ฟเวอร์ตรวจสิทธิ์ตรงนั้น
   ไม่เชื่อ `tripId` ที่โมเดลส่งมาโดยไม่ตรวจ (โมเดลอ่าน `tripId` มาจาก prompt ซึ่งอาจถูกป้อนผิดได้)

### 2.2 Tool อ่าน (เรียกได้เองอิสระ ไม่ต้องขออนุญาต)

| tool | ห่ออะไร | input | output ที่สำคัญ |
|---|---|---|---|
| `get_day_schedule` | `computeSchedule()` `lib/schedule.ts:127` | `tripId, dayId` | `stops[]` แต่ละตัวมี `arrival`, `departure`, `arrivalMinutes`, `departureMinutes`, `resolvedDwellMinutes`, `travelMinutesFromPrev`, `travelSource`; ระดับวันมี `departFrom`, `arriveBackAt`, `endOfDayMinutes` |
| `check_opening_hours` | `isOpenDuring()` + `minutesUntilClose()` + `weekdayHoursLabel()` `lib/openingHours.ts` | `tripId, dayId, stopIds[]?` | ต่อจุด: `isOpen: true\|false\|null`, `minutesUntilClose: number\|null`, `hoursLabel: string\|null` |
| `estimate_reorder` | `suggestOrder()` + `routeDistanceKm()` `lib/optimizeRoute.ts` | `tripId, dayId, pinnedStopIds[]?` | `suggestedOrder[]`, `currentKm`, `suggestedKm`, `changed: boolean` · **ไม่เขียนอะไร** |
| `get_departure_advice` | `computeDepartureAdvice()` `lib/departureAdvice.ts:42` | `tripId, dayId, stopId` (แถว `kind="transfer"`) | `mustArriveBy`, `shouldLeaveBy`, `plannedArrival`, `lateByMinutes`, `slackMinutes` |
| `get_day_city_segments` | `buildDayCitySegments()` `lib/citySegments.ts:117` | `tripId, dayId` | `segments[]` = `{ city, stopCount, items[] }` |
| `get_travel_time` | `fetchRealTravelTime()` + แคช `lib/travelProvider.ts:21` | `tripId, fromRef, toRef, mode` | `minutes`, `distanceMeters`, `source: "provider"\|"estimate"`, `asOf` · 🔴 **ต้องอ่านแคชผ่าน `security definer` ไม่ใช่ client ปกติ — ดู 10** |
| `find_places` | `searchPlacesText()` / `searchNearby()` `lib/googlePlaces.ts:69,179` | `tripId, query?, nearStopId?, includedTypes[]?, radiusMeters?` | `candidates[]` = `{ placeId, name, address, lat, lng, rating, openingHours, primaryType }` |
| `get_place_details` | `getPlaceDetails()` `lib/googlePlaces.ts:226` | `tripId, googlePlaceId` | รายละเอียด + `regularOpeningHours` |

| `get_capabilities` | provider registry (หัวข้อ 6) | `tripId, dayId?` | ความสามารถของประเทศที่วันนั้นอยู่ |
| `get_now` | `trip_days.timezone` + `lib/localDate.ts` | `tripId, clientTimeZone?, clientNow?` | `todayDayId`, `todayDate`, `nowMinutes`, `timeZone`, `clockSuspect: boolean` |

**`get_now` เป็น tool ที่สำคัญกว่าที่หน้าตามันดู** (กฎ 7) — มันคือจุดเดียวที่ตัดสินว่า "วันนี้" คือวันไหน
เซิร์ฟเวอร์คำนวณจาก `trip_days.timezone` ของทริป **ไม่ใช่จากนาฬิกาเครื่อง** แล้วเทียบกับ `clientNow`
ที่เครื่องส่งมา ถ้าต่างกันเกิน ~30 นาที ให้ตั้ง `clockSuspect: true`
เคสจริงที่กันอยู่คือมือถือค้างเวลาไทยตอนอยู่เกาหลี ซึ่ง `lib/localDate.ts` บันทึกไว้เองว่าเกิดขึ้นจริง
— 2 ชั่วโมงแรกหลังเที่ยงคืนเกาหลีจะเข้าใจวันผิดไปทั้งวัน

**หมายเหตุ `get_day_schedule`** — `computeSchedule` ถือว่าเวลาเดินทางที่ยังไม่รู้เป็น 0 นาที
(`lib/schedule.ts:125`) ซึ่งทำให้ตารางดู "แน่นเกินจริง" tool wrapper ต้องนับจำนวนช่วงที่
`travelMinutesFromPrev === null` แล้วคืนเป็น `unknownLegCount` ให้โมเดลเตือนผู้ใช้ได้
ไม่งั้น Copilot จะตอบว่า "วันนี้สบายมาก" ทั้งที่ความจริงคือยังไม่รู้เวลาเดินทางเลยสักช่วง

### 2.3 Tool เขียน — ทั้งหมดเป็น "ข้อเสนอ" ไม่ใช่การเขียน

🔴 **DB นี้คือแผนทริปจริงของคน 2 คนที่บิน 11 ต.ค. 2026 — agent ห้ามแก้เอง**

tool กลุ่มนี้ **ไม่แตะข้อมูลทริป** สิ่งที่มันทำคือเขียนแถว *ข้อเสนอ* ลง `copilot_proposals`
แล้วคืน `proposalId` + สรุปสิ่งที่จะเปลี่ยน · ฝั่ง UI เอา `proposalId` ไปเรนเดอร์เป็นการ์ด
"ก่อน → หลัง" พร้อมปุ่ม **ยืนยัน / ยกเลิก** · การเขียนจริงเกิดตอนคนกดยืนยันเท่านั้น

🔴 **การกดยืนยันวิ่งผ่าน `app.decide_proposal()` ที่เป็น `SECURITY DEFINER` ไม่ใช่ Server Action ธรรมดา**
ร่างแรกของผมเขียนว่า "วิ่งผ่าน Server Action ปกติเหมือนที่คนกดเอง" ซึ่ง **ผิด** และ P4 จับได้
(`security-review.md §8.1` · **D38**) — เหตุผลที่ผิดสำคัญพอที่จะเขียนไว้ตรงนี้ เพราะเป็นความเข้าใจผิด
ที่จะเกิดซ้ำตอน E3 ย้าย 60 จุดไป Server Action:

> **Server Action ที่ใช้ session ของผู้ใช้ ก็รันเป็น role `authenticated` เหมือน browser**
> RLS ไม่สนว่าคำสั่งมาจากเซิร์ฟเวอร์หรือเบราว์เซอร์ มันสนแค่ role
> — "ย้ายไปฝั่งเซิร์ฟเวอร์แล้ว" **ไม่ได้แปลว่าได้สิทธิ์เพิ่ม**

ผลของความเข้าใจผิดนี้: ตารางที่ตั้งใจไม่เปิด UPDATE policy จะเปลี่ยน `status` ไม่ได้เลย
ได้ `42501` **ทุกครั้ง** = เส้นทางกดยืนยันพังทั้งเส้น · และ 2 ทางแก้ที่ดูชัดเจนผิดทั้งคู่
(เปิด UPDATE policy = เปิดช่องที่ตั้งใจปิด · ใช้ service role = ข้าม RLS ทั้งระบบ)
→ ทางที่ถูกคือ `SECURITY DEFINER` ที่ถือ **ทั้งการตรวจ `base_versions` และการเขียน**
ไว้ในทรานแซกชันเดียว ทำให้ด่านข้ามไม่ได้เชิงโครงสร้าง ไม่ใช่เพราะมีวินัย
· รายละเอียดและ DDL อยู่ที่ `docs/engine/schema/copilot_proposals.sql`

⚠️ **ยังต่อยอดจาก `lib/writeGuard.ts:19` ได้เหมือนเดิมสำหรับฝั่ง UI** (พังแล้วต้องมีเสียง)

   ใส่ index ธรรมดาแล้วเขียนคอมเมนต์ว่า "กันไม่ให้ยิงซ้อน" ซึ่ง P4 ชี้ว่าเป็น
   **รูปแบบเดียวกับบั๊ก `travel_time_cache` เป๊ะ: เจตนาอยู่ในคอมเมนต์ การบังคับไม่มีอยู่**
   ✅ ตัดสินแล้ว: **หนึ่ง pending ต่อผู้ใช้ต่อทริป** ไม่ใช่หนึ่งต่อทริป — เพราะกฎนี้เป็นกฎของ
   *บทสนทนา* และผู้ใช้ 2 คนคุยกับ Copilot พร้อมกันได้จริง · ถ้าบังคับหนึ่งต่อทริป
   คนที่สองจะถูกบล็อกด้วยเหตุผลที่ไม่เกี่ยวกับตัวเองและแก้เองไม่ได้ ต้องรอให้อีกคนกดการ์ดค้าง
   ส่วนเคสที่ 2 คนเสนอชนกันจริง มี `base_versions` รับอยู่แล้ว → คนที่สองได้ `stale`
2. ทุก proposal ต้องมี `preview` ที่ผ่าน `computeSchedule` **ของสถานะหลังเปลี่ยน** แนบมาด้วย
   คนจะได้เห็นว่าเวลาทั้งวันขยับยังไงก่อนกดยืนยัน ไม่ใช่เห็นแค่ "สลับ A กับ B"
3. proposal หมดอายุใน 10 นาที และผูกกับ `updated_at` ของทุกแถวที่จะแก้ — ถ้าอีกคนแก้ก่อน ให้ปฏิเสธ
   แล้วบอกว่า "แผนเปลี่ยนไปแล้วระหว่างที่คุยกัน ขอดูใหม่นะ" (เว็บนี้ sync สด 2 คน เคสนี้เกิดจริงแน่)
   ✅ **D7 ทำให้ด่านนี้แข็งขึ้นมาก** — พอ `updated_at` มาจาก DB trigger แทน client มันกลายเป็น
   concurrency token ที่เชื่อได้จริง · ของเดิมที่ client ส่งเวลาเครื่องตัวเองมา (20+ จุดใน 6 hook)
   ใช้เป็นด่านกันชนไม่ได้เลย เพราะเครื่องที่ตั้งนาฬิกาผิดจะชนะ LWW ตลอด
   🔴 **การตรวจต้องอยู่ในฟังก์ชันเดียวกับการเขียน** (`app.decide_proposal`) พร้อม `for update`
   ล็อกแถวไว้ · ถ้าตรวจในแอปแล้วค่อยเขียน จะมีช่องระหว่างสองขั้นให้อีกคนแทรกได้เสมอ
   และคน 2 คนกดยืนยันข้อเสนอเดียวกันพร้อมกันจะ apply ซ้ำ
4. **soft delete (D7): ต้องเช็คว่าแถวยังไม่ถูกลบก่อนเสมอ** — แถวที่ถูก soft delete ยังอยู่ในตาราง
   ถ้า tool อ่านแบบไม่กรอง Copilot จะเสนอแก้จุดที่ผู้ใช้ลบไปแล้ว ซึ่งดูเหมือนระบบเพี้ยน
5. `propose_remove_stop` / `propose_move_stop` ห้ามใช้กับ `kind` เป็น `"transfer"` หรือ `"intercity"`
   (`lib/supabase.ts:97-107`) — แถวพวกนี้ผูกกับตั๋วเครื่องบิน/KTX ที่จองแล้ว ให้ปฏิเสธและบอกให้คนแก้เอง
6. บันทึก audit ทุกครั้ง: `{ proposalId, tool, args, actor, decidedAt, decision }`
   `actor` เป็น FK → `profiles.id` ได้จริงหลัง E1 (`architecture.md §2.1`) ไม่ใช่ข้อความที่พิมพ์เอง

### 2.4 ทำไมไม่ยอมให้เขียนตรงแม้แต่ตัวเดียว

มีเสียงค้านที่คาดไว้ว่า "ให้เขียนได้บ้างสิ ไม่งั้นไม่เรียกว่า agent" — ข้อโต้แย้งคือ:

- **ต้นทุนความผิดพลาดไม่สมมาตร** อ่านผิดคือตอบผิดหนึ่งครั้ง เขียนผิดคือแผนของคน 2 คนพังกลางเกาหลี
- **ไม่มี undo** ระบบนี้ไม่มีประวัติเวอร์ชันของ `trip_stops` ลบแล้วคือหาย
- **แก้เองอยู่แล้วง่ายกว่า** UI ลากจัดลำดับมีอยู่แล้วและผ่านสนามจริงมาแล้ว (`hooks/useTripDnd.ts`)
  Copilot ไม่ได้แข่งกับ "ต้องพิมพ์ SQL เอง" แต่แข่งกับ "ลากนิ้วสองที"
  คุณค่าจริงของมันคือ **บอกว่าควรลากไปตรงไหน** ไม่ใช่ลากแทน
- ด่านยืนยันนี้ **ไม่ได้ทำให้ช้าลงจริง** เพราะแตะยืนยันคือหนึ่งแตะ เท่ากับที่ต้องแตะอยู่แล้ว

### 2.5 rank key (D6) — ได้อะไร และมีกับดัก 2 ข้อที่ Copilot ต้องรู้

D6 เปลี่ยน `order_index` จาก integer เป็น rank key เรียงได้ **นี่เป็นข่าวดีสำหรับ Copilot มากกว่าที่คิด**:

**ได้อะไร**
- ย้าย 1 จุด = เขียน DB **แถวเดียว** (ของเดิม `hooks/useStops.ts:413-419` เขียนทับทุกแถวทั้งวัน
  แยกคำขอด้วย `Promise.all`) → proposal เล็กลงมาก อ่านง่ายขึ้นบนการ์ดยืนยัน
- ด่าน `updated_at` (ข้อ 3) ต้องเช็คแค่แถวเดียวแทน n แถว → **โอกาสชนกับอีกคนลดลงตามจำนวนแถว**
  ซึ่งสำคัญมากกับเว็บที่ sync สด 2 คน
- ปิดหน้าต่างบั๊ก 8.1 ที่ `sortStops` (`hooks/useStops.ts:13-17`) ไม่มี tie-break — เลขซ้ำเมื่อไหร่
  2 เครื่องเห็นลำดับไม่ตรงกัน ซึ่ง Copilot จะยิ่งทำให้เกิดง่ายขึ้นเพราะยิงคำขอถี่กว่าคนลากนิ้ว

**กับดัก 2 ข้อ — ต้องเขียนไว้ในชั้น 1 ของ prompt**

1. **แทรกพร้อมกันตำแหน่งเดียวกันได้ลำดับสลับกันได้** (README D6 ยอมรับข้อนี้ไว้แล้วว่ารับได้
   เพราะไม่ใช่ข้อมูลสูญหาย) — แต่สำหรับ Copilot แปลว่า:
   > หลังผู้ใช้กดยืนยัน **ห้ามสรุปลำดับสุดท้ายจากสิ่งที่ตัวเองเสนอ** ให้เรียก `get_day_schedule` ใหม่
   > แล้วรายงานจากของจริง · ถ้าลำดับที่ได้ไม่ตรงกับที่เสนอ ให้บอกตรงๆ ว่าอีกคนแก้พร้อมกันพอดี

2. **`propose_reorder_day` ยังคงมีอยู่ ไม่ได้ถูกแทนด้วย `propose_move_stop`** — จัดลำดับใหม่ทั้งวัน
   (เคส 3) ยังต้องเขียนหลายแถวโดยธรรมชาติ แต่ต่างจากของเดิมตรงที่ **เขียนเฉพาะแถวที่ตำแหน่งเปลี่ยนจริง**
   ไม่ใช่ทุกแถวทั้งวัน · tool wrapper คำนวณ rank key ให้เอง **โมเดลไม่ต้องรู้จัก rank key เลย**
   ส่งมาแค่ `orderedStopIds[]` ตามลำดับที่ต้องการ
   > ห้ามให้โมเดลสร้าง/เดา/ส่งค่า rank key เอง — เป็นรายละเอียดของ storage ไม่ใช่ของภาษา

⚠️ **rebalance เป็นเรื่องของ E2 ไม่ใช่ของ Copilot** — README D6 เตือนว่าแทรกซ้ำที่เดิมบ่อยๆ
ทำให้คีย์ยาวขึ้นเรื่อยๆ · Copilot ยิงถี่กว่าคนจึงเร่งให้ถึงจุดนั้นเร็วขึ้น แต่กลไก rebalance
ต้องอยู่ในชั้น storage ไม่ใช่ให้ Copilot หลบเอง — **ฝากไว้กับ P1/P7 ที่ E2**

## 3. RAG — จำเป็นไหม

**สรุป: ระยะ 2 ไม่ต้องทำ RAG เลย** ทั้ง vector store และ embedding pipeline
เหตุผลตรงไปตรงมา: **ปัญหาของ Copilot นี้ไม่ใช่ปัญหาการค้นหา**

| สิ่งที่ Copilot ต้องรู้ | หาจากไหน | ต้อง embed ไหม |
|---|---|---|
| แผนทริปปัจจุบัน | tool อ่านจาก DB | ไม่ — ข้อมูลมีโครงสร้าง query ตรงเร็วกว่าและแม่นกว่า |
| เวลาเปิด-ปิด · เรตติ้ง · ที่ใกล้เคียง | Places API (New) | ไม่ — Google เป็น index ที่ดีที่สุดที่มีอยู่แล้ว |
| คลังสถานที่คัดสรร **72 ที่** (⚠️ เอกสารเก่าเขียน "39" · นับจริงแล้ว 72 · ดู **13.6**) | `data/places.ts` (1,207 บรรทัด ~71 KB) | ไม่ — เล็กพอจะโหลดทั้งก้อนถ้าจำเป็น และมีโครงสร้างชัด |
| โน้ตที่ผู้ใช้จดเอง | `trip_stops.note` (`lib/supabase.ts:91`) | ไม่ — ปริมาณระดับสิบแถว |

การใส่ RAG ตรงนี้จะแลก "ค้นหาแบบคลุมเครือ" มาแทน "query ที่แม่น 100%" ซึ่งเป็นการแลกที่ขาดทุน
เพราะคำถามของผู้ใช้เกือบทั้งหมดชี้เจาะจงอยู่แล้ว ("วันที่ 3" "ร้านนี้")

**เงื่อนไขที่จะทำให้กลับมาคิดใหม่** — ทั้งสามข้อต้องเกิดพร้อมกัน ไม่ใช่ข้อใดข้อหนึ่ง:
1. ทริปต่อผู้ใช้เยอะจนถามข้ามทริปได้ ("ร้านที่เราชอบตอนไปโอซาก้าชื่ออะไรนะ")
2. มีคลังเนื้อหาแบบข้อความยาวจริง (รีวิว/ไกด์ที่เขียนเอง) ไม่ใช่แค่ metadata
3. วัดแล้วว่า query ตรงตอบไม่ได้จริง ไม่ใช่แค่ "รู้สึกว่าน่าจะดีกว่า"

ถึงตอนนั้น รูปแบบที่เหมาะคือ embed **โน้ตกับรีวิวที่ผู้ใช้เขียนเอง** ต่อ `trip_id` เท่านั้น
(ไม่ embed ข้อมูลจาก Google — มันมี API ให้ค้นอยู่แล้วและ ToS จำกัดการเก็บ)

### เคส 1 — "วันที่ 3 แน่นไปไหม"

**tool:** `get_day_schedule` → `check_opening_hours`

> **ผู้ใช้:** วันที่ 3 แน่นไปไหม

### 4.8 DoD-7 สำหรับ Copilot — "ถ้าข้อนี้พังตอนใช้จริง เราจะรู้ได้ยังไง"

`README.md` ยก **"ผลลัพธ์ที่ดูเหมือนปลอดภัย กับผลลัพธ์ที่พังสนิท หน้าตาเหมือนกัน"** เป็นหลักการหลัก

## 6. หลายประเทศ — prompt รู้ได้ยังไงว่าประเทศนี้ทำอะไรได้

### 6.1 ปัญหา

เกาหลีใต้ไม่คืนเส้นทาง DRIVE/WALK จาก Google (กฎหมายห้ามส่งออกข้อมูลแผนที่ละเอียด)
เวียดนามคืนครบทุกโหมด — **ความสามารถต่างกันจริงรายประเทศ** และจะต่างขึ้นอีกเมื่อรับประเทศเพิ่ม
ถ้าปล่อยให้โมเดลจำเอง มันจะจำผิดแน่นอน (และจะผิดแบบมั่นใจ)

`lib/mapLinks.ts` มีแนวคิดนี้อยู่แล้วแบบ hard-code (เกาหลีใช้ Naver/Kakao · ฮานอยใช้ Google)
สิ่งที่ต้องทำคือยกขึ้นเป็นข้อมูล ไม่ใช่ `if`

### 6.2 ทางออก: อ่านจาก provider registry ของ P1 — ไม่สร้าง registry ตัวที่สอง

🔴 **`get_capabilities` ต้องอ่านจาก registry เดียวกับที่ `architecture.md §4.2` นิยามไว้ ห้ามสร้างของตัวเอง**

P1 นิยาม seam ไว้แล้วที่ `architecture.md §4.2`:

```ts
// lib/providers/route.ts
export type RouteProvider = {
  id: string;
  supports(country: string, mode: TravelMode): boolean;
  fetch(o: LatLng, d: LatLng, mode: TravelMode): Promise<RealTravelTime | null>;
};
```

`get_capabilities` เป็นแค่ **ตัวอ่าน** ที่เรียก `supports()` วนทุกโหมดแล้วแปลงเป็นข้อความที่โมเดลอ่านรู้เรื่อง
ถ้าสร้าง registry แยกฝั่ง Copilot จะเกิดสิ่งที่แย่ที่สุด คือ **UI กับ Copilot บอกผู้ใช้ไม่ตรงกัน**
โดยที่ทั้งคู่ "ถูก" ตามแหล่งข้อมูลของตัวเอง

จุดอื่นที่ Copilot ต้องอ่านจากตารางเดียวกับ UI (`architecture.md §4.3`):

| Copilot ใช้ทำอะไร | อ่านจาก |
|---|---|
| บอกว่าให้เปิดแอปนำทางตัวไหน | `countries.map_provider` (ไม่ใช่ hardcode ใน `lib/mapLinks.ts`) |
| ขอชื่อสถานที่จาก Google เป็นภาษาอะไร | `countries.default_locale` + locale ของผู้ใช้ |
| ตอบเรื่องเบอร์ฉุกเฉิน | `emergency_contacts` |
| ตอบเรื่องทางไปสนามบิน | `airport_access_options` |

รูปร่างข้อมูลต่อประเทศที่ `get_capabilities` คืน:

```
countryCode: "kr"
travelModes:
  transit: { real: true,  source: "google-routes" }
  walk:    { real: false, source: "estimate", reason: "กฎหมายข้อมูลแผนที่เกาหลี" }
  drive:   { real: false, source: "estimate", reason: "กฎหมายข้อมูลแผนที่เกาหลี" }
placesSearch: true
navigationApps: ["naver", "kakao", "google"]
```

และในชั้น 2 ของ prompt กลายเป็นข้อความสั้นๆ ที่โมเดลอ่านรู้เรื่อง:

> ทริปนี้ผ่าน 2 ประเทศ:
> **เกาหลีใต้ (วันที่ 2–11)** — เวลาเดินทางจริงมีเฉพาะ **ขนส่งสาธารณะ** · เดินและแท็กซี่เป็น
> **ค่าประมาณเท่านั้น** ต้องติดป้ายทุกครั้ง · นำทางใช้ Naver/Kakao
> **เวียดนาม (วันที่ 1, 11)** — เวลาเดินทางจริงมีครบทุกโหมด · นำทางใช้ Google Maps

### 6.3 กฎในชั้น 1 ที่รองรับ registry

> ก่อนพูดถึงเวลาเดินทางของวันไหน ให้ดูว่าวันนั้นอยู่ประเทศไหนจากตารางในชั้น 2
> ถ้าโหมดนั้นเป็น `real: false` ต้องติดป้าย "ค่าประมาณ" ทุกครั้งที่พูดถึง
> ถ้าทริปมีประเทศที่ไม่มีในตาราง ให้ถือว่า **ไม่รู้** และถามผู้ใช้ ห้ามเดาจากความรู้ทั่วไป

ข้อสุดท้ายสำคัญ — โมเดลรู้เรื่องข้อจำกัดแผนที่เกาหลีจากการฝึกอยู่แล้วบ้าง แต่ไม่รู้เรื่องประเทศอื่น
ครบและอาจล้าสมัย · registry ต้องเป็นแหล่งความจริงเดียว

### 6.4 สิ่งที่ยังไม่เสนอโดยตั้งใจ

`PLAN.md:77` ตัดสินแล้วว่า **ไม่เพิ่ม ODsay/Kakao/Naver API** (สมัครยาก ต้องยืนยันตัวตนแบบเกาหลี)
เอกสารนี้จึงออกแบบ registry ให้เสียบผู้ให้บริการเพิ่มได้ทีหลัง **แต่ไม่เสนอให้ทำตอนนี้**
ถ้าจะทำต้องคุยกับผู้ใช้ก่อน

prompt caching: อ่านจากแคช ~0.1× · เขียนแคช ~1.25× (TTL 5 นาที) / ~2× (TTL 1 ชม.)

สมมติต่อหนึ่งคำถาม:

| ส่วน | token | หมายเหตุ |
|---|---|---|
| prompt ชั้น 1 (แคช) | ~2,500 | อ่านจากแคชเกือบทุกครั้ง |
| prompt ชั้น 2 (แคช) | ~1,500 | ต่อทริป |

→ ราคาต่อคำถามโดยประมาณ **~$0.03** (ประมาณ 1 บาท)

⚠️ **ตัวเลข 800 token ของช่อง output คือจุดที่ประมาณการนี้เปราะที่สุด** เพราะ thinking กินโควตาก้อนเดียวกับคำตอบ
และปริมาณ thinking แปรตาม `effort` กับความยากของคำถาม · เวลาวัดจริงด้วย `count_tokens` ต้องวัด
**ยอด output รวม thinking** ไม่ใช่นับความยาวคำตอบที่ผู้ใช้เห็น ไม่งั้นจะประเมินต่ำไปหลายเท่า

|---|---|
| ช่วงวางแผนก่อนบิน ~20 คำถาม/วัน | ~$0.6/วัน (~20 บาท) |
| ระหว่างทริป 11 วัน ~30 คำถาม/วัน | ~$10 ทั้งทริป (~350 บาท) |
| เผื่อค่าทดสอบ/พัฒนา | ~$20–40 |

**สรุป: ทั้งโปรเจกต์น่าจะไม่เกิน $60 (~2,000 บาท)** — ซึ่งน้อยกว่าที่คนมักคาดไว้มาก
ตัวเลขนี้เป็นการประมาณจาก token count ที่คาด **ยังไม่ได้วัดจริง** ต้องวัดด้วย `count_tokens` ก่อนสรุป

**ตัวคุมค่าใช้จ่ายถ้าเกินคาด** เรียงจากที่ควรทำก่อน — **ข้อ 1 กับ 2 ต้องทำก่อนคิดเรื่องอื่นเสมอ**:
1. **ตรวจว่าแคชทำงานจริง** (`cache_read_input_tokens > 0` ทุกครั้งหลังคำถามแรก)
   ถ้าเป็น 0 แปลว่ามีอะไรทำให้ prefix เปลี่ยนทุกคำขอ (มักเป็นเวลาปัจจุบันหลุดเข้าชั้น 1/2) —
   แก้ตรงนี้จุดเดียวลดค่าใช้จ่ายได้มากกว่าทุกข้อที่เหลือรวมกัน
2. **ลด `effort` เป็น `low`** สำหรับคำถามสั้น
3. ตัดจำนวนผลลัพธ์จาก `find_places` เหลือ 3–5 รายการ ไม่ใช่ 20
4. rate limit ต่อทริป — ประสานกับ P6-DevOps (`docs/engine/devops.md`) ต่อยอดจาก `lib/rateLimit.ts`

🔴 **สิ่งที่ห้ามทำเพื่อลดค่าใช้จ่าย: ปิด thinking** — ดู 1.5 · ประหยัดได้ไม่กี่ร้อย token
แลกกับ tool ที่ไม่ถูกเรียกจริงโดยไม่มี error ให้จับ

### 9.2 อันไหน SQL ล้วน · อันไหนต้อง embedding (✅ รับแล้ว → **`D56`**)

**คำตอบสั้น: 10 ข้อข้างบนเป็น SQL ล้วนทั้งหมด · `E2` ไม่ต้องมี `pgvector`**
ยืนยันหัวข้อ **3** เดิมทุกตัวอักษร ไม่มีอะไรเปลี่ยนหลังจากไล่คำถามจริงมาแล้ว

P1 ถามถูกจุดว่า *"ถ้าต้องมี vector ต้องมีตั้งแต่ `E2` เพราะเป็นการตัดสินใจระดับสคีมา"*
— ผมตรวจข้อนี้แยกจากคำตอบ "ไม่ต้องทำ RAG" แล้ว เพราะเป็นคนละคำถาม และคำตอบคือ **ยังไม่ต้อง** ด้วยเหตุผลนี้:

> เติม `pgvector` ทีหลังคือ `create extension` + `alter table add column` + สร้าง index
> **ไม่มีคอลัมน์เดิมต้องเปลี่ยนรูป · ไม่มีตารางอื่นที่ดีไซน์ขึ้นกับมัน · ไม่มี FK ต้องกลับทิศ**
> ต้นทุนจริงของการเติมทีหลังคือ **การ backfill embedding** ซึ่งเป็นงาน compute ไม่ใช่งาน migration
> — และเราจะต้องจ่ายต้นทุนนั้นเท่าเดิมไม่ว่าจะสร้างคอลัมน์ไว้วันนี้หรือปีหน้า

ต่างจาก rank key (`D6`) หรือทิศ FK (`D52`) ที่ตัดสินผิดแล้วต้องรื้อของที่เขียนทับไปแล้ว
**คอลัมน์ vector ที่ว่างเปล่าไม่ได้ซื้ออะไรเลยนอกจากความรู้สึกว่าเตรียมไว้แล้ว**

#### ✅ แต่มีของที่**ต้อง**ตัดสินที่ `E2` จริง และไม่ใช่ vector — `pg_trgm`

คำถามข้อ **6** (*"ตลาดกลางคืน"* → `place_id`) เป็น **fuzzy text match ไม่ใช่ semantic search**
ผู้ใช้พิมพ์ชื่อไม่ครบ พิมพ์ผิด หรือพิมพ์ชื่อเกาหลีที่ก๊อปมาจากบล็อก — งานนี้ `pg_trgm` + `unaccent` ทำได้
และทำได้แม่นกว่า embedding ด้วยซ้ำสำหรับชื่อเฉพาะ (embedding มีนิสัยลาก "ตลาดกลางคืน" ไปหา
"ตลาดเช้า" เพราะใกล้กันเชิงความหมาย ทั้งที่เป็นคนละที่กันสิ้นเชิง)

🔴 **อันนี้เป็นการตัดสินใจระดับสคีมาจริง** เพราะเป็น GIN index บน `place_names.name`
→ **ขอ `pg_trgm` (+ `unaccent`) ที่ `E2` · ไม่ขอ `pgvector`**

**เงื่อนไขกลับมาคิดใหม่เรื่อง vector** ยังเป็น 3 ข้อเดิมในหัวข้อ **3** และต้องเกิด**พร้อมกันทั้งสามข้อ**

### 9.3 `place_names` แยกเป็นตารางต่างหากเพราะอะไร · ต้องค้นด้วยภาษาไหน (✅ รับแล้ว → **`D55`**)

#### ทำไมต้องแยก — 3 เหตุผล เรียงตามน้ำหนักจริง

1. **เพิ่มภาษาใหม่ต้องเป็น `insert` ไม่ใช่ `migration`** (นี่คือ `B6` ในรูปแบบของชื่อ)
   วันนี้ `Place` มี `nameTh`/`nameEn`/`nameLocal` ตายตัว 3 ช่อง · แพลตฟอร์มหลายประเทศแปลว่า
   ญี่ปุ่น/ไต้หวัน/เวียดนามเข้ามาเรื่อยๆ — **ทุกภาษาใหม่ = alter table = ต้องแตะโค้ดทุกจุดที่อ่านชื่อ**
2. **ที่เดียวมีหลายชื่อในภาษาเดียวกันได้** — ชื่อทางการ · ชื่อที่คนเรียกจริง · ชื่อบนป้าย
   คำถามข้อ **6** พึ่งข้อนี้โดยตรง: ผู้ใช้พูด "ตลาดกลางคืน" ไม่ใช่ชื่อทางการของที่นั้น
   **โครงสร้าง 3 คอลัมน์เก็บข้อนี้ไม่ได้เลย** ต้องเลือกว่าจะเก็บชื่อไหน แล้วอีกชื่อหายไป
3. **index เดียวครอบทุกภาษา** — `pg_trgm` บน `place_names.name` หนึ่ง index
   แทนที่จะเป็น 3 index บน 3 คอลัมน์ แล้วต้อง `or` กันตอน query

#### 🔴 3 อย่างที่รูปทรง `place_names(place_id, locale, name)` เปล่าๆ ยังขาด

| ขาดอะไร | ทำไมต้องมี |
|---|---|
| **`is_primary`** | ถ้ามี 2 แถวเป็น `ko` การ์ดจะโชว์อันไหน · ต้องมี partial unique index `(place_id, locale) where is_primary` **ไม่งั้นชื่อที่โชว์จะขึ้นกับลำดับที่ DB คืนมา ซึ่งเปลี่ยนได้เงียบๆ** |
| **`source`** | ชื่อจาก Google (`place_details_local_cache.name_local` · `D77` แยกออกจาก `place_details_cache` เมื่อ 25 ส.ค. · เดิม migration 0024) กับชื่อที่เราคัดเอง **มี ToS คนละแบบ** · ถ้าปนกันในตารางเดียวโดยไม่มีคอลัมน์บอก **เราจะลบเฉพาะของ Google ไม่ได้เมื่อจำเป็น** — เป็นเหตุผลเดียวกับที่หัวข้อ **3** ไม่ยอม embed ข้อมูล Google |
| **`addressLocal` ห้ามลงตารางนี้** | 🔴 **ที่อยู่ไม่ใช่ชื่อ** · มันอยู่บนแถว `places` · วันนี้ `Place.addressLocal` มีไว้เพราะ **บนแท็กซี่เกาหลี ที่อยู่ใช้ได้ดีกว่าชื่อร้าน** (คนขับป้อนเข้านำทางได้ตรง) · ยัดลง `place_names` แล้วมันจะโผล่ในผลค้นหาชื่อ |

#### ต้องค้นด้วยภาษาไหน

| locale | ค้น | โชว์ | เหตุผล |
|---|---|---|---|
| `th` | ✅ | ✅ | ภาษาผู้ใช้ |
| `en` | ✅ | ↩︎ fallback | ชื่อที่บล็อก/รีวิวสากลใช้ |
| `ko` / `vi` / ท้องถิ่น | ✅ **จำเป็น** | ✅ คู่กับไทยเสมอ | ผู้ใช้ก๊อปชื่อเกาหลีจาก IG/บล็อกมาถามตรงๆ — **ถ้าค้น `ko` ไม่ได้ คำถามข้อ 6 ตายทันที** |

**กฎการโชว์:** ชื่อท้องถิ่นขึ้น**คู่กับ**ชื่อไทยเสมอ ไม่ใช่แทนที่
· fallback ตอนไม่มีชื่อในภาษาที่ขอ: `th → en → local → id` และ **ต้องบอกว่า fallback**
ไม่ใช่เงียบๆ โชว์ภาษาอื่น (Copilot ที่ตอบเป็นไทยแล้วแทรกชื่ออังกฤษโดยไม่บอก อ่านเหมือนพิมพ์ผิด)

### 11.1 ตารางที่ P1 ขอ — query shape ต่อคำถาม

เรียงตามความถี่จริงเหมือน **9.1** · `deleted_at is null` เป็นเงื่อนไขร่วมทุกข้อ (`D7`) ไม่เขียนซ้ำ

| คำถาม | filter | join | order | index ที่บังคับ |
|---|---|---|---|---|
| **① resolve** `place_id[]` → ชื่อ/พิกัด/หมวด | `id = any($1)` | `place_names` (`is_primary` · locale) | ตามลำดับที่ส่งเข้าไป | PK + 🔴 `place_names (place_id, locale) where is_primary` |
| **② browse** *"ปูซานมีที่ไหนอีก"* | `city_id = $1` | **anti-join** `trip_stops` (ทริปนี้) + `hidden_places` | `category` → ชื่อ | 🔴 **`(city_id, category)` — index หลักของคลัง** |
| **③ fuzzy name** *"ตลาดกลางคืน"* → `place_id` | `name % $1` (`D56`) **+ จำกัดขอบเขตเมืองก่อน** | `place_names` → `places` | `similarity() desc` | GIN trgm บน `place_names.name` |
| **④ ในร่ม/กลางแจ้ง** (11.2) | `city_id = $1 and weather_sensitivity = 'indoor'` | — | `category` | **ไม่ต้องเพิ่ม** — ดู 11.3 |
| **⑤ transport?** | `category = 'transport'` | — | — | ครอบด้วย ② แล้ว |
| **⑥ ประเทศ/ความสามารถ** | `cities.id = $1` | `countries` | — | PK พอ (ตารางหลักสิบแถว) |

#### 🔴 3 ข้อที่ตารางข้างบนบังคับ และมองไม่เห็นถ้าดูแค่รายชื่อคอลัมน์

**① `place_names` ต้องถูก join แบบ batch ไม่ใช่ทีละแถว**
`get_day_schedule` คืนจุดแวะ n จุด และ **ต้องแปลงเป็นชื่อให้ครบก่อนพูดได้แม้แต่ประโยคเดียว**
→ ถ้า resolve เป็น n query มันคือ N+1 ที่ยิงทุกเทิร์นของบทสนทนา ไม่ใช่ทุกการโหลดหน้า
· **Copilot ยิงถี่กว่าคนลากนิ้วมาก** (เหตุผลเดียวกับที่ `2.5` ยกเรื่อง rebalance)

**② ③ ต้องจำกัดขอบเขตเมือง *ก่อน* ค้นชื่อ ไม่ใช่หลัง**
คลังของแพลตฟอร์มหลายประเทศจะมี "ตลาดกลางคืน" อยู่ทุกประเทศ · ค้นทั้งคลังแล้วค่อยกรอง
= ผู้ใช้ถามถึงปูซานแล้วได้ที่ในไทเปมาอันดับหนึ่ง **ด้วยคะแนน similarity ที่สูงกว่าจริงๆ**
🔴 **ผลกับ DDL: `place_names` ต้องกรองด้วยเมืองได้โดยไม่ join กลับ `places` ทุกครั้ง**
→ เสนอ **denormalize `city_id` ลง `place_names`** แล้วทำ index เป็น `(city_id)` + GIN trgm
· ⚠️ นี่คือการ denormalize จริงๆ และมันมีราคา — **ย้ายสถานที่ข้ามเมืองต้องอัปเดต 2 ตาราง**
  ผมเสนอเพราะ *"สถานที่ย้ายเมือง"* แทบไม่เกิด ส่วน *"ค้นชื่อ"* เกิดทุกเทิร์น **แต่ P1 ตัดสิน ไม่ใช่ผม**

**③ ② ไม่มีอะไรให้เรียงเลยนอกจากชื่อ — และนั่นถูกต้องแล้ว**
คนจะอยากเรียง browse ด้วย **เรตติ้ง** ทันที · **9.4 ข้อ 2 ห้ามเก็บเรตติ้งไว้แล้ว**
→ ถ้าอยากเรียงตามความนิยมจริง ต้องยิง Google ตอนนั้น **ไม่ใช่เติมคอลัมน์ `rating` เข้าคลัง**
🔴 **นี่คือจุดที่ 9.4 จะถูกกดดันให้แตกเป็นจุดแรก** จดไว้ให้เห็นตอนรีวิว DDL

### 11.2 🔴 คอลัมน์ที่ผมตกไปใน 9.1 — คำถามของ P1 เปิดมันขึ้นมา

*"ที่เที่ยวในร่มแถวนี้ ถ้าฝนตก"* — **9.1 ทั้งตารางไม่มีข้อนี้ และมันควรมี**

ผมเอามันผ่านเกณฑ์ของ **9.4** ทุกข้อก่อนเสนอ:

| เกณฑ์ | ผล |
|---|---|
| เน่าได้ไหม | ❌ **ไม่** — พิพิธภัณฑ์อยู่ในร่มถาวร · ชายหาดอยู่กลางแจ้งถาวร |
| Google มีให้ไหม | ❌ **ไม่มีฟิลด์ที่ใช้ได้จริง** — เดาจาก `primaryType` ได้บ้างแต่ผิดบ่อย (ตลาดมีทั้งมีหลังคาและไม่มี) |
| Copilot ตอบได้ไหมถ้าไม่มี | ❌ **ไม่ได้เลย** — และเป็นคำถามที่จะถูกถามจริงมาก เกาหลีเดือน ต.ค. ฝนตก |
| ใครดูแลให้ไม่เก่า | ✅ **ไม่ต้องดูแล** — ตั้งครั้งเดียวตอนเพิ่มสถานที่ |

→ **เสนอ `weather_sensitivity: indoor | outdoor | mixed`** (ไม่ใช่ `indoor boolean`)
เพราะ *"มีหลังคาแต่ยังหนาว"* กับ *"ในตึกจริงๆ"* ต่างกันในทางที่มีผลกับคำตอบ
· `mixed` = ตลาดมีหลังคา · วัดที่เดินกลางแจ้งระหว่างอาคาร
· ⚠️ **ห้ามให้ Copilot เดาค่านี้เองจากหมวด** — `culture` เป็นได้ทั้งสามค่า

📌 **บันทึกไว้ว่าทำไมผมตกข้อนี้:** ผมไล่จาก **7 เคสใน 4** ซึ่งเขียนตอนทริปเกาหลีเป็นโจทย์เดียว
**เคสเหล่านั้นไม่มีเคสสภาพอากาศเลย** → ผมได้คำถามครบตามที่มีอยู่ แต่ไม่ครบตามที่ผู้ใช้จะถาม
· **การไล่จากรายการที่มีอยู่ ให้ผลที่ครบเท่ากับรายการนั้น ไม่ใช่ครบเท่าความจริง**

### 11.3 คอลัมน์ vs `jsonb` vs index — กฎที่ผมใช้ตอบ P1

**กฎเดียว:** *ถ้ามีคำถามใน **9.1**/**11.1** ข้อไหน `filter` หรือ `order` ด้วยมัน — **มันต้องเป็นคอลัมน์***

→ คอลัมน์: `city_id` · `category` · `weather_sensitivity` · `lat`/`lng` · `source` · `google_place_id`
→ **`jsonb` ไม่ควรมีเลยในตารางนี้** · ของที่อยากยัดลง `jsonb` เกือบทั้งหมดคือของใน **9.4** ที่ไม่ควรมีตั้งแต่แรก
· `jsonb` ในคลังจะกลายเป็นที่ที่เรตติ้งกับเวลาเปิด-ปิดแอบกลับเข้ามาโดยไม่ต้องผ่านการรีวิวคอลัมน์

**index — ขอแค่ 2 ตัวที่ `E2`:** `(city_id, category)` และ GIN trgm บน `place_names.name`
🔴 **ไม่ต้องทำ index ให้ ④** — เมืองหนึ่งมีสถานที่ระดับหลักสิบถึงหลักร้อย กรองในหน่วยความจำหลัง ② เร็วกว่า
**index ที่เพิ่มไว้เผื่อ คือของที่ต้องดูแลโดยไม่มีใครรู้ว่ามันเคยช่วยอะไรไหม**

### 11.4 ② `pgvector` — **ไม่ · และข้อโต้แย้งใหม่ของ P1 ทำให้คำตอบแข็งขึ้น ไม่ใช่อ่อนลง**

> ⚠️ ข้อนี้ **ตัดสินไปแล้วเมื่อ 24 ส.ค. = `D56`** — ตอบซ้ำเพราะ P1 ยกเหตุผลใหม่ที่ `D56` ยังไม่ได้ตอบ
> **ไม่ใช่การเปิดมติใหม่** · ถ้าคำตอบนี้ขัดกับ `D56` เมื่อไหร่ ให้ถือ `D56` แล้วมาคุยกัน

P1 ชี้ว่า: *"ถ้าต้องมี embedding ต่อสถานที่ มันเปลี่ยนว่า `catalog.places` เป็นตารางเดียวหรือต้องมีตารางลูก
และเปลี่ยนว่าใครเป็นคนเขียนแถวนั้น"* — **ข้อนี้ถูกทั้งข้อ และคำตอบของมันไม่ขึ้นกับเวลา:**

> 🎯 **embedding ต้องอยู่ในตารางลูกเสมอ ไม่ว่าจะเพิ่มวันนี้หรือปีหน้า**
> เพราะมัน **ผูกกับรุ่นของโมเดล** — วันที่เปลี่ยนโมเดล embedding ต้อง re-embed ทั้งคลัง
> และระหว่างย้ายต้อง **ถือสองรุ่นพร้อมกัน** ไม่งั้นค้นไม่ได้ระหว่างทาง
> คอลัมน์ `vector` บน `places` ถือได้รุ่นเดียว · `place_embeddings(place_id, model, embedding)` ถือได้ n รุ่น

**ผลตรงกับคำถามทั้ง 2 ข้อของ P1:**
- *"ตารางเดียวหรือตารางลูก"* → **ตารางลูก และรู้คำตอบแล้ววันนี้** · `catalog.places` จึงหน้าตาเหมือนกันเป๊ะทั้งสองทาง
- *"ใครเขียนแถวนั้น · policy คนละแบบ"* → **ตารางลูกมี policy ของตัวเอง** (เซิร์ฟเวอร์เขียนอย่างเดียว)
  → **ไม่ปนเปื้อน policy ของ `catalog.places` เลย** ซึ่งเป็นสิ่งที่ P1 กังวลพอดี

✅ **ตอบตรงตามที่ P1 ขอ ไม่ใช่ "น่าจะดี": ไม่ต้องมี `pgvector` ที่ `E2`**

**ราคาที่ P1 ขอให้ยืนยันว่ายอมจ่าย — ยอม และมันไม่ใช่ราคาที่ประหยัดได้:**
backfill embedding ทั้งคลังต้องจ่ายอยู่ดี **เพราะ embed แถวที่ยังไม่มีอยู่ไม่ได้**
· สร้างคอลัมน์ว่างไว้วันนี้ไม่ได้ลดงาน backfill แม้แต่แถวเดียว

#### เงื่อนไขที่ต้องเกิดก่อนถึงจะรู้ — P1 ขอมาตรงๆ ว่าจะได้ไม่รอเปล่า

**ทั้ง 3 ข้อต้องเกิดพร้อมกัน** (เดิมอยู่ใน **3** · เขียนให้วัดได้ตามที่ P1 ขอ):

| # | เงื่อนไข | วัดยังไงว่าเกิดแล้ว |
|---|---|---|
| 1 | ผู้ใช้ถามข้ามทริปได้ | มีผู้ใช้ที่มี **≥ 3 ทริปจบแล้ว** ในระบบ |
| 2 | มีข้อความยาวจริงให้ embed | `trip_stops.note` + รีวิวที่เขียนเอง **ยาวเฉลี่ย > 200 ตัวอักษร และมี > 500 แถว** |
| 3 | วัดแล้วว่า query ตรงตอบไม่ได้ | มี log ของคำถามที่ `pg_trgm` คืน 0 แถว **แล้วผู้ใช้ถามซ้ำด้วยคำอื่น** > 10% ของ session |

🔴 **ไม่มีข้อไหนเป็นจริงได้ก่อน `E8` เพราะ Copilot ยังไม่มีอยู่** — **P1 ไม่ต้องรออะไรเลยที่ `E2`**
· ข้อ 2 คือข้อที่จะเกิดก่อนเพื่อน และมันเกิดที่ **`trip_stops.note` ไม่ใช่ที่คลัง** → ตอนนั้นตารางลูกจะห้อยกับ `trip_stops` ไม่ใช่ `catalog.places` ด้วยซ้ำ

## 14. `is_primary` — **หนึ่ง ไม่ใช่ "ไม่เกินหนึ่ง"** · และ partial unique index บังคับได้แค่ครึ่งเดียว (25 ส.ค. 2026)

> P1 ถาม: *"หนึ่งสถานที่ต่อหนึ่ง locale มี primary ได้กี่ชื่อ"* และเสนอ partial unique index
> `(place_id, locale) where is_primary` แบบเดียวกับ `D52`
> 🔴 **ผมเป็นคนเสนอ index ตัวนั้นเองใน 9.3 · และตอนนี้ผมคิดว่ามันไม่พอ — แก้ข้อเสนอตัวเอง**

### 14.1 คำตอบตรงคำถาม

> **หนึ่ง — และต้องเป็น "หนึ่งเป๊ะ" ไม่ใช่ "ไม่เกินหนึ่ง"**
> เงื่อนไขที่ถูกคือ: **ทุก `(place_id, locale)` ที่มีแถวอยู่อย่างน้อย 1 แถว ต้องมี primary หนึ่งแถวพอดี**

**partial unique index บังคับ `≤ 1` · มันไม่บังคับ `≥ 1`** — และช่องว่างนั้นคือบั๊กที่ **9.3** เขียนขึ้นมาเพื่อกันพอดี

### 14.2 สถานะ "ศูนย์ primary" ไปถึงได้ด้วย**การแก้ที่ธรรมดาที่สุด**ของตารางนี้

⚠️ ต้องแยกสองอย่างที่หน้าตาเหมือนกันก่อน:

| สถานะ | เป็นปัญหาไหม |
|---|---|
| `(place, 'ko')` **ไม่มีแถวเลย** | ✅ ปกติ — ที่ในฮานอยไม่จำเป็นต้องมีชื่อเกาหลี · fallback `th → en → local → id` ทำงานถูก |
| `(place, 'ko')` **มี 2 แถว ไม่มีอันไหน primary** | 🔴 **พัง** — มีชื่ออยู่แต่ไม่รู้จะโชว์อันไหน → กลับไปขึ้นกับลำดับที่ DB คืนมา **ซึ่งคือสิ่งที่ 9.3 ห้ามไว้ทั้งข้อ** |

**แถวที่สองเกิดจากอะไร:** มีคนลบชื่อเกาหลีที่ผิดออก แล้วแถวที่เหลือไม่ใช่ primary

> 🔴 **นั่นคือการแก้ที่ธรรมดาที่สุดที่จะเกิดกับตารางชื่อ — ไม่ใช่เคสประหลาด**
> และมันพังเงียบ: การ์ดยังขึ้นชื่อ · ไม่มี error · **แค่เป็นชื่อที่เปลี่ยนได้เองเมื่อ planner ของ Postgres เปลี่ยนใจ**

### 14.3 ทางที่เสนอ — `priority` แทน `is_primary` · ให้ `≥ 1` มาฟรีจากโครงสร้าง

```
place_names(place_id, locale, name, priority int, source, city_id)
unique (place_id, locale, priority)
อ่าน: distinct on (place_id, locale) … order by place_id, locale, priority
```

| ได้อะไร | ทำไม |
|---|---|
| **`≥ 1` ฟรี** | **เซตที่ไม่ว่างมีค่าน้อยสุดเสมอ** — ไม่มีทางไม่มี primary ถ้ามีแถวอยู่ |
| **ลบแถวไหนก็ไม่พัง** | ลบตัวที่ `priority=1` → ตัวถัดไปกลายเป็น primary **โดยไม่ต้องเขียนอะไรเลยสักแถว** |
| **เสมอไม่ได้** | unique `(place_id, locale, priority)` ปิดไว้ |
| **ไม่ต้องมี trigger · ไม่ต้อง `deferrable`** | เคารพ `P-27` ที่เพิ่งปฏิเสธ `deferrable` ไป |

**เทียบกับทางที่ต้องใช้ถ้าเก็บ `is_primary` ไว้:** partial unique index **บวก** trigger ที่ตรวจตอน `delete`/`update`
ว่ากลุ่มนั้นยังมี primary อยู่ — **สองกลไกที่ต้องถูกพร้อมกัน** แทนที่จะเป็นศูนย์กลไก

⚠️ **ราคาที่ผมไม่ซ่อน:**
- อ่านต้องใช้ `distinct on` ไม่ใช่ `where is_primary` — **อ่านออกน้อยกว่านิดหน่อย**
- *"ทำให้ชื่อนี้เป็น primary"* = ต้องหาเลขที่ว่าง หรือ renumber → **นี่คือปัญหาเดียวกับ rank key ของ `D6`**
  🎯 **แต่ไม่ใช่ปัญหาเดียวกันในทางปฏิบัติ:** ชื่อต่อ locale มี 2–4 แถว ไม่ใช่ 20 · แก้ชื่อไม่มี 2 คนทำพร้อมกัน
  · renumber 3 แถวในทรานแซกชันเดียวคือของฟรี **ต่างจากจุดแวะที่ `D6` ต้องเลี่ยงการเขียนทับทั้งวัน**
  → **ยกมาเพราะ P1 ควรเห็นความคล้ายแล้วตัดสินเอง ไม่ใช่เพราะผมคิดว่ามันบล็อก**

### 14.4 ถ้า P1 เลือก `is_primary` ต่อ — สิ่งที่ **ต้อง**มีคู่กัน

ผมไม่คัดค้านถ้าเลือกทางนั้น (อ่านง่ายกว่าจริง) **แต่ห้ามมีแค่ partial unique index ตัวเดียว**
ต้องมีตัวที่บังคับ `≥ 1` ด้วย และ 🔴 **มันต้องเป็นกลไกของฐาน ไม่ใช่วินัยของโค้ดที่เรียก**

> **เหตุผลเดียวกับ `2.3` ข้อ 1 เป๊ะ** — ร่างแรกของผมเขียน *"กันไม่ให้ยิงซ้อน"* ไว้ในคอมเมนต์
> แล้ว P4 ชี้ว่ามันคือรูปแบบเดียวกับบั๊ก `travel_time_cache`: **เจตนาอยู่ในคอมเมนต์ การบังคับไม่มีอยู่**
> `is_primary` ที่ไม่มีตัวบังคับ `≥ 1` คือรูปแบบนั้นอีกครั้ง — **แค่ครึ่งบนถูกบังคับ จึงดูเหมือนมีด่านอยู่**

📌 **และนี่คือเหตุผลจริงที่ผมเปลี่ยนใจจาก 9.3:** ตอนเขียน **9.3** ผมถามว่า *"ถ้ามี 2 แถวจะโชว์อันไหน"*
แล้วตอบด้วย index ที่กัน 2 แถว · **ผมไม่ได้ถามว่า "ถ้ามี 0 แถวจะโชว์อันไหน"**
🎯 **คำถามที่ผมถามตัวเองมีทิศเดียว และ constraint ที่ได้ก็มีทิศเดียวตามมัน**

## 15. "คำถามมีทิศเดียว" — ข้อเดียวกับ `กฎ E0 ข้อ 1–2` ที่ขอบเขตแคบไปหนึ่งหมวด (25 ส.ค. 2026)

> P1 ถามว่ามันต่างจาก *"เคสด้านลบล้วน"* ที่ `rlsMatrix.test.ts` กันไว้ตั้งแต่ต้นยังไง
> **คำตอบ: ข้อเดียวกัน · และมันมีเลขอยู่แล้ว — `กฎ E0 ข้อ 1–2`**

```
lib/__tests__/rlsMatrix.test.ts:449
🔴 กฎ E0 ข้อ 1–2: ด่านต้องมีเทสต์ ทั้งด้านลบและด้านบวก
   ด้านลบอย่างเดียวไม่พอ — ฟังก์ชันที่คืน null ให้ทุกอย่างจะทำให้ด้านลบเขียวหมดทั้งชุด
```

### 15.1 รูปร่วมของทั้งหมด — **ผูกไว้ด้านบน ไม่ผูกด้านล่าง**

| กรณี | ผูกด้านบนว่า | ไม่ผูกด้านล่างว่า | สถานะว่างเปล่าที่ผ่านฉลุย |
|---|---|---|---|
| เคสด้านลบล้วน (`rlsMatrix` กับดัก 3) | คนนอก**ต้องไม่**เห็น | เจ้าของ**ต้อง**เห็น | RLS บล็อกทุกคน |
| ด่านที่เขียวตั้งแต่รอบแรก (P1) | ต้อง**ไม่**มีธงค้าง | ต้อง**เห็น**ธงที่มีจริง | ฟังก์ชันคืน 0 แถวเสมอ |
| `place_names` (ผม · **14**) | primary **≤ 1** | primary **≥ 1** | ไม่มี primary เลย |

🎯 **ทุกช่องขวาสุดคือ "ระบบที่ไม่ทำอะไรเลย" — และมันนั่งอยู่ก้นล่างของขอบที่ไม่มีใครผูก**

**คำถามที่ใช้ได้กับทั้งด่าน · เทสต์ · constraint:**
> **"อะไรคือสถานะที่*ว่างเปล่าที่สุด*ที่ยังผ่านข้อนี้ได้"**
> ถ้าคำตอบคือ *"ระบบที่ไม่ทำอะไรเลย"* → **คุณผูกไว้ด้านเดียว**

### 15.2 ทำไม `E0` ข้อ 1–2 ที่มีอยู่แล้วยังจับผมไม่ได้

**ไม่ใช่เพราะกฎผิด — เพราะขอบเขตของมันแคบไปหนึ่งหมวด:**

> กฎเขียนว่า **"ด่าน"** ต้องมี **"เทสต์"** สองทิศ
> `place_names` **ไม่ใช่ด่าน** และ **ไม่มีเทสต์เลย** — มันคือ constraint ในสคีมา
> → ผมอ่านกฎนั้นมาแล้ว และมันไม่ได้ชี้มาที่ผมสักนิด เพราะผมไม่ได้กำลังเขียนเทสต์ของด่าน

**สิ่งที่กฎกำลังพูดถึงจริงๆ ไม่ใช่เทสต์ — มันคือ *ข้อรับประกันทุกชนิด*** และ `constraint` ก็เป็นข้อรับประกัน
ที่ **ไม่มีเทสต์เป็นตัวกลาง** จึงหลุดจากประโยคที่ขึ้นต้นว่า "ด่านต้องมีเทสต์"

### 15.3 🔴 ผมเสนอว่า **ไม่ควรให้เลขใหม่** — และเหตุผลคือ `D71` ในทิศกลับ

ถ้าออกเลขใหม่ เราจะมี **สองบันทึกของกฎเดียวกัน** — `กฎ E0 ข้อ 1–2` กับเลขใหม่
· คนที่ `grep` เจอทั้งคู่จะไม่รู้ว่าอันไหนคือของจริง **ซึ่งคือสิ่งที่ `D71` เพิ่งสอนเราวันนี้ทั้งวัน**

**เสนอแทน:**
1. **ขยายถ้อยคำของ `E0` ข้อ 1–2** จาก *"ด่านต้องมีเทสต์สองทิศ"* → *"ข้อรับประกันทุกชนิด (เทสต์ · ด่าน · constraint · index) ต้องผูกทั้งสองขอบ"*

### 17.2 🔴 "คีย์ที่มีสิทธิ์" คืออะไร — และด่านมีช่องที่สอง ที่**กัดได้ตั้งแต่วันนี้**

นิยามนี้ทดสอบด้วย static scan ตรง ๆ ไม่ได้ → **จึงต้องกลับทิศของด่าน:**

| วันนี้ | เสนอ |

**นี่คือ 15 อีกครั้ง:** ด่านวันนี้ผูกไว้ด้านเดียว (ชื่อที่รู้ว่าแย่) · allowlist ผูกอีกด้าน (ทุกอย่างที่ไม่รู้ว่าดี)
