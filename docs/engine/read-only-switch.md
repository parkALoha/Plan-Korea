# `E3-AC7` — สวิตช์โหมด read-only: บัญชีทางเขียนทั้งหมด

เจ้าของ: **P1-Lead** · 26 ส.ค. 2026 · สถานะ: **ยังไม่เขียนโค้ด รอคำตอบ P6 + P7**

> เอกสารนี้เป็น *บัญชีของสิ่งที่สวิตช์ต้องครอบ* — ต้องมีไม่ว่ากลไกสุดท้ายจะเป็นแบบไหน
> ทำก่อนเลือกกลไก เพราะกลไกที่ครอบไม่ครบคือกลไกที่ผิด ไม่ใช่กลไกที่ทำไม่เสร็จ

## 1. 🔴 ข้อความในเกณฑ์ที่ผมเขียนเองและ **ไม่จริง** — ถอนแล้ว

`E3-AC7` เขียนว่าชั้น DB (`revoke` สิทธิ์เขียน) *"ไม่มีทางเดินอ้อม **แม้ผ่าน RPC/Server Action**"*

**ท่อน "แม้ผ่าน RPC" ผิด** · ฟังก์ชันที่ไคลเอนต์เรียกได้ **7 ตัวเป็น `security definer`**:

| ฟังก์ชัน | ทำอะไร |
|---|---|
| `create_trip` | สร้างทริป |
| `soft_delete_booking` · `soft_delete_checklist_item` · `soft_delete_custom_place` · `soft_delete_place_note` · `soft_delete_trip_hotel` · `soft_delete_trip_stop` | ลบทุกชนิดของผู้ใช้ |

`security definer` รันด้วยสิทธิ์ของ**เจ้าของฟังก์ชัน** → `revoke` จาก `authenticated` ไม่มีผลข้างในมันเลย

🎯 **ไม่ใช่การคาดเดา — หลักฐานสดมีอยู่แล้ววันนี้:** `soft_delete_*` ทั้ง 6 ตัวเขียน `deleted_at` ได้
ทั้งที่ `deleted_at` **ไม่อยู่ใน column grant ของ `authenticated` เลยสักตาราง**
(`client_writable_timestamps(['deleted_at'])` → `[]`) — definer เขียนข้ามสิทธิ์ผู้เรียกอยู่แล้ว *โดยการออกแบบ*

→ **read-only ที่ทำด้วย `revoke` อย่างเดียว จะเหลือทางเขียนเปิดอยู่ 7 ทาง รวม "ลบ" ทุกชนิด**

## 2. บัญชีทางเขียน — 3 กลุ่ม คนละกลไก

### ① ผ่าน DAL ตรง ๆ — **24 จุดใน `lib/engine/db.ts`**
`insert` / `update` / `upsert` / `delete` บน `trip_days` · `hidden_places` · `place_notes` ·
`trip_hotels` · `checklist_items` · `trip_day_plan_settings` · `bookings` · `trip_plans` · `trip_stops`
· กลุ่มนี้ `revoke` หรือ policy กันได้จริง

### ② ผ่าน RPC — **11 ตัวที่ไคลเอนต์เรียกได้ · 7 ตัวเป็น definer** (ดูข้อ 1)
· `invoker` 4 ตัว (`create_custom_place` · `duplicate_trip_plan` · `set_active_plan` · `search_place_names`)
  ถูก `revoke` กันได้ตามปกติ **เพราะมันเขียนด้วยสิทธิ์ของผู้เรียก**
· `definer` 7 ตัว **ต้องมีกลไกอื่น**

### ③ 🔴 ไฟล์ใน Storage — **7 จุด ที่ไม่มีใครพูดถึงตอนเขียนเกณฑ์**
```
components/BookingEditModal.tsx   upload ×1 · remove ×4
lib/stopPhoto.ts                  upload ×1 · remove ×2
```
· ⚠️ **ไม่ได้อยู่นอก Postgres อย่างที่ดูเผิน ๆ** — Supabase Storage เก็บ metadata ใน `storage.objects`
  ซึ่งมี RLS ของตัวเอง → **ครอบได้ แต่ต้องตั้งใจครอบ ไม่ใช่ได้มาฟรีจากการทำ `public`**
· 🔴 **ถ้าลืมกลุ่มนี้ ผลคือ "อ่านอย่างเดียว" ที่ยังอัปโหลดและ *ลบไฟล์* ได้** — ลบไฟล์เป็นการทำลาย
  ที่ย้อนไม่ได้ และเป็นสิ่งที่ read-only ควรกันมากที่สุด

## 3. กลไกที่ผมจะเสนอ (ยังไม่ตัดสิน รอ P6/P7)

**`before insert/update/delete` trigger ที่ใช้ฟังก์ชันร่วมตัวเดียว บนทุกตารางของผู้ใช้**

เหตุผล: **trigger ยิงกับทุกการเขียน ไม่สนว่าคนเขียนเป็นใครหรือมาจาก `security definer`**
— เป็นจุดคอขวดเดียวที่ครอบทั้ง ① และ ② ได้พร้อมกัน · `grant` ทำไม่ได้ · policy ทำไม่ได้กับ definer

🔴 **และมันขัดกับสิ่งที่ผมเขียนไว้เองใน `…122247_e2_freeze_row_times.sql`:**
> *"trigger ที่ยกเว้นตาม role คือด่านที่เชื่อว่าคนเรียกเป็นใคร ซึ่งเปราะกว่าสิทธิ์"*

ถ้า `E7` ต้องเขียนได้ระหว่างโหมดนี้ trigger **ต้อง**ยกเว้น `service_role` = ต้องเชื่อ role พอดี
**ผมยังไม่มีคำตอบที่ดีสำหรับความขัดแย้งนี้** และเป็นเหตุผลที่คำถามข้อ 3 ถึง P6 สำคัญที่สุด

## 3.5 🔴 วัดแล้ว — และผลทำให้ "ยกเว้นตาม role" ใช้ไม่ได้เลย (26 ส.ค. 2026)

P6 ตั้งสมมติฐานว่า trigger ที่ถูกยิงจากข้างใน `security definer` เห็น `current_user`
เป็น**เจ้าของฟังก์ชัน** ไม่ใช่ผู้เรียก · เขายืนยันเองไม่ได้ (เครื่องไม่มี `psql`/docker)
→ วัดบน engine-dev (`20260826182000`) · ผลอ่านซ้ำได้ผ่าน `public.role_probe_result()`

| เส้นทาง | `current_user` ที่ trigger เห็น | GUC |
|---|---|---|
| เขียนตรง ในฐานะเจ้าของ | `postgres` | – |
| ผ่าน definer ในฐานะเจ้าของ | `postgres` | – |
| 🔴 **ผ่าน definer ในฐานะ `authenticated`** | **`postgres`** | – |
| ผ่าน definer ในฐานะ `authenticated` + ตั้ง GUC ก่อนเรียก | `postgres` | **`on`** |

**สมมติฐานของ P6 จริง** · แถวที่ 3 คือคำตอบ: ผู้เรียกเป็น `authenticated` แต่ trigger เห็น `postgres`

🎯 **ผลที่ตามมา — และมันแรงกว่าคำว่า "เปราะ" ที่ผมใช้ตอนแรก:**
เงื่อนไข *"ยกเว้นถ้า `current_user` เป็น `postgres`/`service_role`"* จะยกเว้น
**ทั้ง 7 RPC ที่ trigger เกิดมาเพื่อปิดพอดี** — มัน **whitelist เป้าหมายของตัวเอง**
· และมันจะ **เขียวสนิท**: ทางตรงถูกปิดจริง คนทดสอบเห็นว่า "เขียนไม่ได้"
  **แต่ผู้ใช้ยังลบทุกอย่างและสร้างทริปได้ตามปกติ** — ซึ่งเป็นทางที่คนใช้จริง

✅ **แถวที่ 4 ยืนยันทางออกของ P6 ว่าใช้ได้จริง:** GUC ที่ตั้งด้วย `set local` **ข้ามชั้น definer
ไปถึง trigger ได้** → ยกเว้นตาม *เจตนาที่ประกาศไว้ในทรานแซกชัน* ไม่ใช่ตาม *ตัวตน*
· 🔴 **ยังต้องพิสูจน์อีกข้อก่อนใช้จริง: ไคลเอนต์ตั้ง GUC ตัวนี้เองได้ไหมผ่าน PostgREST/JWT**
  ถ้าตั้งได้ ทางยกเว้นกลายเป็นทางเข้า — **ขอ P4 ยิงหาทางตั้งมันให้ได้ก่อนผมเขียนโค้ด**

⚠️ **ขอบของการวัดนี้:** จำลองผู้เรียกด้วย `set local role authenticated` ในทรานแซกชันเดียว
ทางที่ผู้ใช้จริงเดินคือ PostgREST + JWT · **ผลตรงกันได้ไม่ได้แปลว่าเหมือนกันทุกอย่าง**

## 4. คำถามที่ค้างอยู่ — **ยังไม่เขียนโค้ดจนกว่าจะได้คำตอบ**

**P6 — ตอบครบแล้ว 26 ส.ค. 2026:** ① **SQL คำสั่งเดียว** (ไม่เอา dashboard: ไม่เหลือร่องรอยว่าใครกดเมื่อไหร่ · ไม่เอา env: บังคับ definer ไม่ได้)
② **ทันที** → `revoke`/`grant` ชนะการแก้ policy N ตัว เพราะ *"แก้ N ตัว = มี N วิธีที่จะย้อนไม่ครบ และตัวที่ย้อนไม่ครบจะเงียบ"*
③ **ต้องเขียนได้** (`E7` คือการเขียน) → ยกเว้นด้วย `set local app.maintenance_write` **ไม่ใช่ด้วย role** (ดู §3.5)
④ **ไม่มีสถานะกลาง ทั้งระบบอย่างเดียว** — *"บางทริปเขียนได้บางทริปไม่ได้ อธิบายกับผู้ใช้ไม่ได้ และซัพพอร์ตไม่ออก"*
⑤ อ่านสถานะจากฐานผ่าน RPC · **และชุดสดต้อง *ล้มพร้อมบอกเหตุผล* ถ้ารันตอนโหมดเปิด** ไม่ใช่พ่น `42501` ให้คนไปไล่หาบั๊กใน policy ที่ไม่มีบั๊ก
· 🔴 **ข้อบังคับ ops 2 ข้อ:** ตารางสวิตช์ต้องอยู่ใน schema ที่ DB ทริปจริงไม่มี (รันผิดฐาน = **ล้มเพราะไม่มีตาราง**)
  · ข้อความต้องบอกว่า *"ระบบอยู่ในโหมดอ่านอย่างเดียว"* ไม่ใช่ *"บันทึกไม่สำเร็จ"* — ไม่งั้นตอบไม่ได้ว่า *"มันพังหรือมันตั้งใจ"*
· ✅ **`ci.yml` รัน `next build` อยู่แล้ว** (`ci.yml:112`) → ด่าน `server-only` มีอะไรบังคับจริงบน CI

**P7 — ตอบครบแล้ว 26 ส.ค. 2026:** ① **`revoke` แนบ `errcode` ของตัวเองไม่ได้ตามนิยาม** → สัญญาณต้องมาแยกทาง เป็นธงที่ `authenticated` อ่านได้ (รูปเดียวกับ `unsafe_state_reason()` คนละสิทธิ์)
· **ข้อบังคับที่มาคู่กัน: ระหว่างโหมดนี้ `select` ต้องไม่ถูกถอน** ไม่งั้นธงเองก็อ่านไม่ได้ (`P-50`: *ธงที่อ่านไม่ได้ ไม่ใช่ธง*)
② **ไม่มีคิว จึงไม่มีเพดาน · ห้ามมี auto-retry เลย** — ผู้ใช้เป็นคนลองใหม่ ทุกความล้มเหลวมี toast
③ **ธงต้องขับ banner ตอน *โหลด* ไม่ใช่ตอน *เขียนพลาด*** — คนที่กลับมาต้องรู้ก่อนเริ่มพิมพ์ · ปิดปุ่ม = **การสื่อสาร ไม่ใช่การบังคับ**
④ **การเขียนที่ประกอบจาก snapshot เก่า ห้ามถูกเล่นซ้ำทีหลัง** ไม่ว่ากรณีใด
⑤ ด่าน cutover: *"อย่าทำตอนนั้น"* → *"ทำตอนนั้นไม่ได้"* · 🔴 **P1 ค้าน: ประธาน "ทั้งแพลตฟอร์ม" จะไม่มีวันว่างเมื่อมีผู้ใช้จำนวนมาก** → ต้องเปลี่ยนหน่วยประธาน หรือยอมรับว่ากระทบแล้วออกแบบให้รู้ตัวก่อน · **ยังไม่สรุป**

**เดิม:**

**P7** ① `42501` จากโหมดนี้ ต่างจาก `42501` ที่แปลว่า "ไม่มีสิทธิ์จริง" ยังไง — ในสายตาคิวออฟไลน์
② คิวมีเพดานลองใหม่ไหม · ③ ผู้ใช้เห็นอะไร · ④ op ที่แก้ของเดิมควรลองใหม่ไหม (conflict model)
⑤ 🔴 **ถ้า cutover เกิดตอนผู้ใช้อยู่ในทริปจริงและไม่มีสัญญาณ** — คำตอบที่ถูกอาจเป็นข้อกำหนดเชิงเวลา
   (*อย่าให้ cutover เกิดตอนมีคนอยู่ในทริป*) ไม่ใช่เชิงโค้ด

## 6. 🔴 ผลข้างเคียงที่ตั้งใจ และคนแรกที่เจอจะคิดว่าเป็นบั๊ก (P6 ขอให้จด)
