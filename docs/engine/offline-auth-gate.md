# ประตูตรวจสิทธิ์กับการใช้งานออฟไลน์ — ข้อเสนอ (ยังไม่ลงมือ)

> 🔴 **เป็นการแก้ประตูตรวจสิทธิ์ — ห้ามลงมือก่อนมีคนพยายามหักมัน**

## 1. อาการ — **ผู้ใช้เจอเอง ไม่ใช่สมมติฐาน**

ผู้ใช้ปิด Wi-Fi แล้วกดรีเฟรชหน้าทริป → **เด้งไป `/login?next=/trip/…`**
ทั้งที่เพิ่งพิสูจน์ไปเมื่อครู่ว่า IndexedDB มีข้อมูลครบ (11 วัน · 62 จุดแวะ · ที่พัก · ตั๋ว 8 ใบ)

```
lib/auth/proxySession.ts:58
  const { data, error } = await supabase.auth.getUser();
  return { response, user: error ? null : (data.user ?? null) };
                     ↑ error ตัวไหนก็ตาม → ถือว่าไม่ได้ล็อกอิน
```
🎯 **แยกไม่ออกระหว่าง *"token ใช้ไม่ได้"* กับ *"ถามไม่ได้"* — แล้วเลือกตอบว่าไม่ได้ล็อกอิน**

## 2. ⚠️ ขอบเขตของหลักฐาน — อย่าอ่านเกิน

ผู้ใช้ทดสอบบนเครื่องตัวเอง · **ปิด Wi-Fi ไม่ตัด `localhost`** → เซิร์ฟเวอร์ยังทำงาน แล้วไปถาม Supabase ผ่านเน็ตซึ่งล้ม
· ตอนอยู่ต่างประเทศไม่มีสัญญาณจริง เว็บอยู่บนโดเมนจริง → **ต่อไม่ติดตั้งแต่แรก → SW เสิร์ฟ shell จากแคช → `proxy.ts` ไม่ทำงานเลย**
· 🔴 **แปลว่าที่เจอคือกรณี *"ต่อเว็บได้ แต่ต่อ Supabase ไม่ได้"* ไม่ใช่ *"ไม่มีสัญญาณ"***

**แต่กรณีนั้นเกิดจริงระหว่างทริปได้ และอาจบ่อยกว่าไม่มีสัญญาณเลย:**
สัญญาณอ่อนในรถไฟใต้ดิน · Wi-Fi ที่ต้องกดยอมรับก่อน (captive portal) · Supabase ล่มเอง

## 3. 🔴 เหตุผลที่เขียนไว้ในโค้ด **หมดอายุไปแล้ว — และไม่มีใครไปแตะมัน**

`proxy.ts:46-52` เขียนเหตุผลของ fail-closed ไว้ตรง ๆ:
> *"แพลตฟอร์มไม่ใช่แบบนั้น: ตาราง · RLS · ตัวตน อยู่ใน Supabase ทั้งหมด
> **ไม่มี Supabase = ไม่มีข้อมูลให้แสดงอยู่แล้ว** → ปล่อยผ่านไม่ได้อะไรกลับมาเลย"*

**จริงตอนเขียน · เท็จตั้งแต่ `E6` ทำแคชออฟไลน์เสร็จ** — วันนี้ *มี* ข้อมูลให้แสดงโดยไม่ต้องมี Supabase และเราเพิ่งยิงพิสูจน์เอง
· 🎯 **ตระกูล `D71` เป๊ะ: กติกาที่เหตุผลหมดอายุแล้ว แต่ยังอ่านเหมือนบังคับอยู่** · อยู่ในคอมเมนต์ จึงไม่มีใครไล่วันที่
· ⚠️ **และครึ่งหนึ่งของเหตุผลนั้น *ยังจริง***: กรณี "ตั้ง env ไม่ครบ" ปล่อยผ่านแล้วได้หน้าเปล่าไม่มีด่าน ซึ่งไม่มีใครสังเกต

## 4. ข้อเสนอ — **ผ่าเป็นสามกรณี ไม่ใช่สอง**

| กรณี | วันนี้ | ข้อเสนอ |
|---|---|---|
| ไม่มี token / token ใช้ไม่ได้ | `/login` | **`/login` เหมือนเดิม** |
| ตั้งค่าไม่ครบ (ไม่มี env · auth ปฏิเสธเชิงโครงสร้าง) | `/login` | **`/login` เหมือนเดิม** |
| 🔴 **ติดต่อ auth ไม่ได้ (transport error) ทั้งที่มีคุกกี้ session อยู่** | `/login` | **ปล่อยผ่าน → ให้หน้าเรนเดอร์จากแคช** |

**แยกด้วยของที่มีอยู่แล้ว ไม่ต้องเดาจากสตริง:**
```ts
import { isAuthRetryableFetchError } from "@supabase/supabase-js";  // ตรวจแล้ว export จริง
```

### เงื่อนไขที่ต้องครบ **ทุกข้อ** ถึงจะผ่อน (แคบโดยตั้งใจ)
1. `isAuthRetryableFetchError(error)` เป็นจริง — **ไม่ใช่ `error` อะไรก็ได้**
2. **มีคุกกี้ session ของ Supabase อยู่จริง** — คนที่ไม่เคยล็อกอินต้องไม่ได้อะไรจากข้อนี้
3. **เส้นทางไม่ใช่ `/api/*`** — API ยังต้อง `401` เหมือนเดิม

### 🔴 สิ่งที่ **ห้าม** เปลี่ยน
· `/api/*` ยัง `401` — **ข้อมูลจริงยังต้องผ่าน RLS เสมอ** · ที่เรนเดอร์ได้คือของที่อยู่ในเครื่องผู้ใช้อยู่แล้ว
· ด่าน PIN · `/unlock` · `/auth/callback` ไม่แตะ
· ไม่ยืดอายุ session · ไม่เขียนคุกกี้ใหม่ตอนผ่อน

## 5. 🎯 ทำไมข้อนี้ถึงไม่ใช่ "เปิดช่อง"

**สิ่งที่ประตูนี้ป้องกันคือ *การเข้าถึงข้อมูล* ซึ่งอยู่ที่ RLS ไม่ใช่ที่นี่**
· ผ่านประตูแล้วยังไม่ได้ข้อมูลอะไรเพิ่ม — `/api/*` ยัง `401` · แคชในเครื่องเป็นของผู้ใช้คนนั้นเองอยู่แล้ว
· คนที่ไม่มีคุกกี้ session ไม่เข้าเงื่อนไขข้อ 2 ตั้งแต่ต้น

## 6. 🔴 ที่อยากให้ P4 พยายามหัก

1. **ปลอม transport error ได้ไหม** — บังคับให้ `getUser()` โยน retryable โดยที่ผู้โจมตีคุมได้ (เช่น ทำให้ Supabase ตอบช้าจน timeout) แล้วได้อะไรเพิ่ม?
2. **คุกกี้ session ที่หมดอายุ/ถูกเพิกถอนแล้ว** ยังนับเป็น "มีคุกกี้" ตามข้อ 2 ไหม — ถ้าใช่ ผู้ใช้ที่ถูกเตะออกจากทริปยังเปิดหน้าได้ระหว่างเน็ตล้ม (**ได้แค่ shell แต่ควรตอบให้ชัด**)
3. `isAuthRetryableFetchError` ครอบ `503`/`429` ด้วยไหม — ถ้าใช่ **Supabase rate-limit จะกลายเป็นทางผ่านประตู** ← ข้อนี้ผมสงสัยที่สุด
4. มีเส้นทางไหนที่ผ่านประตูแล้ว **เรนเดอร์ข้อมูลจากเซิร์ฟเวอร์** (ไม่ใช่จากแคชไคลเอนต์) ไหม

🎯 **จึงไม่มีใครดักคำขอ navigate เลย → วิ่งชนเซิร์ฟเวอร์ → `proxy.ts` ทำงาน → เด้ง `/login`**
· ตอนใช้งานจริง (production) SW จะลงทะเบียน แล้ว navigate ใช้ `networkFirst` → ออฟไลน์ได้ shell จากแคช → **`proxy.ts` ไม่ทำงานเลย**

## 🔴 ผลที่ต้องจดไว้ให้ทีมรู้ — **`E6-AC4` ข้อ (ข) ทดสอบใน dev ไม่ได้เลยตามโครงสร้าง**
ใครพยายามยิงข้อนี้บน dev server **จะได้ผลลบเสมอ และผลนั้นไม่มีความหมาย**
· ต้อง `next build && next start` เท่านั้น — **ซึ่งเป็นสิ่งที่คอมเมนต์ในไฟล์บอกไว้อยู่แล้ว แต่ไม่มีใครอ่านตอนออกแบบเกณฑ์**
· ✅ **เกณฑ์ของ `AC4` ข้อ (ข) ต้องระบุว่า *ต้องวัดบน production build* ไม่งั้นเกณฑ์เองก็ผลิตผลลบปลอม**

## ⚠️ และบน production build ก็ยังยิงไม่ได้ในเบราว์เซอร์ของเอเจนต์
สร้าง production build จริงแล้วเปิดที่ `localhost:3301`:

· **ห้ามอ่านผลนี้ว่า "SW พังบน production"** — หลักฐานไม่รองรับข้อสรุปนั้น
· ✅ **ต้องให้ผู้ใช้เปิดในเบราว์เซอร์ของตัวเอง** แล้วเราหยุดเซิร์ฟเวอร์ให้ = การตัดเน็ตที่ซื่อที่สุดเท่าที่ทำได้

# 8. ✅ ผลรีวิวเชิงโจมตีของ P4 — **รับทั้งสองข้อแก้ · เงื่อนไขของเขาเป็นเงื่อนไขบังคับ**

## ① ข้อสงสัยของ P1 เรื่อง `429` — **ผิด · และของจริงกว้างกว่า**
```js
auth-js/dist/main/lib/fetch.js:32
NETWORK_ERROR_CODES = [500,501,502,503,504, 520…530]      // 429 ❌ ไม่อยู่ → ประตูปิด
if (!looksLikeFetchResponse(error)) throw new AuthRetryableFetchError(msg, 0)
                                     // ↑ อะไรก็ตามที่ทำให้ fetch โยน (DNS·TLS·abort·CORS) = retryable
```
🔴 **จุดที่อันตรายกว่าคือ 5xx — เพราะ 5xx แปลว่า Supabase *ตอบแล้ว*** = เครือข่ายดี ฝั่งเซิร์ฟเวอร์มีปัญหา
**ไม่ใช่ "ออฟไลน์" ตามเจตนาข้อเสนอเลย และเป็นแถบที่กระตุ้นได้**

**✅ แก้ตามที่ P4 เสนอ: ผ่อนเฉพาะ `error.status === 0` เท่านั้น**
· `status 0` = `fetch` โยนจริง = เครือข่ายไปไม่ถึง · **ผู้ใช้ปิด Wi-Fi ได้ `0` → เคสที่ตั้งใจแก้ไม่เสียเลย**
· ตัด `500–504` + `520–530` ออกทั้งแถบ
· ⚠️ **ข้อจำกัดที่ P4 เขียนเอง: ยังไม่กันผู้โจมตีที่ทำให้ `fetch` โยนได้** (Wi-Fi สาธารณะ · DNS · proxy) — **กันไม่ได้ตามนิยาม**
  แต่ลดพื้นที่จาก *"เครือข่ายล้ม **หรือ** Supabase 5xx"* เหลือ *"เครือข่ายล้ม"* อย่างเดียว

## ② คุกกี้ที่ถูกเพิกถอน — **ผ่านประตูแน่นอน · และคำตอบนี้ยอมรับได้**
เงื่อนไข *"มีคุกกี้"* ตรวจ **รูป** ไม่ใช่ **ความถูกต้อง**
· ✅ **แต่ได้แค่ shell เปล่า** — แคชอยู่ใน IndexedDB ของเบราว์เซอร์เหยื่อ · เครื่องผู้โจมตีไม่มีข้อมูลนั้น
· → เสียหายจริงเฉพาะบนเครื่องที่แชร์กัน **ซึ่งผู้โจมตีมีเครื่องอยู่แล้ว = ไม่ได้อะไรเพิ่มจากประตูนี้**

## ④ ไม่มีเส้นทางที่เรนเดอร์ข้อมูลจากเซิร์ฟเวอร์ — **P4 วัดแล้ว: ไม่มีจริง**
```
grep 'engine/db|engine/trip' app/ --include=page.tsx --include=layout.tsx   → ว่าง
ผู้ใช้ DAL ทั้งหมดอยู่ใต้ app/api/** ซึ่งข้อเสนอคงไว้ที่ 401
```

## 🟡 ของที่หายไป — เล็กแต่ระบุได้ชัด
```
ออนไลน์   📋 เกาหลี ต.ค. 2026     ·  11 – 21 ต.ค. 2026 · หน้านี้ดูอย่างเดียว…
ออฟไลน์   📋 ทริปนี้              ·  หน้านี้ดูอย่างเดียว…            ← ชื่อทริป + ช่วงวันที่ หายไป
```
· **เมทาดาทาของทริป (ชื่อ · ช่วงวันที่) ไม่ได้ถูกแคช** → ตกไปที่ค่าสำรอง `"ทริปนี้"`
· ⚠️ **ไม่ใช่แค่ความสวยงาม** — คนที่มีหลายทริปจะแยกไม่ออกว่ากำลังดูใบไหนตอนออฟไลน์
· 📌 ของอื่นทั้งหมดแคชแล้ว **ขาดใบเดียวคือ trip เอง** — น่าจะเป็นการหลุดสำรวจ ไม่ใช่การตัดสินใจ

## 🔴 ผลต่อข้อเสนอหัวข้อ 4 — **ลดความสำคัญ ไม่ใช่ถอน**
เดิมข้อเสนอนี้เกิดจากอาการ *"ออฟไลน์แล้วเด้ง `/login`"* — **ซึ่งวันนี้พิสูจน์แล้วว่าไม่เกิดในสภาพจริง**
```
dev (ไม่มี SW)              เด้ง /login        ← สภาพที่ไม่มีอยู่จริงตอนใช้งาน
production (มี SW) ออฟไลน์   ผ่านสบาย ๆ         ← สภาพจริง
```
· ✅ **เคสที่เหลืออยู่จริง: "ต่อเว็บได้ แต่ต่อ Supabase ไม่ได้"** (สัญญาณอ่อน · captive portal · Supabase ล่ม)
  — SW จะได้ HTML สดจากเซิร์ฟเวอร์ → `proxy.ts` **ทำงาน** → เด้ง `/login` ทั้งที่แคชมีของ
· 🔴 **จึงยังควรทำ แต่ *ไม่ด่วน* และ *ไม่ใช่ของที่กันผู้ใช้ตกยากตอนอยู่เกาหลี* อีกต่อไป**
