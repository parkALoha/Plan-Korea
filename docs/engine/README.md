### ของที่ต้องใช้ซ้ำ ไม่ใช่เขียนใหม่

- `lib/travelProvider.ts` — ฟังก์ชันเดียว ห่อ Routes API ครบ → ยกเป็น provider registry ต่อประเทศได้ทันที
- `lib/writeGuard.ts` — choke point ของการเขียน **ตาราง** (10/10 hooks) → แปลงเป็น Server Action ได้โดยไม่ไล่แก้ 60 จุด
  🔴 **แต่ไม่ครอบ Storage เลยสักจุด (0/9) ดู D15** — ผมเคยเขียนว่า "ทุกการเขียน" ซึ่งผิด
- `lib/mapLinks.ts` — มีแนวคิด "เกาหลีใช้ Naver/Kakao · ฮานอยใช้ Google" อยู่แล้ว แค่เขียนเป็น predicate ตายตัว
- `schedule` · `stopOrdering` · `optimizeRoute` · `citySegments` · `hotelLegs` · `openingHours` · `departureAdvice`
  — pure function มีเทสต์คุมครบ **ย้ายได้ทั้งก้อน** = domain core ที่แพลตฟอร์มใช้ต่อได้เลย
- `hooks/useTripDnd.ts` + `@dnd-kit` — โจทย์ "Drag-and-Drop Itinerary UX" **มีของที่ผ่านสนามจริงแล้ว**

### ข้อจำกัดที่เป็นเหตุผลของ provider registry

Google **ไม่คืนเส้นทาง DRIVE/WALK ในเกาหลีใต้** (กฎหมายห้ามส่งออกข้อมูลแผนที่ละเอียด) คืนได้แค่ TRANSIT
— ยืนยันด้วยการทดสอบจริงแล้ว (`PLAN.md §2`) · **นี่ไม่ใช่บั๊ก แต่เป็นหลักฐานว่าความสามารถของผู้ให้บริการ
ต่างกันรายประเทศจริง** จึงต้องเป็น registry ไม่ใช่ `if (country === "kr")` กระจายทั่วโค้ด

⚠️ `PLAN.md §2` ตัดสินไว้แล้วว่า **ไม่เพิ่ม ODsay/Kakao/Naver API** (สมัครยาก ต้องยืนยันตัวตนแบบเกาหลี)
— ออกแบบ registry ให้เสียบเพิ่มได้ทีหลัง แต่**อย่าเสนอให้ทำตอนนี้โดยไม่คุยกับผู้ใช้ก่อน**

ข้อค้นพบที่หนักที่สุดของวันแรก **6 ข้อเป็นรูปแบบเดียวกันหมด — ความล้มเหลวที่หน้าตาเหมือนความสำเร็จ:**

**กฎ 4 ข้อที่ถอดออกมาได้ และใช้กับทุกเฟส:**
1. 🔴 **ทุกเคสที่พิสูจน์ว่า "ทำไม่ได้" ต้องมีเคสคู่ที่พิสูจน์ว่า "เส้นทางที่ถูกต้องยังทำได้"**
   ไม่งั้นเรากำลังวัดว่าระบบพัง แล้วอ่านผลว่าระบบปลอดภัย
2. 🔴 **ต้องเห็นมันแดงก่อน** — เทสต์/เมทริกซ์ที่ไม่เคยแดง ไม่ได้พิสูจน์ว่าจับได้
3. 🔴 **ถ้าความล้มเหลวไม่ส่งเสียง ต้องไปตั้งใจดู** — อย่ารอ error จากของที่ออกแบบมาให้เงียบ
4. 🔴 **การลดความเสี่ยงหนึ่ง มักได้อีกแบบมาแทน — ถามทุกครั้งว่าแบบใหม่ตรวจง่ายกว่าหรือยากกว่าแบบเดิม**
   (E7-AC4 เป็นตัวอย่างสด: เอาความเสี่ยง "ไฟล์หายระหว่างย้าย" ออก ได้ "พังเงียบ" มาแทน ซึ่งตรวจยากกว่า)
5. 🔴 **ห้ามให้สิทธิ์แบบเหมารวม (`grant ... on all ...`) ในเอกสารนี้เลยแม้แต่ที่เดียว** (P4 เสนอ)
   **มันคือรูปแบบเดียวที่ทำให้ 2 ไฟล์ซึ่งอ่านแยกกันแล้วถูกทั้งคู่ ให้ผลผิดตามลำดับการรัน**
   ตัวอย่างจริง (P-09): `grant execute on all functions in schema app to authenticated` เขียนตอน `app` มีแต่ helper
   · พอ `app` มีฟังก์ชัน SECURITY DEFINER ที่เขียนข้อมูล → **เปิดให้เรียกตรงข้ามด่านสมาชิกทั้งด่าน**
   และ**ลบล้าง `revoke` ที่อีกไฟล์เขียนไว้ ถ้ารันทีหลัง** · ต้อง grant ทีละตัวเสมอ
   + `alter default privileges ... revoke execute on functions from public` เพราะ **Postgres ให้ EXECUTE กับ `public` เป็นค่าเริ่มต้น**
   → **ฟังก์ชันใหม่ต้องถูก grant โดยตั้งใจ ไม่ใช่ได้มาเอง**
   ⚠️ **นี่เป็นชนิดที่การรีวิวทีละไฟล์จับไม่ได้เลย** — ต้องกันด้วยกฎ ไม่ใช่ด้วยสายตา

   🔴 **กับดักของกฎข้อนี้เอง (P5 ชี้): ห้าม `grep "all"` แล้วลบตามกฎแบบกลไก**
   | เขียนแบบไหน | แปลว่า | ตัดสิน |
   |---|---|---|
   | `revoke all on function <ชื่อ+signature>` | ทุก**สิทธิ์** ของฟังก์ชัน**ตัวที่ระบุ** | ✅ ใช้ได้ ไม่ขัดกฎ |
   | `grant ... on all functions in schema` | ทุก**ฟังก์ชัน**แบบเหมารวม | 🔴 ห้าม |

   **ลบผิดตัว = ลบ `revoke` ทิ้ง = เปิดช่องที่กฎข้อนี้เขียนมาเพื่อปิด**
   → **กฎที่ทำตามแบบกลไกแล้วก่อความเสียหายที่มันเขียนมาเพื่อกัน คือกฎที่ต้องเขียนวิธีอ่านกำกับไว้ด้วย**

   🎯 **และกฎข้อนี้ให้ผลที่ใหญ่กว่าการปิดช่อง (P5 มองจากฝั่งคนโดน):**
   > *"ผมเขียนไฟล์นี้มา 3 รอบโดยไม่เคยรู้ว่าตารางตัวเองไม่มีสิทธิ์ —* **ไม่ใช่ว่าผมตัดสินใจแล้วตัดสินผิด**
   > *แต่คำถามไม่เคยมาถึงผมเลย"*

   **`grant ... on all` ไม่ได้ทำให้เจ้าของตารางตัดสินใจผิด — มันปิดคำถามก่อนที่เจ้าของจะรู้ว่ามีคำถาม**
   → **grant ทีละตัวคืนคำถามกลับไปให้เจ้าของตาราง** · ตารางที่ยังไม่มี grant **คือสิ่งที่ควรเห็น ไม่ใช่สิ่งที่ควรกลบ** (P4)
   ⚠️ และคู่กัน: **policy กับ grant ต้องมาคู่เสมอ** (policy = "แถวไหน" · grant = "ทำอะไรได้")
   คนที่อ่านเฉพาะบล็อก policy จะเห็นว่าครบแล้วทั้งที่ยังใช้ไม่ได้ — **"ด่านหายเพราะสิ่งที่ไม่มีอยู่" อีกหน้าหนึ่ง**

### 🔴 DoD-7 — เกณฑ์ปิดเฟสที่ปิดช่องนี้โดยตรง (P8 นับมา · ผมรับ)
P8 ไล่นับ "ของที่พังโดยไม่มีสัญญาณ" ในโปรเจกต์นี้ได้ **10 ตัว** และตัวเลขบอก 3 อย่าง:
1. 🔴 **7 ใน 10 จะถูกรู้ตอนใช้จริงหน้างาน หรือไม่ถูกรู้เลย — และไม่มีตัวไหนที่ CI/lint/เทสต์จับได้ตามธรรมชาติ**
   → **DoD ที่เรามีอยู่ (lint · test · build) ไม่แตะปัญหาประเภทนี้เลยแม้แต่ตัวเดียว**
2. **3 ใน 10 เป็นการตัดสินใจที่ตั้งใจและถูกในบริบทเดิม** ไม่ใช่บั๊ก — เป็นหนี้ที่เกิดตอนบริบทเปลี่ยน
   (`localCache` · `proxy.ts` fail-open · Storage public) · **`localCache` ทำถูกแล้วตรงที่เขียนเหตุผลกำกับ ผิดตรงที่ไม่มีใครกลับมาทบทวน**
3. **แพลตฟอร์มหลายผู้ใช้ทำให้ทุกตัวแย่ลง** เพราะคนที่เจอผลจะไม่ใช่คนที่รู้ว่าระบบเคยตัดสินใจอะไรไว้

> **DoD-7: ก่อนปิดทุกเฟส ต้องตอบ — "ถ้าข้อนี้พังตอนใช้จริง เราจะรู้ได้ยังไง"**
> **ตอบว่า "ไม่รู้" = ต้องเพิ่มสัญญาณก่อนปิดเฟส**

⚠️ **ต้องเป็น DoD ไม่ใช่ความเสี่ยง** เพราะต้องถาม**ทุกเฟส** ไม่ใช่ครั้งเดียวตอนวางแผน
· คู่กับคำถาม 2 ข้อของ **D23** ที่ถามก่อนล็อกขอบเขต — **D23 ถามตอนเริ่ม · DoD-7 ถามตอนปิด**

📌 **เลข DoD ใช้ `DoD-1`…`DoD-7` ห้ามเขียน `D1`…`D7` เฉยๆ** — ชนกับเลขข้อตัดสินในไฟล์นี้
(ผมเองเคยเขียน "DoD เพิ่ม build + D4" ซึ่งกำกวม เพราะ `D4` ในไฟล์นี้คือบั๊ก service worker)

| ชิ้นส่วน | สิ่งที่เป็นจริง |
|---|---|

### 🟢 D51 — `leg` **ยังคงเป็นค่าที่คำนวณเอา** · `trip_hotels` ผูกกับ**ช่วงวันที่จริง** ไม่ใช่ `leg_id` (P1 ตัดสิน · 24 ส.ค. 2026)


**เหตุผล 4 ข้อ:**
1. **การจองโรงแรมในโลกจริง*คือ*ช่วงวันที่** — โมเดลตรงกับของที่มันแทน · `leg` เป็นเรื่องของ*แผน* ไม่ใช่เรื่องของ*ใบจอง*
2. **`trip_days` ยังเป็นแหล่งความจริงเดียวของ "นอนเมืองไหน"** — ถ้าทำ `trip_legs` เป็นตาราง เราจะมีแหล่งที่สองที่ไม่มีอะไรบังคับให้ตรงกับ `trip_days` · **นี่คือ `P-15` ในรูปใหม่เป๊ะ** และทีมนี้เพิ่งจ่ายราคาให้มันไปแล้วรอบหนึ่ง
3. 🔴 **ของเดิมทำให้ใบจองที่จ่ายเงินไปแล้ว ขยับตามการแก้แผนอย่างเงียบ ๆ** — `leg.id` คือ id ของวันแรก · เปลี่ยนเมืองที่นอนวันที่ 5 แล้วขอบเขต leg เลื่อน → `leg_id` เปลี่ยน → **แถวโรงแรมกำพร้าหรือย้ายไปคุมคืนที่ไม่ได้จอง โดยไม่มีอะไรฟ้อง**

### 🟢 D52 — `trips.active_plan_id` **ไม่มี** · แผนที่ใช้อยู่ทำเครื่องหมายที่ `trip_plans` (P1 ตัดสิน · 24 ส.ค. 2026)

**ปิดข้อ ⏳3 ของ [`column-map.md`](column-map.md)** — *"`trips.active_plan_id` สร้าง FK วนกับ `trip_plans.trip_id` ต้องเลือกว่าใครถือ FK"*

**ตัดสิน: ไม่มีใครถือ FK วน — ตัดวงจรทิ้งทั้งวง**
```sql
trip_plans.is_active boolean not null default false
create unique index trip_plans_one_active on public.trip_plans (trip_id) where is_active;
```

**เหตุผล:** FK วนบังคับให้ต้องมีตัวใดตัวหนึ่งเป็น nullable หรือ `deferrable` — และ **`deferrable` คือของที่เราเพิ่งปฏิเสธไปใน `P-27` วันนี้เอง** ด้วยเหตุผลว่ามันย้ายความผิดพลาดไปโผล่ตอน commit
· partial unique index บังคับ **"หนึ่งทริปมีแผนที่ใช้อยู่ได้ไม่เกินหนึ่ง"** ได้ตรง ๆ ที่ระดับฐานข้อมูล · และ **ลบแผนทิ้งแล้วไม่มีอะไรค้างชี้ไปหาของที่ไม่มี**

**สลับแผนต้องเป็น statement เดียว ไม่ใช่สอง:**
```sql
update public.trip_plans set is_active = (id = $new_plan) where trip_id = $trip;
```
🔴 **เขียนแยกเป็น 2 คำสั่ง (ปลดของเก่า แล้วตั้งของใหม่) จะชน unique index ได้ถ้าลำดับกลับกัน** — statement เดียวถูกตรวจตอนจบคำสั่ง จึงผ่านเสมอ
⚠️ **"ไม่เกินหนึ่ง" ไม่ใช่ "ต้องมีหนึ่ง"** — ทริปที่ไม่มีแผนไหน active เป็นสภาพที่เกิดได้ · **UI ต้องรับมือ ไม่ใช่สมมติว่ามีเสมอ**
