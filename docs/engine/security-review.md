## 0. สรุปให้ P1 อ่าน 1 นาที

**ยืนยันข้อเท็จจริงของ P1 ครบทุกข้อ** รวมบั๊ก `travel_time_cache` (ยืนยันได้ถึงชั้นไลบรารี — §7.1 ของไฟล์ SQL)
และตัวเลข 53 policy / 14 ตาราง ตรงกับที่นับได้จริง

**สิ่งที่ต้องแย้ง / เพิ่มจากที่ P1 เขียนมา — 6 ข้อ เรียงตามความสำคัญ:**

| # | เรื่อง | ทำไมสำคัญกว่าที่บรีฟไว้ |
|---|---|---|
| **F1** | Storage **แย่กว่า** ที่ B3 บรรยาย | bucket ตั้ง **Public** → เส้น `/object/public/...` **ไม่ผ่าน RLS เลย** policy 4 ตัวจึงไม่ได้กันการอ่านตั้งแต่ต้น · ซ้ำ policy `select` ยอมให้ `POST /object/list/booking-files` **ไล่ชื่อไฟล์ทั้ง bucket** → ได้รายชื่อครบแล้วเปิดอ่านทุกไฟล์ ซึ่งเป็น**รูปตั๋วที่มีชื่อตามพาสปอร์ต** · และ path ไฟล์ไม่มี prefix ทริป → เขียน policy แยก tenant กับข้อมูลที่มีอยู่**ไม่ได้เลย** ต้อง rename |
| **F2** | เปิด RLS แล้ว **realtime DELETE จะหายเงียบทุกตาราง** | บั๊ก migration `0009` กลับมาในรูปแบบใหม่ — คราวนี้ต้นเหตุคือ RLS ไม่ใช่ client filter จะไล่หาผิดที่ · ต้อง `replica identity full` ทุกตารางใน publication ไม่ใช่แค่ `trip_stops` (ยังไม่ยืนยันด้วยการรัน → เคส **T-14**) |
| **F3** | `proxy.ts` matcher **ยกเว้นทุก path ที่ลงท้ายด้วยนามสกุลไฟล์** | `proxy.ts:71` ตัด `.svg .png .jpg .jpeg .webp .ico .woff woff2` ออกจากด่าน → เส้นทางใดก็ตามที่ลงท้ายด้วยนามสกุลพวกนี้**ไม่เข้าด่าน PIN เลย** · วันนี้ไม่มีรูรั่วเพราะทุก route ไม่มีนามสกุล แต่แพลตฟอร์มจะมี `[param]` และ export ไฟล์ → รูเปิดโดยไม่มีใครแก้อะไรผิด |
| **F4** | `is_locked` (ล็อกวัน) **ไม่ใช่มาตรการอะไรเลย** | บังคับอยู่ใน client ล้วนๆ ยิง REST ตรงข้ามได้ · พอมี viewer/editor คนอื่น "ล็อกแล้ว" ต้องล็อกจริง → ต้องเป็น trigger (RLS ทำไม่ได้เพราะเทียบ OLD/NEW ไม่ได้) |
| **F5** | `file_url` / `photo_url` **ไม่ผ่าน `safeHttpUrl`** ทั้งที่ `link` ผ่าน | `lib/url.ts` มีอยู่แล้วและถูกใช้ที่ `bookings.link` ทุกจุด แต่ `BookingEditModal.tsx:346` และ `app/today/page.tsx:906` ใส่ `file_url` ลง `href` ตรงๆ · เป็นการใช้มาตรการที่มีอยู่แล้วไม่ทั่วถึง ไม่ใช่มาตรการที่ขาด |
| **F6** | ช่องทำลายข้อมูลที่**ถูกที่สุด**คือ `trip_plans` DELETE | `trip_stops.plan_id references trip_plans(id) on delete cascade` (`0006:4`) + DELETE เป็น `using (true)` → ลบแผน 1 คำสั่ง = จุดแวะทั้งแผนหายทั้งชุด ไม่ต้องรู้อะไรนอกจาก plan id |

**ไม่พบ** ในสิ่งที่หลายคนคาดว่าจะเจอ (ตรวจแล้วว่าไม่มีจริง ไม่ใช่ยังไม่ได้ตรวจ):

`bookings_secret` (แยกคอลัมน์อ่อนไหว §5.9.1) · trigger 4 ตัว (§9) · `replica identity full` (§10)
· และ 3 schema แทน 1 (§1)

## 1. Threat model

### 1.1 ใครคือผู้โจมตี

| ผู้โจมตี | ได้อะไรมาแล้ว | ความสามารถวันนี้ |
|---|---|---|
| **A. คนที่เจอ URL** | URL เว็บ | โดนด่าน PIN 4 หลัก + rate limit 10/นาที (`app/api/unlock/route.ts:8`) — ไล่ครบ 10,000 ค่าใช้ ~16 ชม. |
| **B. คนที่ดึง anon key ออกจากบันเดิล** | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 🔴 **ทำได้ทุกอย่างกับทุกตารางทุกแถว + ทุกไฟล์ใน bucket** ข้ามด่าน PIN ทั้งหมด (P1 พิสูจน์ด้วย curl 11 ส.ค. 2026) |
| **C. สมาชิกทริปเอง (ระยะ 2)** | บัญชีจริง + JWT | ผู้โจมตีหลักของแพลตฟอร์ม — cross-tenant, privilege escalation, self-join |
| **D. คนถือ URL ไฟล์ที่รั่ว** | public URL ของไฟล์ตั๋ว | อ่านไฟล์ได้ตลอดกาล ไม่มีวันหมดอายุ ไม่มี log |
| **E. prompt injection ผ่าน Copilot (ระยะ 2)** | เนื้อหาที่ผู้ใช้อื่นใส่ | โน้ต/ชื่อสถานที่กลายเป็นคำสั่งให้ agent เรียก tool เขียน DB — **พื้นที่โจมตีใหม่ทั้งหมด** ส่งต่อ P5 |

**B คือแกนของทุกอย่างวันนี้** และเป็นเหตุผลที่ RLS ต้องมาก่อน (E1 มาก่อน E2 ตาม `README.md`)
ตราบใดที่ policy เป็น `using (true)` มาตรการอื่นทั้งหมด (PIN, rate limit, HTTPS, `safeHttpUrl`)
กันได้แค่ทางเข้าประตูหน้า ขณะที่ประตูหลังเปิดอยู่และเขียนบอกไว้ในโค้ดเองว่าเปิด

### 1.2 จัดลำดับตามความเสียหายจริง

เรียงด้วย **ความเสียหายถ้าเกิด × ความง่ายที่จะเกิด** ไม่ใช่เรียงตามความน่าสนใจทางเทคนิค

| ลำดับ | เกิดอะไร | ทางเข้า | ความเสียหายจริง | สถานะระยะ 2 |
|---|---|---|---|---|
| **1** | ไฟล์ตั๋วรั่วทั้ง bucket | B, D — `object/list` แล้วเปิด public URL | **ชื่อตามพาสปอร์ต + เลขที่จอง** พอโทรเข้า call center อ้างเป็นเจ้าของการจอง → เปลี่ยน/ยกเลิกตั๋วคนอื่นได้ · ย้อนกลับไม่ได้ | §6 + `rls-policies.sql` §8 |
| **2** | อ่าน `bookings` ข้าม tenant | B, C | เลขที่จอง · เลขไฟลต์ · วันเวลาเดินทาง | policy + `bookings_secret` |

### 2.2 🔴 3 กับดักที่ทำให้เทสต์ RLS ขึ้นเขียวทั้งที่ policy ไม่ได้กันอะไร

อ่านข้อนี้ก่อนเขียนเทสต์บรรทัดแรก — ผิดข้อใดข้อหนึ่ง เทสต์ทั้งไฟล์ไร้ค่าและจะให้ความมั่นใจผิดๆ

**กับดัก 1 — ใช้ service-role key ใน client ทดสอบ**
`service_role` มี `BYPASSRLS` → ข้าม policy ทุกตัว → **ทุกเคสผ่านหมด** รวมเคสที่ต้องการให้ fail
ป้องกัน: assert ในไฟล์เทสต์เองว่า key ที่ใช้ไม่ใช่ service role ก่อนรันเคสใดๆ
```ts
// บรรทัดแรกของ describe block — กันตัวเองพลาด ไม่ใช่กันคนอื่น
it("ต้องไม่ใช้ service-role key", () => {
  for (const k of [ANON_KEY, ...])
    expect(JSON.parse(atob(k.split(".")[1])).role).toBe("anon");
});
```

**กับดัก 2 — assert ด้วย `error` สำหรับ SELECT/UPDATE/DELETE (ผิดทั้งหมด)**
RLS **ไม่ throw ตอนอ่าน** มันกรองแถวออกเงียบๆ → PostgREST คืน **HTTP 200 + `data: []` และ `error: null`**
เช่นเดียวกับ UPDATE/DELETE ที่แถวไม่ผ่าน `using` → 200 + ไม่มี error + ไม่มีอะไรเปลี่ยน

| verb | ถูกปฏิเสธแล้วได้อะไรกลับมา | assert ที่ถูกต้อง |
|---|---|---|
| SELECT | 200 · `data: []` · `error: null` | `expect(data).toHaveLength(0)` |
| INSERT | **403 · `error.code === "42501"`** | `expect(error?.code).toBe("42501")` |
| UPDATE | 200 · `data: []` · `error: null` | อ่านซ้ำ**ในฐานะเจ้าของ** แล้วยืนยันค่าเดิมไม่เปลี่ยน |
| DELETE | 200 · `data: []` · `error: null` | อ่านซ้ำ**ในฐานะเจ้าของ** แล้วยืนยันแถวยังอยู่ |
| upsert ที่ชน | **403 · `42501`** (ON CONFLICT DO UPDATE ตรวจ USING ของ UPDATE policy) | `expect(error?.code).toBe("42501")` |

→ **UPDATE/DELETE ต้องยืนยันด้วยการอ่านซ้ำเสมอ** เขียน helper `expectUnchanged(asOwner, table, id, field)`
ถ้าเทสต์ UPDATE/DELETE ทุกเคสเขียนแค่ `expect(error).toBeTruthy()` มันจะ**ล้มเหลวเสมอแม้ policy ถูก**
แล้วคนจะไป "แก้" ให้ผ่านด้วยการเช็คผิดทาง — ซึ่งจะกลายเป็นเทสต์ที่ผ่านตลอดไม่ว่า policy จะเป็นอะไร

**กับดัก 3 — เทสต์แต่ขาอ่าน ไม่เทสต์ `with check`**
Postgres ใช้ `using` แทน `with check` ให้เองเมื่อ UPDATE policy ไม่เขียน `with check`
→ เคสที่ทดสอบแค่ "A อ่านของ B ไม่ได้" จะผ่านทั้งที่ยังเปิดช่อง **"A ย้ายแถวของตัวเองเข้าทริปของ B"**
ซึ่งร้ายกว่า เพราะเป็นการเขียน ไม่ใช่อ่าน → เคส **T-07 / T-08** มีไว้เพื่อข้อนี้เฉพาะ

### 2.6 เกณฑ์ผ่าน E2 ตาม D13 — เมทริกซ์ 104 เคส · รับ แต่ต้องแก้ 1 จุด

รับเกณฑ์ **13 ตาราง × 4 verb × 2 persona = 104 เคส ต้องถูกปฏิเสธ 104/104**
และรับข้อที่สำคัญกว่าตัวเลข: **ต้องเห็นเมทริกซ์แดงก่อน** ถึงจะพิสูจน์ว่าเทสต์จับได้จริง
ไม่ใช่เขียวเพราะเขียนผิด — นี่คือ **"เทสต์ตัวเทสต์"** ซึ่งเป็นสิ่งที่ควรมีในทุกงานความปลอดภัย
ที่วัดผลด้วยการ "ไม่มีอะไรเกิดขึ้น" เพราะการไม่มีอะไรเกิดขึ้นเป็นผลลัพธ์เดียวกันทั้งตอนกันได้
และตอนเทสต์ไม่ทำงาน

🔴 **แต่ *"ต้องเห็นเมทริกซ์แดงบนสคีมาวันนี้ก่อน"* ทำได้แค่ครึ่งเดียว — ด้วยเหตุผลของ D13 เอง**

D13 ย้ายเกณฑ์จาก E1 ไป E2 เพราะวันนี้ยังไม่มี `trip_id` ในตารางไหนเลย (B4)
**เหตุผลเดียวกันทำให้ persona "สมาชิกทริปอื่น" ทดสอบบนสคีมาวันนี้ไม่ได้** — ไม่มีคอลัมน์ให้แยกทริป
จึงไม่มีสิ่งที่เรียกว่า "ทริปของ B" ให้ A ไปแตะ · เมทริกซ์แดงจึงแยกเป็น 2 ชุดที่เก็บ baseline
ต่างเวลากัน:

| persona | baseline แดงเก็บได้เมื่อไหร่ | เคส | หมายเหตุ |
|---|---|---|---|
| **ANON** (ไม่ล็อกอิน) | 🟢 **วันนี้เลย** ไม่ต้องรออะไร | 13 × 4 = **52** | วันนี้ต้องได้ **0/52 ถูกปฏิเสธ** — ทุกช่องผ่านหมดเพราะ `using (true)` · นี่คือ B2+B3 ที่วัดเป็นตัวเลขได้ |
| **สมาชิกทริปอื่น** | 🔴 **หลังมี `trip_id` แล้วแต่ก่อน policy ลง** (กลาง E2) | 13 × 4 = **52** | ก่อนหน้านั้นไม่มีอะไรให้วัด · ถ้ารอจนหลัง policy ลงจะเก็บ baseline แดงไม่ได้อีกเลย |

→ **ข้อเสนอ: เพิ่มขั้นบังคับใน E2** ว่าเมื่อ `trip_id` ครบทุกตารางแล้ว **ต้องรันเมทริกซ์เก็บ
baseline แดง 0/52 ให้ได้ก่อนลง policy** · มีหน้าต่างเดียวที่ทำได้ ถ้าเลยไปแล้วต้องรื้อ policy
ออกเพื่อย้อนวัด ซึ่งไม่มีใครกล้าทำและจะกลายเป็นข้ามไปเลย
· ชุด ANON 52 เคสเก็บได้ตั้งแต่วันนี้ **แต่ต้องรันกับ Supabase local ที่ replicate สคีมาวันนี้
ไม่ใช่ยิง DB ทริปจริง** — ทำได้ทันทีที่โปรเจกต์ staging ของ P6 ขึ้น (D14) ไม่ต้องรอ E1

**หมายเหตุเรื่องการนับ 4 verb:** บางตารางไม่มี policy ของบาง verb โดยตั้งใจ
(`trip_hidden_places` ไม่มี UPDATE เพราะโค้ดไม่ใช้ — `schema/rls-policies.sql` §5.7) · **ไม่ทำให้ 104 เพี้ยน**
เพราะ "ไม่มี policy" ให้ผลเป็น "ถูกปฏิเสธ" ซึ่งคือสิ่งที่เมทริกซ์คาดหวังอยู่แล้ว
· ตรงข้ามกัน: ถ้าช่องไหน**ผ่าน**ทั้งที่ไม่ควรมี verb นั้น = มี policy เกินมาจากที่ออกแบบ ซึ่งเมทริกซ์จับได้ด้วย

### 2.7 🔴 D18 เพิ่มชุดที่ 3 เข้าเมทริกซ์ — เคสที่ **owner ต้องถูกปฏิเสธ**

เมทริกซ์ 104 เคสเดิมพิสูจน์ว่า *"คนที่ไม่ควรทำได้ ทำไม่ได้"* · D18 (ถอด DELETE policy ทั้ง 11 ตาราง)
สร้างเงื่อนไขชนิดใหม่ที่เมทริกซ์เดิม**มองไม่เห็นเลย**: `DELETE` ต้องถูกปฏิเสธ **สำหรับทุกคน
รวม owner ของทริปนั้นเอง** ซึ่งเป็นเคสที่ persona ทั้งสองของ §2.6 ไม่ครอบ เพราะทั้งคู่เป็น "คนนอก"

| เคส | ผู้กระทำ | ทำอะไร | ต้องได้ |

| **T-22** | `U_A` (**owner** ของ `TRIP_1`) | `DELETE` แถวของตัวเองใน 11 ตารางที่ถอด policy ออก | ถูกปฏิเสธ **11/11** · ถ้าผ่านแม้ตารางเดียว = policy หรือ GRANT หลุดกลับมา |

**T-23 คือคู่ที่ขาดไม่ได้ของ T-22** — เทสต์ที่ยืนยันแค่ "ทำไม่ได้" อย่างเดียว จะยังเขียวอยู่

| **T-35** | `U_A` | เลิก archive แล้วเขียนได้อีก | T-12 (archived ห้ามเขียน) |

#### 🔴 ข้อบังคับที่สำคัญกว่าตัวเคส: baseline แดง = **inconclusive ไม่ใช่ pass**

การเพิ่มเคสบวกเข้าไปเฉยๆ **ยังไม่พอ** เพราะถ้ามันแดงพร้อมกับที่เคสปฏิเสธเขียว
รายงานจะออกมาเป็น "8 แดง 104 เขียว" ซึ่งคนอ่านจะซ่อม 8 ตัวแล้วเชื่อ 104 ตัวที่เหลือ
**ทั้งที่ 104 ตัวนั้นไม่ได้พิสูจน์อะไรเลยตราบใดที่ baseline ยังแดง**

→ **T-28 ต้องเป็น precondition ของทั้งชุด ไม่ใช่เทสต์พี่น้อง**
```ts
// รันก่อนทุกเคสปฏิเสธ · ล้มแล้วต้อง "หยุดทั้งชุด" ไม่ใช่ "แดง 1 ตัว"
beforeAll(async () => {
  const ok = await ownerCanDoEverything(U_A, TRIP_1);
  if (!ok) throw new Error(
    "baseline แดง — ผลของเคสปฏิเสธทั้งหมดถือเป็น inconclusive ห้ามอ่านว่าผ่าน"
  );
});
```
`beforeAll` ที่โยนจะทำให้ vitest ข้ามทั้ง suite และรายงานว่า **suite ล้ม** ไม่ใช่รายงานผลรายเคส
— นี่คือความต่างระหว่าง "ไม่รู้" กับ "ปลอดภัย" ที่กฎข้อ 1 พยายามบังคับให้เห็น

#### 🔴 กฎข้อ 1 ชนกับกฎข้อ 2 — วิธีแยก 2 สถานะที่หน้าตาเหมือนกัน

กฎข้อ 2 บอกว่า *"ต้องเห็นมันแดงก่อน"* · กฎข้อ 1 บอกว่า *"ต้องมีเคสคู่ที่เขียว"*
**ในรอบเก็บ baseline แดงของ §2.6 สองข้อนี้ขัดกันเอง** เพราะ "แดง" กลายเป็นผลที่ต้องการ
→ แล้ว "แดงเพราะ policy ยังไม่ลง" (ที่ต้องการ) กับ "แดงเพราะ fixture ยังไม่พร้อม" (ที่ต้องหยุด)
**หน้าตาเหมือนกัน** — รูปแบบเดิมโผล่ในกฎที่เขียนมาเพื่อกันรูปแบบนั้นเอง

**วิธีแยก: T-28 ต้องเขียวทุกรอบ ไม่มีข้อยกเว้น — รวมรอบที่เราตั้งใจให้เมทริกซ์แดง**
เหตุผลที่ใช้ได้: T-28 ทดสอบว่า **เจ้าของทริปทำงานของตัวเองได้** ซึ่งเป็นจริงทั้งก่อนและหลังลง policy
· ก่อนลง policy: ผ่านเพราะ `using (true)` ปล่อยทุกอย่าง · หลังลง: ผ่านเพราะ policy เขียนถูก
**มันไม่ใช่เคสที่ policy ทำให้เปลี่ยนผล จึงเป็นเครื่องวัด fixture ได้อย่างเดียวล้วนๆ**

| T-28 | เคสปฏิเสธ | อ่านว่าอะไร | ทำอะไร |
|---|---|---|---|
| 🟢 | 🔴 ทั้งหมด | **baseline แดงที่ต้องการ** — fixture พร้อม policy ยังไม่ลง | ✅ บันทึกเป็น baseline แล้วลง policy |
| 🟢 | 🟢 ทั้งหมด | policy ทำงานแล้ว | ✅ ผ่านเกณฑ์ E2 |
| 🔴 | 🔴 | **fixture ยังไม่พร้อม** ไม่ใช่ baseline | 🛑 **หยุด ห้ามบันทึก** ซ่อม fixture แล้วรันใหม่ |
| 🔴 | 🟢 | ระบบพังจนทำอะไรไม่ได้เลย | 🛑 หยุด — เป็นภาพ `trip_members` ว่างข้างบนพอดี |

→ **T-28 แดง = หยุด ไม่ใช่บันทึก** ในทุกรอบ · เขียนเป็นเงื่อนไขของสคริปต์เก็บ baseline
ไม่ใช่ข้อความเตือนในเอกสาร เพราะคนที่รันจริงจะเจอสองอย่างนี้ปนกันแน่นอน

**เคส T-01…T-06 ใน §2.3 คือเมทริกซ์นี้เขียนเป็นโค้ด** — `TENANT_TABLES` มี 9 ตารางเนื้อหา
ส่วนที่เหลืออีก 4 ของ 13 คือ `profiles` `trips` `trip_members` `trip_days` ซึ่งมีเคสมือแยก
(T-09/T-10/T-15/T-21) เพราะกฎต่างจากตารางเนื้อหา → **รวมแล้วครบ 13 ตาราง ไม่ตกตัวไหน**

## 3. แผน E2E

### 3.1 ปัญหาวันนี้: `environment: "node"` แปลว่าเทสต์ component ไม่ได้เลย

`vitest.config.ts` ตั้ง `environment: "node"` ตัวเดียวทั้งโปรเจกต์ → ไม่มี `document`/`window`
→ 44 component และ 28 hook **ไม่มีเทสต์ได้แม้แต่ตัวเดียว** ทั้งที่ตรรกะสำคัญอยู่ในนั้นมาก
(`useTripDnd` · `writeGuard` + `reload()` · optimistic update ที่ต้องเด้งกลับเมื่อเขียนไม่ผ่าน)

**อย่าเปลี่ยน `environment` เป็น `jsdom` ทั้งโปรเจกต์** — 13 ไฟล์เทสต์ pure function ที่มีอยู่จะช้าลง
โดยไม่ได้อะไรกลับมา และ jsdom มีพฤติกรรมที่ต่างจาก node ในเรื่อง timer/`Date`/`Intl`
ซึ่ง `schedule` และ `openingHours` พึ่งพาอยู่ → เสี่ยงทำเทสต์ที่ผ่านอยู่แล้วพังโดยไม่มีเหตุ

**แยกเป็น 2 project:**

```ts
// vitest.config.ts — ต้องอัป vitest จาก ^2.1.9 เป็น ^3 ก่อน (v2 ใช้ environmentMatchGlobs
// ซึ่ง deprecated ใน v3) · การอัปเป็นงานของ P6 ในระยะ 2
export default defineConfig({
  plugins: [tsconfigPaths()],
  test: {
    projects: [
      { test: { name: "unit", environment: "node",  include: ["lib/__tests__/**/*.test.ts"] } },
      { test: { name: "dom",  environment: "jsdom", include: ["{components,hooks}/__tests__/**/*.test.tsx"],
                setupFiles: ["./test/setup.dom.ts"] } },
    ],
  },
});
```

ของที่ต้องเพิ่ม: `jsdom` · `@testing-library/react` · `@testing-library/user-event` · `@testing-library/jest-dom`
· mock ของ `supabase-js` (หรือ MSW ดักที่ชั้น HTTP ซึ่งดีกว่าเพราะไม่ผูกกับรูปร่าง API ของไลบรารี)

### 3.2 Playwright — ของที่ jsdom ทำไม่ได้จริงๆ

เพิ่ม `@playwright/test` แยกจาก vitest ไม่ปนกัน (คนละ runner คนละ config คนละคำสั่ง)

## 4. เส้นทางเลิก fail-open ของ `proxy.ts` โดยไม่เสี่ยงเว็บตาย

### 4.1 เหตุผลเดิมถูก — และเป็นกุญแจของทางแก้

`proxy.ts:38-45` เลือกปล่อยผ่านเมื่อไม่มี env และเขียนเหตุผลไว้ชัด: ถ้าบล็อกแล้วลืมตั้ง env บน Vercel
เว็บจะตายทั้งเว็บ ซึ่งอันตรายกว่ามากตอนอยู่เกาหลีแล้วเปิด `/today` ไม่ได้ **การประเมินนี้ถูกต้อง
สำหรับบริบทของมัน** และไม่ควรถูกเรียกว่าความพลาด

แต่สังเกตรูปของ dilemma: การตัดสินใจเกิดขึ้น **ตอนมี request เข้ามาแล้ว** ซึ่งเป็นจังหวะที่เหลือทางเลือกแค่
"เว็บตาย" หรือ "เว็บเปิดโล่ง" — ไม่มีทางที่สาม **เพราะตัดสินใจสายเกินไป ไม่ใช่เพราะตัดสินใจผิด**

### 4.2 ทางแก้: ย้ายการตรวจไปตอน deploy แล้ว dilemma หายไปเอง

**ขั้นที่ 1 — ตรวจตอน build (แกนของข้อเสนอ)**
ทำให้สภาพ "production ที่รันอยู่โดยไม่มี auth env" **เป็นไปไม่ได้** ตั้งแต่ต้น
```ts
// next.config.ts — ต้องพังตอน build ไม่ใช่ตอนมี request
const REQUIRED_IN_PROD = ["TRIP_PIN_SECRET", "SUPABASE_JWT_AUD" /* ฯลฯ ของระยะ 2 */];
if (process.env.VERCEL_ENV === "production") {
  const missing = REQUIRED_IN_PROD.filter((k) => !process.env[k]);
  if (missing.length) throw new Error(`ตั้ง env ไม่ครบ: ${missing.join(", ")}`);
}
```
ผลลัพธ์: **ลืมตั้ง env = deploy ไม่ผ่าน = deploy เดิมที่ทำงานอยู่ยังให้บริการต่อไป**
ซึ่งเป็นสิ่งที่ต้องการจริงๆ ทั้งสองด้าน — ไม่มีเว็บตาย และไม่มีเว็บเปิดโล่ง
(ของ Vercel: deploy ที่ build fail ไม่ถูก promote ไป production เลย)

**ขั้นที่ 2 — runtime fail closed เฉพาะ production**
เมื่อขั้นที่ 1 ทำให้สภาพนั้นเป็นไปไม่ได้แล้ว การ fail closed จึงไม่เสี่ยงอะไร
```ts
if (!expectedPinToken()) {
  if (process.env.VERCEL_ENV === "production") {
    return NextResponse.json({ error: "misconfigured" }, { status: 503 });
  }
  return NextResponse.next();  // local dev ยังสะดวกเหมือนเดิม
}
```

**ขั้นที่ 3 — `/api/health` ที่บอก "ตั้งค่าครบไหม" ไม่ใช่แค่ 200**
คืน **boolean เท่านั้น ห้ามคืนค่า secret หรือความยาวของ secret** · อยู่ใน `PUBLIC_PATHS` และต้อง rate limit
```json
{ "ok": true, "auth": { "configured": true }, "db": { "reachable": true } }
```
ให้ P6 ตั้ง monitor ที่ alert เมื่อ `auth.configured === false` → รู้จาก monitor ไม่ใช่รู้จากการถูกเจาะ
(ปิดช่อง A09 ในส่วนที่สำคัญที่สุด: **ตรวจจับ misconfiguration ก่อนที่จะมีคนใช้ประโยชน์**)

**ขั้นที่ 4 — break-glass ที่มีอายุ แทน "ปิด auth ชั่วคราว"**
สำหรับเหตุจริง (auth provider ล่มขณะยืนอยู่กลางโซล):
- token ลงนามฝั่งเซิร์ฟเวอร์ **มีวันหมดอายุในตัว** ใช้ได้ครั้งเดียว → เปิด session ปกติ
- ทุกครั้งที่ใช้ต้อง log
- 🔴 **ห้ามทำเป็น env แบบ boolean `DISABLE_AUTH=1`** — ธงแบบนั้นถูกเปิดตอนตีสามแล้วไม่มีใครปิด
  และไม่มีอะไรเตือนว่ายังเปิดอยู่ · ของที่หมดอายุเองปลอดภัยกว่าของที่ต้องจำไปปิด

**ขั้นที่ 5 — ลดแรงจูงใจที่ทำให้อยากเปิด fail-open ตั้งแต่แรก**
ความกลัวจริงคือ "เปิด `/today` ไม่ได้ตอนอยู่หน้างาน" ไม่ใช่ "auth ไม่ทำงาน"
→ ให้ SW/IndexedDB เก็บแผน**ของวันนี้แบบอ่านอย่างเดียว** ไว้ให้ผู้ใช้ที่ล็อกอินไว้แล้ว
auth ล่ม = ดูแผนวันนี้ได้แต่แก้ไม่ได้ ดีกว่าทั้ง "เว็บตาย" และ "เว็บเปิดโล่ง"
⚠️ **นี่คือ offline อ่านอย่างเดียว ไม่ใช่ offline editing** ที่ `PLAN.md §1` ตัดออกไปแล้ว —
ไม่มี conflict resolution เพราะไม่มีการเขียน · **เป็นโซนของ P3/P7 ผมเสนอเป็นทิศทาง ไม่ได้ออกแบบ**

### 4.3 `/api/keep-alive` — fail-open แบบเดียวกัน แต่แก้ง่ายกว่า

`keep-alive/route.ts:24-27` ปล่อยผ่านเมื่อไม่มี `CRON_SECRET` (ตอนนี้ตั้งแล้ว ยืนยัน 401 แล้ว)
ความเสียหายจำกัดกว่ามาก — route คืนแค่ `{ ok, pingedAt }` ไม่คืนข้อมูลทริป (`:36-44` เขียนกำกับไว้ชัด)
เข้าขั้นที่ 1 ชุดเดียวกันได้เลย: ใส่ `CRON_SECRET` ใน `REQUIRED_IN_PROD` แล้วเปลี่ยนเป็น fail closed
**ไม่ต้องมีกลไกพิเศษของตัวเอง**

## 5. แผนย้าย rate limit ออกจาก in-memory

### 5.1 ทำไมของวันนี้กันไม่ได้จริง

`lib/rateLimit.ts:5` เป็น `Map` ต่อ **serverless instance** — โค้ดเขียนกำกับเองที่บรรทัด 8 ว่า
"เป็นด่านคุมค่าใช้จ่าย ไม่ใช่ด่านความปลอดภัย" ซึ่งเป็นการประเมินตัวเองที่ตรงและซื่อสัตย์
3 อย่างที่ทำให้ข้ามได้:

1. **หลาย instance = หลาย Map** · Vercel สเกลตามโหลด → ยิงแรงขึ้นได้ instance เพิ่มขึ้น เพดานจริงเพิ่มตาม
   → **ยิงแรงขึ้น = โดนจำกัดน้อยลง** ซึ่งกลับหัวจากที่ควรเป็น
2. **`x-forwarded-for` ตัวซ้ายสุด** (`:38`) เป็นค่าที่ client เติมเองได้ → เปลี่ยน IP ทุก request = ไม่เคยชนเพดาน
   (โค้ดรู้อยู่แล้ว — บรรทัด 7 เขียนว่า "ปลอมได้")
3. **`buckets.clear()` เมื่อถึง `MAX_BUCKETS`** (`:15`) → ยิงจาก IP ปลอม 5,000 ตัวรวดเดียว
   **ล้างสถานะของคนที่กำลังโดนจำกัดอยู่** = ปลด rate limit ของตัวเองได้ตามใจ
   ข้อนี้สำคัญที่สุดสำหรับ `/api/unlock` เพราะเพดาน 10/นาที คือ**สิ่งเดียว**ที่ทำให้ PIN 4 หลักพอใช้ได้
   (`unlock/route.ts:5-8` เขียนเองว่า "ห้ามถอดออก") — ช่องนี้ทำให้ไล่เดา PIN ครบ 10,000 ค่าได้ในเวลาอันสั้น

### 5.1.1 ข้อตัดสินที่ P1 ส่งมาให้ผมตัดสิน: `/api/unlock` แก้ก่อนบินไหม

**คำตอบ: ไม่แก้โค้ดก่อนบิน — เห็นด้วยกับ P1 แต่ด้วยเหตุผลอื่น · และมี 1 อย่างที่ควรทำ ซึ่งไม่ต้องแตะโค้ด**

**ก. เหตุผลของ P1 (*"ไม่มีใครรู้ URL"*) ผมไม่รับ** — นั่นคือ security through obscurity
ถ้ามันเป็นเหตุผลที่ยอมรับได้ มันก็เป็นเหตุผลให้ไม่ต้องมีด่าน PIN เลยตั้งแต่ต้น
และมันจะกลายเป็นข้ออ้างเดิมซ้ำได้ทุกครั้งที่เจอช่องใหม่ · **ควรบันทึกว่ารับความเสี่ยง ไม่ใช่ว่าไม่มีความเสี่ยง**

**ข. เพดาน 10/นาที อ่อนกว่าที่ `unlock/route.ts:5-8` คำนวณไว้จริง และไม่ต้องปลอม header ก็ข้ามได้**
คอมเมนต์ในไฟล์ประเมินว่า 10/นาที = ไล่ครบ 10,000 ค่าใช้ ~16 ชม. ซึ่งถูกถ้ามี bucket เดียว
แต่ `Map` อยู่ **ต่อ serverless instance** → ยิงพร้อมกันหลายสายทำให้ Vercel เพิ่ม instance
→ เพดานจริงคือ **10 × จำนวน instance ต่อนาที** · ยิ่งยิงแรงยิ่งได้เพดานสูงขึ้น ซึ่งกลับหัวจากที่ควรเป็น
ถ้าโดน 20 instance = 200/นาที → **10,000 ค่าไล่ครบใน ~50 นาที ไม่ใช่ 16 ชม.**
ข้อนี้ **ไม่ต้องปลอม `x-forwarded-for` เลย** จึงไม่ขึ้นกับคำถามว่า Vercel เขียน header นั้นทับหรือต่อท้าย
(คำถามนั้นยังไม่ได้ยืนยัน — ยืนยันได้ด้วยการยิง `/api/unlock` พร้อม XFF ปลอมแล้วดูว่าโดนนับรวมไหม
**ยังไม่ทำเพราะเป็นการยิงทราฟฟิกรูปร่างเดา-PIN ใส่เว็บ production ของผู้ใช้ ต้องขออนุญาตก่อน**)

**ค. เหตุผลจริงที่ไม่ควรแก้ตอนนี้: มันคือลิงก์ที่แข็งที่สุดในโซ่ที่ขาดอยู่แล้ว**
ต่อให้ PIN ถูกเดาแตก ผู้โจมตีได้สิ่งที่ **B2/B3 แจกให้ใครก็ได้ที่เปิด DevTools อยู่แล้ว** —
ทีมตัดสินรับความเสี่ยงชั้นนั้นไว้แล้ว (D12 ก็อ้างเหตุผลเดียวกัน) · การไปเสริมด่านที่ซ้อนอยู่**บน**
ประตูที่เปิดอยู่ ไม่ได้ลดความเสี่ยงจริงลงเลย แต่จ่ายด้วยการแก้โค้ด `lib/rateLimit.ts` ที่ทุก
route ทั้ง 13 ตัวเรียกใช้ **ระหว่าง freeze 8 สัปดาห์ก่อนบิน** → **ความเสี่ยงจากการแก้สูงกว่าความเสี่ยงที่แก้ได้**

**ง. 🟢 สิ่งที่ควรทำ และไม่ต้องแตะโค้ดแม้แต่บรรทัดเดียว: เพิ่มความยาว `TRIP_PIN`**
`pinIsCorrect()` (`pinAuth.ts:46-54`) เทียบความยาวก่อนแล้วเทียบทั้งสตริง — **ไม่มีที่ไหนบังคับว่า 4 หลัก**
`TRIP_PIN` เป็น env var ล้วน → เปลี่ยนเป็น 8-10 หลักได้ที่ Vercel โดยไม่แก้โค้ด ไม่แก้ DB ไม่แก้ migration
- 4 หลัก (10,000 ค่า) ที่ 200/นาที = **~50 นาที**
- 8 หลัก (100,000,000 ค่า) ที่ 200/นาที = **~950 ปี**
→ **ปิดช่องทั้งข้อ ข. ได้โดยไม่ต้องแตะ `rateLimit.ts` เลย** และไม่ขึ้นกับว่า XFF ปลอมได้หรือไม่
เพราะไม่ได้ไปพึ่งเพดานอีกต่อไป

ราคาที่จ่าย 2 อย่าง ต้องรู้ก่อนทำ:
1. **cookie เดิมใช้ไม่ได้ทันที** — cookie คือ `HMAC(secret, pin)` (`pinAuth.ts:26-31`) เปลี่ยน PIN
   แล้วค่าที่คาดหวังเปลี่ยน → ทั้ง 2 คนต้องกรอกใหม่ครั้งเดียว · **ต้องทำก่อนออกเดินทาง ไม่ใช่ระหว่างทริป**
2. env ของ Vercel ต้อง **redeploy** จึงมีผล — เป็นการ deploy ที่ไม่มี diff ของโค้ด จึงเสี่ยงต่ำสุดเท่าที่ deploy จะเป็นได้

UX แทบไม่เปลี่ยน: cookie อายุ 90 วัน (`pinAuth.ts:15`) → กรอกครั้งเดียวต่อเครื่องต่อทริป
**PIN ยาวขึ้น 4 หลักแลกกับ 950 ปี เป็นการแลกที่ดีที่สุดในรีวิวนี้ทั้งฉบับ**

⚠️ **นี่เป็นการเปลี่ยนค่า env ของ production + ทำให้ทั้ง 2 คนต้องกรอก PIN ใหม่ → เป็นการตัดสินใจ
ของผู้ใช้ ไม่ใช่ของผมหรือ P1** · ขอให้ P1 เสนอผู้ใช้ พร้อมบอกว่าต้องกรอกใหม่ครั้งเดียว

**ประเมินความเร่งด่วนของ `rateLimit.ts` เอง:** ต้องแก้ก่อน**เปิดให้คนอื่นสมัคร** (ตอนนั้น
`/api/unlock` จะกลายเป็น login ซึ่งเพดานเป็นด่านจริง และ PIN ยาวช่วยไม่ได้เพราะรหัสเป็นของผู้ใช้แต่ละคน)
· ไม่ใช่ก่อนบิน

### 5.2 ที่ควรเป็น

| ทางเลือก | ข้อดี | ข้อเสีย | ความเห็น |
|---|---|---|---|
| **Postgres (Supabase ที่มีอยู่)** | ไม่เพิ่ม vendor · แชร์ทุก instance จริง · นับได้ต่อ `user_id` · log ได้ในที่เดียวกับ audit | +1 round-trip ต่อ request · ใช้ connection ของ DB | ✅ **เริ่มที่นี่** |
| Upstash Redis | เร็ว · `@upstash/ratelimit` มี sliding window ให้ · Vercel integration | +1 vendor +1 ชุด secret | ย้ายไปเมื่อ latency เป็นปัญหาจริง วัดก่อน |
| Vercel Firewall / WAF | ไม่ต้องเขียนโค้ด | หยาบ · ผูกกับแพลตฟอร์ม · ไม่รู้จัก `user_id` | เสริมชั้นนอก ไม่ใช่ตัวหลัก |

**ต้องเป็น 1 statement อะตอมมิก** — อ่านแล้วเขียน (แบบที่โค้ดวันนี้ทำ) มี race ที่ทำให้ 2 request
พร้อมกันนับเป็น 1 ครั้ง ซึ่งเป็น bypass ที่พอทำซ้ำได้:
```sql
-- schema `app` (ไม่ expose ให้ PostgREST) · SECURITY DEFINER · เรียกจาก route ด้วย service role
insert into app.rate_limits (bucket_key, window_start, hits)
values (p_key, date_trunc('minute', now()), 1)
on conflict (bucket_key, window_start)
  do update set hits = app.rate_limits.hits + 1
returning hits <= p_limit;
```

**เปลี่ยนคีย์ด้วย ไม่ใช่ย้ายที่เก็บเฉยๆ** — ย้ายที่เก็บแต่ยังนับด้วย IP ที่ปลอมได้ = แก้แค่ครึ่งเดียว:

| route | คีย์ที่ควรใช้ | เหตุผล |
|---|---|---|
| ทุก route ที่ต้องล็อกอิน | `user_id` จาก JWT | ปลอมไม่ได้ (ลงนามแล้ว) · ตรงกับสิ่งที่อยากจำกัดจริง (คนหนึ่งคน ไม่ใช่ IP หนึ่งตัว) |
| `/api/unlock` และ login | IP **จากแพลตฟอร์ม** (ไม่ใช่ XFF ตัวซ้ายสุด) + คีย์ต่อบัญชีที่พยายามเข้า | ยังไม่มี identity ตอนนั้น · ต้องกันทั้ง "IP เดียวลองหลายบัญชี" และ "หลาย IP ลองบัญชีเดียว" |
| `/api/place-*` | `user_id` | เป็น route ที่คิดเงินต่อ request → ต้องรู้ว่าใครใช้ ไม่ใช่แค่กันยอดรวม |

**และปิดที่ต้นทาง:** ย้ายแคชเข้า schema `cache` ที่ไม่ expose (`rls-policies.sql` §7) ทำให้เขียนแคช
จาก browser ไม่ได้เลย → ลดสิ่งที่ต้อง rate limit ลง แทนที่จะ rate limit สิ่งที่ไม่ควรเข้าถึงได้ตั้งแต่แรก

## 6. Storage — ไฟล์ตั๋วเป็นข้อมูลส่วนบุคคล

### 6.0 ตอบ D12 — "มันเปลี่ยนลำดับความเสี่ยงใน threat model ไหม"

**ตอบ: ใช่ และผมจัดให้เป็นอันดับ 1 ไปแล้วก่อนที่ D12 จะมาถึง** (§1.2) — P8 กับผมไปเจอเรื่องเดียวกัน
แยกกันคนละทาง ซึ่งเป็นสัญญาณที่ดีว่าไม่ใช่การตีความเกินจริงของใครคนหนึ่ง

เหตุผลที่ขึ้นอันดับ 1 แทน B2 (ซึ่งดูใหญ่กว่าเพราะครอบ 14 ตาราง):
1. **ความเสียหายออกนอกระบบ** — ตารางอื่นรั่วแล้วเสียหายอยู่ในทริป · ตั๋วรั่วแล้วใช้กับ**สายการบิน**
   ได้ (ชื่อตามพาสปอร์ต + เลขที่จองพอสำหรับอ้างเป็นเจ้าของการจอง) → ความเสียหายไปเกิดที่ระบบ
   ที่เราแก้อะไรไม่ได้และย้อนไม่ได้
2. **RLS แก้ไม่ตก** — ทำ policy ครบทั้ง 14 ตารางแล้วข้อนี้ยังเปิดอยู่ ต่างจากลำดับ 2-6 ที่จบใน E1/E2
3. **ไม่มีที่สำรอง** — ลบไฟล์ตั๋วแล้วหายถาวร ไม่มี soft delete ไม่มี backup ในระบบ

🔴 **และ D12 ยังไม่ครบ — ขาดชั้นที่ทำให้ลูกโซ่สั้นกว่าที่เขียนไว้**
D12 บรรยายลูกโซ่ว่า `anon key → อ่าน bookings.file_url → ดึงไฟล์` ซึ่งถูก แต่**ไม่ต้องผ่าน
ตาราง `bookings` เลยก็ได้**: policy `select` บน `storage.objects` (`0019:9-11`) ยอมให้
`POST /storage/v1/object/list/booking-files` **ไล่ชื่อไฟล์ทั้ง bucket ตรงๆ**
→ ลูกโซ่จริงสั้นกว่า: `anon key → list bucket → ดึงไฟล์` · **ไม่ต้องแตะ B2 เลย**
แปลว่า **ถ้าอุด B2 ครบทุกตารางแต่ไม่แตะ Storage ช่องนี้ยังเปิดเต็มบาน** — และรวมถึง
`trip_stops.photo_url` (รูปหน้างานที่ผู้ใช้ถ่ายเอง) ที่ D12 ไม่ได้พูดถึงแต่อยู่ bucket เดียวกัน
*(สรุปจาก policy + GRANT เริ่มต้นของ Supabase · **ยังไม่ยืนยันด้วยการรัน** ห้ามยิง DB จริง → เคส T-17)*

**สำหรับทริป: เห็นด้วยกับ D12 ว่าไม่แก้ก่อนบิน** — เปลี่ยน bucket เป็น private ตอนนี้ทำให้รูปตั๋ว
หายทั้งเว็บ เพราะโค้ดใช้ `getPublicUrl` ทุกจุด · แต่ขอเพิ่มว่ามีทางลดของที่รั่ว**โดยไม่แตะโค้ดเลย**
และเป็นเรื่องที่ควรถามผู้ใช้ ไม่ใช่ตัดสินแทน → §6.4

### 6.1 สถานะวันนี้ (F1 — ข้อที่ต้องแย้ง P1 หนักที่สุด)

P1 เขียนว่า *"policy ของ Storage 4 ตัว gate แค่ `bucket_id` ไม่มีเงื่อนไขอื่นเลย"* — **ถูก แต่ยังไม่ถึงแก่น**
เพราะ **bucket ตั้งเป็น Public** (`0019:1,7` เขียนกำกับเอง · โค้ดใช้ `getPublicUrl` ที่
`lib/stopPhoto.ts:26` และ `BookingEditModal.tsx:97`) → เส้นทาง `/storage/v1/object/public/...`
**ไม่ผ่าน RLS เลย** · policy 4 ตัวนั้นจึงไม่เคยเป็นด่านของการอ่านตั้งแต่แรก
ต่อให้เขียน `using` ดีแค่ไหนก็ไม่เปลี่ยนอะไรถ้า bucket ยัง public

**3 ชั้นที่ต่อกันเป็นการรั่วทั้ง bucket:**

1. `select` policy `using (bucket_id = 'booking-files')` → `POST /storage/v1/object/list/booking-files`
   **ไล่ชื่อไฟล์ทั้ง bucket ได้** ด้วย anon key เปล่า
   *(สรุปจาก policy + GRANT เริ่มต้นของ Supabase บน `storage.objects` — ยืนยันโดยอ้อมจากข้อเท็จจริงว่า
   การอัปโหลดด้วย anon key ในแอปทำงานได้จริง ซึ่งต้องมี GRANT อยู่แล้ว · **ยังไม่ยืนยันด้วยการรัน** ห้ามยิง DB จริง → เคส T-17)*
2. public bucket → เปิดอ่านทุก path ที่ได้จากข้อ 1 ทันที ไม่ต้อง auth
3. ในไฟล์คือ **รูปตั๋วที่มีชื่อตามพาสปอร์ตและเลขที่จอง** — ตรงกับความเสียหายลำดับ 1 ใน §1.2

ชื่อไฟล์มี `Date.now()` + `Math.random().toString(36).slice(2)` (~57 บิต) ซึ่ง**เดาไม่ได้**จริง
→ ถ้ามีแค่ชั้น 2 ความเสี่ยงจะต่ำ · **แต่ชั้น 1 ทำให้ไม่ต้องเดา** — จุดนี้คือหัวใจ:
มาตรการที่พึ่งพา "URL เดาไม่ได้" พังทั้งหมดเมื่อมี endpoint ที่บอก URL ให้

### 6.2 ปัญหาที่ policy แก้ไม่ได้: path ไม่มี tenant key

```
lib/stopPhoto.ts:21      stop-photo-{stopId}-{ts}-{rand}-{ชื่อไฟล์เดิม}
BookingEditModal.tsx:85  {bookingId}-{ts}-{rand}-{ชื่อไฟล์เดิม}
```
**flat ทั้ง bucket ไม่มีโฟลเดอร์** → policy ที่กรองด้วย `(storage.foldername(name))[1]`
**ไม่มีอะไรให้กรอง** สำหรับไฟล์ที่มีอยู่ · แปลว่านี่ไม่ใช่งานเขียน policy แต่เป็น **งานย้ายข้อมูล**
ต้อง rename ทุก object พร้อมอัปเดต `bookings.file_url` / `trip_stops.photo_url` ที่ชี้อยู่
→ ต้องอยู่ใน `E7` (ซ้อม migrate ข้อมูลจริง 2 รอบ) ไม่ใช่ `E1` · **แจ้ง P1 ให้เผื่อเวลาไว้ในไทม์ไลน์**

## 7. แคชฝั่งเซิร์ฟเวอร์เดินอ้อม RLS (D11) — คลาสที่ RLS กันไม่ได้เลย

**รับข้อนี้ทั้งข้อ และประเมินว่าเป็นความเสี่ยงอันดับ 2 ของระยะ 2 รองจาก Storage**
เหตุผลที่ร้าย: มันไม่ใช่ policy ที่เขียนผิด — **policy ถูกทุกตัวแล้วยังรั่ว** เพราะ RLS เป็นตัวกรอง
ที่ทำงานใน Postgres · การ hit แคชคือการ **ไม่ไปถึง Postgres** → ไม่มีอะไรให้กรอง
ทุกบรรทัดใน `rls-policies.sql` ไร้ผลกับ request ที่ตอบจากแคช

ต่างจากทุกข้อในรีวิวนี้ตรงที่ **ไม่มีวิธีอุดจากฝั่ง DB** — ต้องอุดที่โครงสร้างโค้ดเท่านั้น

### 7.1 blast radius ต่างกันมากตาม directive ที่เลือก (ตรวจกับเอกสาร Next 16.3 ในเครื่องแล้ว)

`next.config.ts` วันนี้ว่างเปล่า (B9) → ยังไม่ได้เปิด `cacheComponents` จึงยังไม่มีความเสี่ยงนี้จริง
แต่ `frontend-arch.md` ของ P3 วางแผนเปิด → ต้องตัดสินกฎก่อนเปิด ไม่ใช่หลัง

| directive | เก็บที่ไหน | อ่าน `cookies()` ได้ไหม | blast radius ถ้าลืมตรวจสมาชิก |
|---|---|---|---|
| `'use cache: private'` | 🟢 **browser memory เท่านั้น · ไม่เก็บบนเซิร์ฟเวอร์เลย** ไม่ข้าม reload | ✅ ได้ | **รั่วข้าม tenant ไม่ได้เชิงโครงสร้าง** — 1 แคช = 1 เบราว์เซอร์ = 1 คน |
| `'use cache'` | 🟡 in-memory **ต่อ instance** · หายเมื่อ restart | ❌ **ไม่ได้ — Next บล็อกให้** | รั่วเฉพาะคนที่ตกลง instance ที่อุ่นไว้ · **เป็นช่วงๆ ทำซ้ำยาก** |
| `'use cache: remote'` | 🔴 **durable · แชร์ทุก instance ทุก region · อยู่ข้าม restart** | ❌ ไม่ได้ | **รั่วถาวรกับทุกคน** จนกว่า tag จะถูก invalidate |

หลักฐาน: `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-cache-private.md:14`
(*"never stored on the server, cached only in the browser's memory"*) และ `:160-167` (ตารางว่า
`cookies()`/`headers()`/`searchParams` **ไม่อนุญาต** ใน `use cache` ธรรมดา) · `use-cache-remote.md:17,25`
(`use cache` เป็น in-memory ต่อ instance · `remote` เป็น *"durable caching shared across all server instances"*)

**ข่าวดีที่ควรบันทึก: กฎของ P1 (*"ข้อมูลรายทริป/รายผู้ใช้ → `'use cache: private'` เท่านั้น"*)
แข็งกว่าที่ D11 เขียนไว้** — ไม่ใช่แค่ "ปลอดภัยกว่า" แต่ทำให้สถานการณ์ใน D11 **เป็นไปไม่ได้**
เพราะไม่มี entry บนเซิร์ฟเวอร์ให้ B ไป hit ตั้งแต่ต้น · และ Next ยังช่วยอีกชั้นด้วยการ**ห้าม**
อ่าน `cookies()` ใน `use cache` ธรรมดา ซึ่งปิด footgun ที่พบบ่อยที่สุด (เผลอ key แคชด้วย session)

### 7.2 🔴 กับดักที่ไม่มีใครในทีมพูดถึง: คำแนะนำเรื่อง performance ในเอกสาร Next คือทางไปสู่เวอร์ชันที่แย่ที่สุด

`use-cache-remote.md:17` เปิดหัวข้อด้วยประโยคที่ตรงกับสิ่งที่คนทำ perf จะรู้สึกใน E6 พอดี:
*"คุณอาจสังเกตว่า cached operation รันซ้ำบ่อยกว่าที่คาด หรือ database ถูกยิงมากกว่าที่ควร"*
→ คำตอบที่เอกสารเสนอคือ **อัปเป็น `'use cache: remote'`**

นั่นคือเส้นทางจริงที่จะเปลี่ยน**การรั่วเป็นช่วงๆ ใน instance เดียว** ให้กลายเป็น
**การรั่วถาวรที่แชร์ทุก instance** — และมันจะเกิดใน **E6 (Perf)** ซึ่งอยู่**หลัง** E2 ที่เทสต์
104 เคสขึ้นเขียวไปแล้ว **โดยที่ไม่มีเทสต์ RLS ตัวไหนพัง** เพราะปัญหาไม่ได้อยู่ที่ policy

**กฎที่ขอให้ P1 รับเข้า `architecture.md §3.4` เพิ่มอีก 1 ข้อ:**
> 🔴 **ข้อมูลรายทริป/รายผู้ใช้ ห้ามใช้ `'use cache: remote'` เด็ดขาด ไม่ว่าตัวเลข perf จะออกมาอย่างไร**

ข้อดีของกฎนี้คือมันไม่ต้องแลกอะไรเลย — `use-cache-remote.md:56` บอกเองว่าถ้า cache key
มีค่าเฉพาะตัวต่อ request (*"user-specific parameters"*) **cache utilization จะเกือบเป็นศูนย์**
→ ข้อมูลรายทริปเป็นกรณีที่ remote cache **ทั้งอันตรายที่สุดและได้ประโยชน์น้อยที่สุด** พร้อมกัน
ไม่ใช่การแลกความเร็วกับความปลอดภัย

### 7.3 เวอร์ชันที่ร้ายกว่า: แคชตัว "ตรวจสิทธิ์" ไม่ใช่แคช "ข้อมูล"

D11 บรรยายกรณีแคชข้อมูล · มีอีกกรณีที่อาการเหมือนกันแต่หายากกว่า:
```
canRead(tripId)  ← เผลอใส่ 'use cache' ที่ฟังก์ชันตรวจสิทธิ์เอง
A เรียก → true → เก็บใต้คีย์ ("X")
B เรียก → HIT → ได้ true ของ A → ผ่านด่าน แล้วไปอ่าน DB ด้วย session ของ B เอง
```
กรณีนี้ **RLS ช่วยไว้ได้** (query จริงยังวิ่งด้วย session ของ B) → เสียหายแค่ B เห็นว่า "มีสิทธิ์"
แล้วได้ข้อมูลว่างเปล่า = หน้าเปล่าแทน 403 · **แต่ถ้า DAL นั้นใช้ service role เพราะ "ตรวจสิทธิ์แล้ว"
จะรั่วเต็มจำนวน** → เชื่อมกับสิ่งที่ผมส่งให้ P5: **ห้าม tool/DAL ใดใช้ service role โดยอ้างว่าตรวจสิทธิ์มาแล้ว**

Next ช่วยกันชั้นหนึ่ง: `use cache` อ่าน `cookies()` ไม่ได้ → ฟังก์ชันตรวจสิทธิ์ที่รับ user จาก session
จะ **error ตอน build** ไม่ใช่เงียบ · ช่องที่หลุดคือตอนส่ง `userId` เข้าไปเป็น argument
(คีย์รวม userId จึงแยกกันถูก) **หรือ** ตอนสร้าง Supabase client ไว้นอกฟังก์ชันแล้วส่งเข้าไป
— อย่างหลังนี่ Next มองไม่เห็นและไม่มีอะไรเตือน

### 7.4 ทำไมเรื่องนี้เทสต์ยากผิดปกติ — และเทสต์แบบไหนที่เชื่อได้

🔴 **`use cache` เก็บใน memory ต่อ instance → ผลลบของเทสต์ไม่พิสูจน์อะไรเลย**
เทสต์ที่ให้ A อุ่นแคชแล้วให้ B ยิง อาจได้ "B ไม่เห็นข้อมูล A" เพราะ B **ตกลง instance อื่น**
ไม่ใช่เพราะโค้ดถูก · รันซ้ำ 100 ครั้งก็ยังเป็นการเดา และจะเขียวใน CI แล้วรั่วใน production
(สภาพตรงข้ามกับที่ทุกคนคาด: dev เครื่องเดียว instance เดียวจะ**เจอบั๊กง่ายกว่า** production หลาย instance)

→ **เทสต์ runtime อย่างเดียวไม่พอสำหรับข้อนี้ ต้องมีเทสต์เชิงโครงสร้างเป็นตัวหลัก**

| เคส | ชนิด | อะไร | ต้องได้ |
|---|---|---|---|
| **C-01** | 🔴 static (ตัวหลัก) | grep/ESLint rule: ไฟล์ไหนมี `'use cache'` หรือ `'use cache: remote'` **และ** แตะตารางที่มี `trip_id` | 0 จุด · เป็น lint error ไม่ใช่ warning |
| **C-02** | 🔴 static | `'use cache: remote'` ปรากฏที่ไหนก็ตามในโค้ดที่ไม่ใช่ catalog | 0 จุด (กฎ §7.2) |
| **C-03** | static | ฟังก์ชันตรวจสมาชิกต้องไม่อยู่ในไฟล์/สโคปที่มี directive แคชใดๆ | 0 จุด (§7.3) |
| **C-04** | runtime | A (สมาชิก X) อุ่นแคช → B (ไม่ใช่สมาชิก) เปิด `/trip/X` **ใน process เดียวกัน** (`next start` instance เดียว บังคับให้ชน instance เดิม) | B ได้ 403/404 · **ห้ามได้ 200 ที่มีข้อมูลของ A** · ต้องรันแบบ single-instance เท่านั้น ไม่งั้นไร้ความหมาย |
| **C-05** | runtime | หลัง C-04 ผ่าน → เปลี่ยน directive เป็น `'use cache'` ธรรมดาชั่วคราวแล้วรัน C-04 ซ้ำ | **ต้องแดง** — พิสูจน์ว่า C-04 จับได้จริง (เทสต์ตัวเทสต์ แบบเดียวกับเมทริกซ์แดงใน §2.6) |
| **C-06** | runtime | `cacheTag`/`revalidateTag` ของทริป X ต้องไม่ล้างหรืออ่าน entry ของทริป Y | tag ต้องมี `tripId` ทุกตัว · tag ระดับ collection (`"trips"`) ห้ามใช้กับข้อมูลรายทริป |

**C-01 กับ C-02 เป็นตัวหลัก ไม่ใช่ตัวเสริม** — เป็นเทสต์เดียวในกลุ่มนี้ที่ให้ผลเหมือนกันทุกครั้ง
ไม่ขึ้นกับว่า request ตกลง instance ไหน · ให้ P6 ใส่ใน CI เป็น step แยกจากเทสต์อื่น

- `cacheComponents: true` ต้องเปิดใน `next.config.ts` ก่อนใช้ directive ใดได้ — **โซน P3**
- `stale` ต้อง ≥ 30 วินาทีเพื่อให้ runtime prefetch ทำงาน · ≥ 5 นาทีเพื่อเข้า App Shell
  (`use-cache-private.md:154`) → ยิ่ง `stale` ยาว หน้าต่างที่ข้อมูลค้างในเบราว์เซอร์หลัง**ถอดคนออกจากทริป**
  ก็ยิ่งยาว · **ถอดสมาชิกออกแล้วเขายังเห็นข้อมูลได้อีกเท่ากับ `stale`** — ยอมรับได้ถ้ารู้ตัวเลข
  แต่ต้องเป็นตัวเลขที่ตัดสินใจ ไม่ใช่ค่าที่ติดมา → ขอให้ P8 เขียนลง acceptance criteria ของ story "ถอดสมาชิก"

## 8. รีวิว `schema/copilot_proposals.sql` ของ P5 (P5 ฝากมาผ่าน P1)

P5 ฝากมาให้ดู *"จุดที่ตรงข้ามกับบั๊ก `travel_time_cache`"* — **ใช่ มีอยู่จริง และร้ายกว่าที่เขาสงสัย**
พร้อมอีก 5 ข้อที่เจอระหว่างอ่าน · **ยืนยันจากไฟล์เท่านั้น ไม่ได้รัน SQL ที่ไหน**

### 8.1 🔴 P-01 · Server Action เปลี่ยน `status` ไม่ได้เลย — ตายก่อนเริ่ม ไม่ใช่ตอน race

P5 ตั้งใจไม่ให้มี UPDATE policy (บรรทัด 119-122) แล้วให้ Server Action เปลี่ยน `status`
**เจตนาถูก แต่ตามที่เขียนไว้ทำไม่ได้:** Server Action ที่ใช้ session ของผู้ใช้ **ก็เป็น role
`authenticated` เหมือน browser** — RLS ไม่สนว่าคำสั่งมาจากเซิร์ฟเวอร์หรือเบราว์เซอร์ มันสนแค่ role
→ ไม่มี UPDATE policy = **ทุกการเปลี่ยน `status` ได้ `42501` ทุกครั้ง** ไม่ใช่บางครั้ง

**ต่างจาก `travel_time_cache` ตรงที่หนักกว่า:** ที่นั่นชนเฉพาะตอน race และผลกระทบเป็นศูนย์
ที่นี่มันคือ **เส้นทางหลักของฟีเจอร์** (กดยืนยัน/ปฏิเสธข้อเสนอ) → พังทุกครั้ง
· ข้อดีคือ **พังดังจนเจอในนาทีแรกของ E8** ไม่ใช่พังเงียบเหมือน `travel_time_cache`

**3 ทางออก และ 2 ทางแรกผิด:**
| ทาง | ผล |
|---|---|
| เพิ่ม UPDATE policy ให้ `authenticated` | ❌ **เปิดช่องที่ P5 ตั้งใจปิดพอดี** — client ยิง REST เปลี่ยน `status` ข้ามด่าน `base_versions` ได้ทันที |
| ให้ Server Action ใช้ service role | ❌ ข้าม RLS ทั้งระบบ · **ขัดกับสิ่งที่ผมส่งให้ P5 ในรอบแรก** และ §7.3 อธิบายว่านี่คือทางที่คนจะเดินเข้าไปด้วยเหตุผลว่า "ตรวจสิทธิ์แล้ว" |
| ✅ **`SECURITY DEFINER` function** | ได้ทั้ง 3 อย่าง: ไม่มี UPDATE policy ให้ client (บายพาสไม่ได้) · ไม่ต้องใช้ service role (RLS ยังทำงานที่อื่นครบ) · **ด่าน `base_versions` อยู่ในฟังก์ชันเดียวกับการเขียน จึงข้ามไม่ได้เชิงโครงสร้าง** |

```sql
-- schema `app` (ไม่ expose ให้ PostgREST) · เจ้าของเป็น postgres
create or replace function app.decide_proposal(p_id uuid, p_accept boolean)
returns text language plpgsql security definer set search_path = '' as $$
declare v_trip uuid; v_stale boolean;
begin
  select trip_id into v_trip from public.copilot_proposals
   where id = p_id and status = 'pending' for update;
  if v_trip is null then return 'not_pending'; end if;
  -- ตรวจสมาชิกเองข้างใน เพราะ SECURITY DEFINER ข้าม RLS ไปแล้ว
  if not app.can_write_trip(v_trip) then raise exception 'forbidden'; end if;
  -- ...ตรวจ base_versions ที่นี่ ในทรานแซกชันเดียวกับการเขียน...
  update public.copilot_proposals
     set status = case when v_stale then 'stale'
                      when p_accept then 'applied' else 'rejected' end,
         decided_at = now(),
         decided_by = (select auth.uid())   -- ไม่รับจากพารามิเตอร์
   where id = p_id;
  return 'ok';
end $$;
```
🔴 **`security definer` ข้าม RLS → ต้องตรวจสมาชิกเองข้างในทุกครั้ง** · ถ้าลืมบรรทัด `can_write_trip`
ฟังก์ชันนี้จะกลายเป็นช่องให้ใครก็ตัดสินข้อเสนอของทริปใครก็ได้ — **อันตรายกว่าการไม่มีฟังก์ชันเลย**
· และ `for update` สำคัญ: ล็อกแถวไว้ ไม่ให้ 2 คนกดยืนยันข้อเสนอเดียวกันพร้อมกันแล้ว apply ซ้ำ

### 8.2 🔴 P-02 · CHECK 2 ตัวขัดกันเอง — คำสั่งเก็บกวาดของ P5 จะ **fail 100%** ไม่ใช่บางครั้ง

```sql
check ((status = 'pending') = (decided_at is null))   -- บรรทัด 84
```
ไล่ทุกกรณี: `status='expired'` + `decided_at is null` → `false = true` → **CHECK ไม่ผ่าน**
แต่ `expired` มีความหมายว่า *"หมดเวลาไปเฉยๆ โดยไม่มีใครกด"* (บรรทัด 73-74) → `decided_at` **ต้อง**เป็น null
และ CHECK ตัวที่สอง (บรรทัด 85) บังคับต่อว่า `decided_at` ไม่ null ⟺ `decided_by` ไม่ null
→ แถว `expired` จะต้องมี "คนตัดสิน" ทั้งที่นิยามคือไม่มีใครตัดสิน

→ **คำสั่งเก็บกวาดที่ P5 เขียนไว้ในคอมเมนต์บรรทัด 135-137 จะโยน CHECK violation ทุกครั้งที่รัน**
ไม่ใช่ edge case · แก้:
```sql
check ((status in ('pending', 'expired')) = (decided_at is null))
```
`stale` ไม่มีปัญหา — คนกดจริงจึงมี `decided_at`/`decided_by` ได้ตามปกติ

### 8.3 🔴 P-03 · `requested_by` ปลอมได้ — บทเรียน `added_by` กลับมาในตารางที่ออกแบบหลังบทเรียน

INSERT policy (บรรทัด 116-117) ตรวจแค่ `can_edit_trip(trip_id)` **ไม่ตรวจว่า `requested_by` เป็นตัวเอง**
→ editor เขียนแถวที่ `requested_by` เป็น uuid ของสมาชิกอีกคนได้ → การ์ดโชว์ว่า *"อีกคนเสนอ"*
ทั้งที่ตัวเองเสนอ · เป็น A08 (Data Integrity) ข้อเดียวกับที่ `added_by` โดนมาแล้ว
```sql
with check (app.can_write_trip(trip_id) and requested_by = (select auth.uid()))
```
· และ `decided_by` **ห้ามรับจากพารามิเตอร์** ต้องมาจาก `auth.uid()` ในฟังก์ชัน (ดู §8.1)

### 8.4 🟡 P-04 · "หนึ่งข้อเสนอต่อหนึ่งเทิร์น" เขียนไว้เป็นคอมเมนต์ แต่ไม่มีอะไรบังคับ

บรรทัด 92-96 บอกว่า index นี้ใช้ *"กันไม่ให้ Copilot ยิงข้อเสนอซ้อนกัน"* — แต่มันเป็น
**index ธรรมดา ไม่ใช่ unique** → index ไม่กันอะไรเลย มันแค่ทำให้ค้นเร็ว
→ 2 request พร้อมกันสร้าง proposal `pending` ของทริปเดียวกันได้ทั้งคู่

**นี่คือรูปแบบเดียวกับ `travel_time_cache` เป๊ะ: เจตนาอยู่ในคอมเมนต์ การบังคับไม่มีอยู่**
ถ้ากฎคือหนึ่ง pending ต่อทริปจริง →
```sql
create unique index copilot_proposals_one_pending
  on public.copilot_proposals (trip_id) where status = 'pending';
```
⚠️ ต้องตัดสินก่อนว่ากฎคือ "หนึ่งต่อทริป" หรือ "หนึ่งต่อผู้ใช้ต่อทริป" — ถ้าเป็นอย่างหลังให้ใส่
`(trip_id, requested_by)` · **P5 ตัดสิน ผมแค่ชี้ว่าตอนนี้ไม่มีอะไรบังคับทั้งสองแบบ**

### 8.5 🟡 P-05 · helper อยู่ `public` = กลายเป็น RPC endpoint ที่ browser เรียกได้

P5 เรียก `public.can_access_trip()` / `public.can_edit_trip()` · **ฟังก์ชันใน `public` ถูก PostgREST
สร้างเป็น endpoint `POST /rest/v1/rpc/can_access_trip` ให้อัตโนมัติ** → ใครก็ยิงถาม uuid มั่วๆ
เป็นชุดได้ กลายเป็น oracle บอกว่าทริปไหนมีอยู่/ตัวเองเป็นสมาชิกทริปไหน
ความเสียหายไม่สูง (บูลีนเกี่ยวกับตัวเอง) แต่เป็นพื้นที่โจมตีที่ไม่ต้องมี
→ ย้ายไป schema `app` ตาม `rls-policies.sql` §1 · **และชื่อไม่ตรงกับของผม** →
`can_access_trip` = `app.can_read_trip` · `can_edit_trip` = `app.can_write_trip`
**ขอ P1 เคาะชื่อชุดเดียวก่อน E2** ไม่งั้นจะมี helper 2 ชุดที่ทำงานเหมือนกัน ซึ่งเป็นทางที่ทำให้
วันหนึ่งมีคนแก้ตัวเดียวแล้วลืมอีกตัว

### 8.6 🟡 P-06 · ของเล็กที่ควรใส่ตอนนี้เพราะถูกกว่าใส่ทีหลัง

- `args`/`preview`/`base_versions` เป็น `jsonb` ไม่จำกัดขนาด · `session_id` เป็น `text` ไม่จำกัด
  → editor ยัดข้อมูลใหญ่ๆ ได้ · ใส่ `check (pg_column_size(preview) < 100000)` และ
  `check (length(session_id) <= 100)`
- **ไม่มี `deleted_at`** ขณะที่ D7 บอก *"soft delete ทุกตารางผู้ใช้"* — ผมเห็นด้วยกับ P5 ว่าตารางนี้
  **ไม่ควรมี** (เป็น audit trail · บรรทัด 139 บอกเองว่าห้ามลบอัตโนมัติ) แต่ต้องเขียนกำกับว่า
  **เป็นข้อยกเว้นที่ตั้งใจ** ไม่ใช่ตกหล่น ไม่งั้นตอนกวาด soft delete ทั้งสคีมาใน E2 จะมีคนใส่ให้
- `day_id references trip_days(id) on delete cascade` — **soft delete ทำให้ cascade ไม่เคยทำงาน**
  → proposal จะอ้างวันที่ถูก soft delete ไปแล้ว · ต้องให้ `app.decide_proposal` ตรวจว่าวันยังมีอยู่จริง
  ก่อน apply ไม่ใช่พึ่ง FK

**สรุปให้ P5 (รอบ 1):** โครงคิดถูกทั้งหมด (ตารางไม่ใช่ memory · TTL · `base_versions` เป็น concurrency
token · ไม่เปิด UPDATE ให้ client) · P-01 กับ P-02 ต้องแก้ก่อนถึงจะรันได้เลย ที่เหลือเป็นการรัดให้แน่น
· **และข้อที่คุณระวังไว้ถูกต้อง** — คุณเป็นคนเดียวที่เขียนกำกับเองว่าอาจมีปัญหาแบบ `travel_time_cache`
ซึ่งช่วยให้ผมรู้ว่าต้องดูตรงไหนก่อน

### 8.7 รอบ 2 — ตรวจของที่ P5 แก้มา · P-01…P-06 ปิดครบ · เจอใหม่ 6 ข้อ

**การหลีกเลี่ยง dynamic SQL ที่ P5 ขอให้ตรวจเป็นพิเศษ — ✅ ถูกต้อง และเหตุผลถูกทั้งข้อ**
`case v->>'table' when 'trip_stops' then ... else raise exception` — แตกเป็น branch ตายตัว
ชื่อตารางไม่เคยกลายเป็นข้อความ SQL · **และตารางที่ไม่รู้จัก `raise exception` ไม่ใช่ข้ามเงียบ** ซึ่งเป็น
ครึ่งที่คนพลาดบ่อยกว่า: ถ้าเขียน `else null` ผู้โจมตีใส่ชื่อตารางมั่วเพื่อ**ปิดด่านกันชนทั้งด่าน**ได้เลย
· ✅ P-04 ที่ P5 **ตัดสินต่างจากที่ผมเสนอ ดีกว่าของผม** — "หนึ่ง pending ต่อผู้ใช้ต่อทริป" ไม่ใช่ต่อทริป
เพราะกฎเดิมเป็นกฎของ*บทสนทนา* และการบล็อกคนที่สองด้วยเหตุผลที่เขาแก้เองไม่ได้คือทางตัน · เหตุผลนี้หนักกว่าของผม

| # | ระดับ | ข้อ |
|---|---|---|
| **P-07** | 🔴 | **`revoke all on function app.decide_proposal ... from authenticated` ทำให้เรียกไม่ได้เลย** (บรรทัด 319) · Server Action รันเป็น `authenticated` → ไม่มี EXECUTE = `permission denied for function` ทุกครั้ง · **นี่คือ P-01 กลับมาอีกชั้นหนึ่ง**: ครั้งแรกด่านหายเพราะไม่มี policy ครั้งนี้เพราะไม่มี GRANT · เหตุผลเดียวกันเป๊ะ (*"ย้ายไปเซิร์ฟเวอร์แล้วน่าจะได้สิทธิ์เพิ่ม"* ซึ่งไม่จริง) → ต้อง `grant execute ... to authenticated` เฉพาะ `decide_proposal` · ส่วน `apply_proposal`/`base_versions_match` **revoke ถูกแล้ว** เพราะ definer เรียกกันเองได้ด้วยสิทธิ์ owner |
| **P-08** | 🔴 | **`base_versions = '[]'` ผ่านด่านโดยไม่ตรวจอะไรเลย** · loop ไม่ทำงาน → `return true` · `check (jsonb_typeof(...) = 'array')` ที่เพิ่มมาไม่กันอาร์เรย์ว่าง · และ **client เป็นคนใส่ค่านี้** (INSERT policy ตรวจแค่ `can_write_trip` + `requested_by`) → editor สร้างข้อเสนอที่ **ปิดด่านกันชนของตัวเองได้** แล้วทับงานที่อีกคนเพิ่งแก้ · **รูปแบบเดียวกับ §2.8 เป๊ะ: ความจริงบนเซตว่าง** → `check (jsonb_array_length(base_versions) > 0)` + ฟังก์ชัน `return false` เมื่อว่าง (fail closed) |
| **P-09** | 🔴 | **ของผมเอง ไม่ใช่ของ P5** — `rls-policies.sql` เดิมเขียน `grant execute on all functions in schema app to authenticated` ซึ่ง **ลบล้าง `revoke` ของ P5 ถ้า migration ผมรันทีหลัง** และเปิดให้เรียก `app.apply_proposal(id)` ตรงๆ ซึ่ง **ไม่ตรวจสมาชิกข้างในตัวเอง** = ข้ามทั้งด่านสมาชิกและ `base_versions` · **2 ไฟล์อ่านแยกกันดูถูกทั้งคู่ ผลขึ้นกับลำดับการรัน ซึ่งไม่มีใครเห็นจากการอ่านไฟล์ใดไฟล์เดียว** · ✅ แก้แล้ว: grant ทีละตัว + `alter default privileges ... revoke execute from public` |
| **P-10** | 🟡 | `base_versions_match` **ไม่ scope ด้วย trip** และรันเป็น definer (ข้าม RLS) → ใส่ `id` ของแถวในทริปคนอื่นได้ ฟังก์ชันจะตอบ true/false = **oracle บอกค่า `updated_at` ของ tenant อื่น** (แบนด์วิดท์ต่ำเพราะ timestamp เอนโทรปีสูง จึงเดาไม่ไหวจริง) · ที่สำคัญกว่าคือ **ด่านอาจ "ผ่าน" โดยตรึงแถวที่ไม่ใช่แถวที่จะถูกแก้** → ส่ง `v_trip` เข้าไปแล้ว scope ทุก branch ปิดทั้ง 2 เรื่องพร้อมกันโดยไม่มีค่าใช้จ่าย |

### 9.0 🔴 PIN จริงถูก commit ลง local — **ยังไม่รั่ว แต่เป็นกับดักที่รอ push** (แก้จากร่างก่อน)

เก็บความผิดไว้ให้เห็นเพราะมันเป็นรูปแบบเดียวกับที่ทั้งเอกสารนี้พูดถึง — ดู "ความผิดของผม" ท้ายหัวข้อ

**สิ่งที่เกิดขึ้น:** ไฟล์เทสต์ 2 ไฟล์ที่ผมเขียนและ commit เมื่อ 17 ส.ค. 2026 (`8c52582`
ชื่อ commit *"Cover the PIN gate, which had no tests at all"*) ใช้ **ค่า PIN จริงของเว็บ**
เป็น fixture — `lib/__tests__/pinAuth.test.ts` และ `lib/__tests__/proxy.test.ts`
ผมหยิบค่าที่อยู่ในบันทึกของโปรเจกต์มาใช้ตรงๆ แทนที่จะสมมติขึ้นมา
· **ยืนยันว่าเป็นค่าจริง** ด้วยการเทียบกับ `TRIP_PIN` ใน `.env.local` (เทียบแบบไม่พิมพ์ค่าออกมา)

**🟢 การเผยแพร่ = ศูนย์ · ยืนยันจากเซิร์ฟเวอร์เอง ไม่ใช่จาก ref ที่ cache ไว้:**
```
git ls-remote origin refs/heads/main          → 99a2ff4  (14 ส.ค. ก่อนวันนี้)
git merge-base --is-ancestor 8c52582 origin/main → ไม่ใช่ ancestor
git log origin/main..HEAD --oneline | wc -l   → 16 commit ของวันนี้ ยังไม่ push ทั้งหมด
```
→ **ค่านั้นไม่เคยออกนอกเครื่องนี้** · ทีมนี้ไม่มีใคร push เลยทั้งวันตามที่ P1 สั่งไว้ตั้งแต่ต้น

**🔴 แต่มันคือกับดักที่ armed อยู่ ไม่ใช่เรื่องที่จบแล้ว**
`4c46808` ลบค่าออกจากไฟล์ **แต่ไม่ลบออกจากประวัติ** — ไล่ดูแล้วค่านั้นยังอยู่ใน
**7 commit ของช่วงที่ยังไม่ push** (`8c52582` · `390173b` · `c8a308e` · `b55ba38`
· `672411e` · `3703c74` · `39252fa`) · HEAD สะอาดแล้ว
และแผนของทีมคือ *"commit ทั้งชุดทีเดียวเมื่อผู้ใช้เคลียร์"*
→ **push ตามแผนนั้น = PIN ขึ้นสาธารณะทันทีและถาวร ทั้งที่ไฟล์ปัจจุบันสะอาด**
✅ P1 สั่งห้าม push ไปทุกเซสชันแล้ว

**ทางออก 2 ทาง และทางที่ 2 แพงกว่ามากบนทรีที่ 8 เซสชันแชร์กัน:**

| ทาง | ผล | ราคา |
|---|---|---|
| 🟢 **หมุน `TRIP_PIN`** | ค่าที่ค้างในประวัติกลายเป็น **ค่าที่ใช้ไม่ได้** → push ได้เลยโดยไม่ต้องแตะประวัติ | เปลี่ยน env + redeploy · กรอกใหม่ครั้งเดียว 2 คน |
| ❌ เขียนประวัติใหม่ | ลบค่าออกจริง | **7 commit ที่ต้องแก้อยู่กลางช่วง 16 commit** ของ 8 เซสชันที่แชร์ทรีเดียวกัน · rebase ระหว่างที่คนอื่นกำลังพิมพ์อยู่ = เสี่ยงกว่าปัญหาที่แก้ |

→ **หมุน PIN ไม่ใช่ "การกู้ความเสียหาย" (ไม่มีความเสียหาย) แต่เป็น "ทางที่ง่ายที่สุดในการปลดล็อกการ push"**

**ผลต่อข้อเสนอ §5.1.1(ง):** ยังเป็น **"ควรทำ"** ไม่ใช่ *"ต้องทำเดี๋ยวนี้เพราะรั่วแล้ว"*
เหตุผลกลับไปเป็นของเดิม (4 หลักไล่ครบใน ~50 นาที) **บวกเหตุผลใหม่ที่แข็งกว่า: มันปลดล็อกการ push**
· ⚠️ ยังต้องทำ **ก่อนออกเดินทาง** เพราะทั้ง 2 คนต้องกรอกใหม่ครั้งเดียว

**ความผิดของผม — บันทึกไว้เพราะเป็นรูปแบบเดียวกับทั้งเอกสารนี้:**
ผมเห็นสัญญาณหนึ่ง (*ค่าอยู่ใน commit*) แล้วสรุปสถานะ (*มันเป็นสาธารณะแล้ว*)
**โดยไม่ตรวจขั้นที่อยู่ระหว่างกลาง** (*commit ถูก push แล้วหรือยัง) — ทั้งที่หลักฐานอยู่ตรงหน้า:
เซสชันนี้เริ่มด้วย `git log` ที่โชว์ `99a2ff4` เป็นคอมมิตล่าสุด และ P1 พูดว่า *"ยังไม่ต้อง push"*
ทุกข้อความ · **"commit แล้ว" ≠ "เผยแพร่แล้ว" และมันจริงก็ต่อเมื่อ push**
· ผลของการพลาดแบบนี้คือ **ผู้ใช้ตัดสินใจบนข้อมูลผิด และเป็นข้อมูลผิดชนิดที่ทำให้ตกใจโดยไม่จำเป็น**
→ กติกาที่ถอดได้: **ก่อนบอกใครว่าความลับ "รั่ว" ต้องยืนยันปลายทางจากปลายทางเอง**
(`git ls-remote` ถามเซิร์ฟเวอร์ · ไม่ใช่ `origin/main` ที่เป็นแค่ cache ในเครื่อง)

**สิ่งที่ยังถูกทุกคำ และแรงขึ้นด้วยซ้ำ — เหตุผลของ secret scanning:**
commit นี้ `npm test` เขียว · `npm run lint` สะอาด · **P1 ตรวจ `git status` + `npm test` เองแล้ว
รายงานผู้ใช้ว่า "freeze อยู่ครบ"** — และคำนั้นก็ถูกด้วย: ไม่มีไฟล์โค้ดแอปถูกแตะจริง
🔴 **เขาตรวจว่ามีไฟล์อะไรเปลี่ยน ไม่ได้ตรวจว่าในไฟล์นั้นมีอะไร** — ไม่มีเครื่องมือใดในโปรเจกต์นี้
ตรวจอย่างหลังได้ตามนิยาม → ดู §10 (งานของ P6)

### 9.5 🔴 หมวดใหม่: **ทางลดที่สร้างช่องใหม่** (P1 ขอให้เพิ่มเป็นหมวด)

| # | มาตรการ | ปิดอะไร | 🔴 เปิดอะไร |
|---|---|---|---|
| 1 | **repo → private** (P1 เสนอ) | ตัดห่วงโซ่ §9.1 ที่ห่วงแรก | **เสีย GitHub secret scanning ซึ่งฟรีเฉพาะ repo public** → เสียเครื่องมือเดียวที่จะจับเรื่องแบบ §9.0 ในอนาคต · ต้องมี `gitleaks` ก่อนหรือพร้อมกัน **ไม่ใช่ตามหลัง** |

| 6 | **break-glass สำหรับเลิก fail-open** (ของผม §4.2 ขั้น 4) | ให้เข้าเว็บได้ตอน auth ล่มขณะอยู่ต่างประเทศ | ถ้าทำเป็นธง `DISABLE_AUTH=1` **จะถูกเปิดตอนตีสามแล้วไม่มีใครปิด** — ผมกันไว้แล้วด้วยการบังคับให้มีวันหมดอายุในตัว **แต่กันได้เพราะนึกถึงตอนออกแบบ ไม่ใช่เพราะมีกลไกอะไรบังคับ** |

## 11. ข้อจำกัดของรีวิวนี้

พูดให้ชัดว่าอะไรที่**ไม่ได้**ทำ เพื่อไม่ให้ใครเข้าใจว่าครอบคลุมกว่าจริง:

- **ไม่ได้ยิง Supabase จริงแม้แต่ request เดียว** — ทุกข้อสรุปมาจากไฟล์ SQL + โค้ด + `node_modules`
  ข้อที่ต้องพิสูจน์ด้วยการรันทำเครื่องหมายไว้แล้ว: **T-14** (realtime + RLS) และ **T-17/§6.1 ชั้น 1** (storage list)
- **ไม่ได้ยิง `/api/unlock` ของ production เพื่อทดสอบว่า `x-forwarded-for` ปลอมได้จริงไหม** — เป็นการส่ง
  ทราฟฟิกรูปร่างเดา-PIN ใส่เว็บของผู้ใช้ **ต้องขออนุญาตก่อน ไม่ทำเอง** · ข้อสรุปใน §5.1.1 **ไม่ขึ้นกับ
  คำตอบนั้น** เพราะช่อง "Map ต่อ instance" ไม่ต้องปลอม header เลย · ถ้าอยากรู้: ยิงพร้อม XFF ปลอม
  แล้วดูว่าโดนนับรวมกับ IP จริงไหม — **ผมทำให้ได้ถ้า P1 หรือผู้ใช้อนุญาต**
- **พฤติกรรมแคชใน §7 อ่านจากเอกสาร Next 16.3 ในเครื่อง ไม่ได้รันพิสูจน์** — `next.config.ts` วันนี้ว่างเปล่า
  ยังไม่ได้เปิด `cacheComponents` จึงไม่มีอะไรให้รันทดสอบ · อ้างไฟล์:บรรทัดของเอกสารไว้ทุกข้อเพื่อให้ตรวจซ้ำได้
  · **ถ้า P3 เปิด `cacheComponents` แล้วพฤติกรรมจริงต่างจากเอกสาร ให้ยึดของจริงและตีกลับมา**
- **ไม่ได้ตรวจ Dashboard ของ Supabase** — ค่า bucket public / auth setting / เครือข่าย ยืนยันจากโค้ดกับ
  คอมเมนต์ใน migration เท่านั้น · ถ้าใครเคยแก้ค่าใน Dashboard โดยไม่ผ่าน migration รีวิวนี้ไม่เห็น
- **ไม่ได้ตรวจ dependency ว่ามี CVE ไหม** (A06) — ต้องรัน `npm audit` ซึ่งเป็นของ P6
- **ไม่ได้รีวิว `docs/engine/architecture.md`** — P1 ยังเขียนไม่เสร็จตอนที่รีวิวนี้เขียน
  ถ้า schema สุดท้ายต่างจากที่บรีฟมา policy ในไฟล์ SQL ต้องรีวิวใหม่ทั้งชุด **ไม่ใช่แก้ทีละชื่อคอลัมน์**
- **ยังไม่มีใครรีวิว policy ชุดนี้** — ผมเขียนเพราะ P1 ออกแบบ schema จึงไม่ควรตรวจงานตัวเอง
  ด้วยเหตุผลเดียวกัน **policy ที่ผมเขียนก็ควรมีคนอื่นตรวจ** · P1 ตรวจความเข้ากันได้กับ schema ได้
  แต่ข้อที่ควรมีตาที่สามคือ §9 (trigger) เพราะเป็นส่วนที่ RLS ตรวจแทนให้ไม่ได้
  และเป็นส่วนที่ถ้าผิดจะไม่มีอะไรฟ้อง
