# `resolvePlace` — บันทึกก่อนออกแบบ (ยังไม่เริ่มทำ)

> **สถานะ: หยุดรอการตัดสินใจ · ห้ามเริ่มลงมือ** · P1 สั่งหยุด 30 ส.ค. 2026
> เนื้อหาส่วนใหญ่มาจากการไล่โค้ดของ **P3** (อ่านอย่างเดียว ไม่แตะโค้ด) · P1 เรียบเรียงและเติมส่วนตัดสินใจ
>
> 🔴 **ทำไมมีไฟล์นี้:** สรุปนี้เดิมอยู่ในข้อความข้ามเซสชัน — **ข้อความหาย ไฟล์ไม่หาย**
> (เป็นเหตุผลเดียวกับที่ P3 บอกว่า *"เหตุผลที่ใช้ปฏิเสธคำสั่ง ควรอยู่ในเคส ไม่ใช่ในแชท"*)

## 1. ทำไมเรื่องนี้ถึงโผล่ขึ้นมา

`E6-AC1` (ลดขนาดบันเดิล) ปิดครึ่งแรกไปแล้ว — `data/itinerary.ts` ออกจากบันเดิลตั้งแต่ `c7aca6d`
**ครึ่งที่เหลือคือ `data/places.ts` (`PLACES` ~71 KB) และมันไม่ใช่ปัญหาชนิดเดียวกัน**

```
ครึ่งแรก   ตารางเล็กบังเอิญอยู่ไฟล์เดียวกับของใหญ่   →  แยกไฟล์ก็จบ (งานเชิงกล)
ครึ่งหลัง   lib/resolvePlace.ts ต้องการ PLACES จริง ๆ  →  **แยกไฟล์ไม่ช่วยเลย** ต้องออกแบบใหม่
```

---

## 2. `resolvePlace` ทำอะไรวันนี้

ค้น **4 เนมสเปซตามลำดับ** แล้วคืน `Place` เต็มใบ:

| # | แหล่ง | หมายเหตุ |
|---|---|---|
| ① | `PLACES.find(id)` | คลังเกาหลีสถิตย์ 71 KB — **ตัวที่ `AC1` อยากเอาออก** |
| ② | `findTransferPoint(id)` | สนามบิน/สถานี — **อยู่นอก `PLACES` โดยตั้งใจ** (ไม่ให้โผล่ในคลังให้ผู้ใช้เลือก) |
| ③ | `hotel@{lat},{lng}` | id ฝังพิกัดในตัว · **สังเคราะห์ ไม่มีต้นทาง** |
| ④ | `customPlaces.find(id)` | มาจากฐาน · ผู้เรียกส่งเข้ามาเอง |

### 🔴 ข้อจำกัดที่ตัดสินทั้งงาน
**มันเป็น `sync` และถูกเรียกจาก 10 ไฟล์** — หลายจุดอยู่ใน `useMemo` / เส้นทาง `computeSchedule`
และ **หนึ่งจุดอยู่ฝั่งเซิร์ฟเวอร์** (`app/api/place-name/route.ts`)

> 🎯 **รูปเดียวกับ `B6` เป๊ะ: `PLACES` รับประกัน *"มีคำตอบทันที ไม่มีสถานะกำลังโหลด"* ให้ฟรี**
> ย้ายไปคลังจากฐาน = เปลี่ยน **sync → async** ซึ่ง `TEAM.md §3.4` เตือนไว้ตรง ๆ
> · **และไม่มีบรรทัดไหนในโค้ดพูดถึงการรับประกันนี้เลย** — เพราะไม่มีใครต้องเขียนมันตอนที่มันฟรี

## 3. ข่าวดี — ตัวแปลงมีอยู่แล้ว ไม่ต้องออกแบบใหม่

`hooks/useCatalogPlaces.ts` มี `toPlace(row): Place` **ครบทั้ง 11 ฟิลด์**
และคีย์ตรงกันอยู่แล้ว: **`catalog_places.legacy_slug` = พื้นที่คีย์เดียวกับ `PLACES.id`**
(API `/stops` คืน `place_id` เป็น `legacy_slug` อยู่แล้ว)

⚠️ **แต่รูปคำถามไม่ตรงกัน** — `useCatalogPlaces` โหลด **ต่อเมือง** ขณะที่ `resolvePlace` ค้น **ตาม id ข้ามทุกอย่าง**

---

## 4. สามทาง

### (ข) ให้ `/stops` ส่งข้อมูลสถานที่มาด้วย ← **P3 เชียร์ · P1 เอนตาม**
- 🎯 **รูปเดียวกับ `StopDto.event?` ที่เพิ่งทำสำเร็จ** (`1156f6f`) — ไคลเอนต์ไม่ต้องรู้จักตารางต้นทาง
- route join `catalog_places` อยู่แล้ว (`{ legacy_slug }`) → **ขยาย select เป็นงานเชิงกล**
- 🔴 **แต่ห้ามแปะรายฟิลด์ลงทุกแถว** — จุดแวะหลายแถวชี้สถานที่เดียวกันได้
  → **ส่งเป็น side-map `places: Record<slug, Place>` ในคำตอบเดียวกัน** (ทริปนี้ 62 จุดแวะ → แมปเล็กมาก)
- **ราคา:** `resolvePlace` ต้องรับแมปเข้ามา — **แตะ 10 จุดเรียก**

### (ก) provider โหลดคลังล่วงหน้า แล้ว `resolvePlace` ค้นในแมปนั้น
- รักษา `sync` ไว้ได้ **แต่ต้องรู้ว่าทริปอ้างถึงสถานที่ไหนบ้าง *ก่อน* เรนเดอร์**
  → ย้อนกลับไปปัญหาเดิม (ต้องอ่าน stops ก่อนถึงจะรู้ว่าจะโหลดอะไร)

### (ค) คงสภาพปัจจุบัน
- ใช้ได้เฉพาะทริปเกาหลี · **ตายทันทีที่มีทริปประเทศอื่นที่มีจุดแวะจากคลัง**

## 5. 🔴 สามข้อที่ต้องตัดสิน **ไม่ว่าจะเลือกทางไหน**

1. **`TRANSFER_POINTS` กับ `hotel@` ไม่ได้มาจากคลัง** — สองอันนี้อยู่ต่อแน่นอน
   → **`AC1` ไม่ได้แปลว่า `data/` ว่างเปล่า** · อย่าเขียนเกณฑ์รับที่อ่านได้แบบนั้น
2. **`app/api/place-name/route.ts` เรียก `resolvePlace` ฝั่งเซิร์ฟเวอร์** — จุดนั้น query ฐานตรงได้
   **ไม่กระทบบันเดิลเลย** → มันควรใช้เส้นทางคนละแบบกับฝั่งไคลเอนต์ **ตั้งแต่ต้น**
3. 🔴 **`Place["city"]` / `Place["category"]` เป็น union ที่ `useCatalogPlaces` `cast` ค่าจากฐานเข้าไป**
   คือคลาสบั๊กที่ทีมไล่กันทั้งวัน 29–30 ส.ค.
   → **ถ้าจะรื้อ `resolvePlace` อยู่แล้ว นี่คือจังหวะเดียวที่ถูกที่จะแก้ชนิดพร้อมกัน** ไม่ใช่แก้ทีหลัง

## 6. สิ่งที่ยังไม่มีใครตอบ

- **ใครเป็นเจ้าของ "สถานที่ของทริปนี้"** — คำถามเดียวกับที่ `§3.24` บอกว่าไม่มีด่านไหนถาม
  และเป็นคำถามที่ `E6-AC11` เพิ่งตอบให้กับ *"วัน"* ไปแล้ว
- **เกณฑ์รับควรวัดอะไร** — ถ้าวัด "ขนาดบันเดิล" อย่างเดียว จะปิดได้ด้วยการย้ายของโดยไม่ตอบข้อ ①–③
  · ดู `waiting-on-user §3.21` (*มาร์กเกอร์ต้องผูกขาด*) และ `§3.22` (*รันเกณฑ์ก่อนจด*)
