> **สถานะ: ตัดสินแล้ว 30 ส.ค. 2026 — ผ่าเป็นสองงาน · ทำ (ก) ก่อน (ข)** · ดูหัวข้อ 7 ท้ายไฟล์
> เนื้อหาส่วนใหญ่มาจากการไล่โค้ดของ **P3** (อ่านอย่างเดียว ไม่แตะโค้ด) · P1 เรียบเรียงและเติมส่วนตัดสินใจ

> (เป็นเหตุผลเดียวกับที่ P3 บอกว่า *"เหตุผลที่ใช้ปฏิเสธคำสั่ง ควรอยู่ในเคส ไม่ใช่ในแชท"*)

## 1. ทำไมเรื่องนี้ถึงโผล่ขึ้นมา

`E6-AC1` (ลดขนาดบันเดิล) ปิดครึ่งแรกไปแล้ว — `data/itinerary.ts` ออกจากบันเดิลตั้งแต่ `c7aca6d`
**ครึ่งที่เหลือคือ `data/places.ts` (`PLACES` ~71 KB) และมันไม่ใช่ปัญหาชนิดเดียวกัน**

```
ครึ่งแรก   ตารางเล็กบังเอิญอยู่ไฟล์เดียวกับของใหญ่   →  แยกไฟล์ก็จบ (งานเชิงกล)
ครึ่งหลัง   lib/resolvePlace.ts ต้องการ PLACES จริง ๆ  →  **แยกไฟล์ไม่ช่วยเลย** ต้องออกแบบใหม่
```

## 2. `resolvePlace` ทำอะไรวันนี้

ค้น **4 เนมสเปซตามลำดับ** แล้วคืน `Place` เต็มใบ:

| # | แหล่ง | หมายเหตุ |
|---|---|---|
| ① | `PLACES.find(id)` | คลังเกาหลีสถิตย์ 71 KB — **ตัวที่ `AC1` อยากเอาออก** |
| ② | `findTransferPoint(id)` | สนามบิน/สถานี — **อยู่นอก `PLACES` โดยตั้งใจ** (ไม่ให้โผล่ในคลังให้ผู้ใช้เลือก) |
| ③ | `hotel@{lat},{lng}` | id ฝังพิกัดในตัว · **สังเคราะห์ ไม่มีต้นทาง** |
| ④ | `customPlaces.find(id)` | มาจากฐาน · ผู้เรียกส่งเข้ามาเอง |

### 🔴 ข้อจำกัดที่ตัดสินทั้งงาน
**มันเป็น `sync` และถูกเรียกจาก 10 ไฟล์** — หลายจุดอยู่ใน `useMemo` / เส้นทาง `computeSchedule`
🔴 **แก้ 30 ส.ค. (P8 จับได้ · P1 ตรวจซ้ำ):** ฉบับเดิมเขียนว่า *"หนึ่งจุดอยู่ฝั่งเซิร์ฟเวอร์
(`app/api/place-name/route.ts`)"* — **เท็จ** · ไฟล์นั้นไม่มี `resolvePlace` เลยสักบรรทัด (มีแต่ในคอมเมนต์)
· ไล่จริง: ผู้เรียกทั้ง 10 ไฟล์ **เป็นฝั่งไคลเอนต์ทั้งหมด ไม่มีเส้น API สักเส้น**
· 🎯 **P3 เขียนข้อนี้ · P1 คัดลอกลงเอกสารโดยไม่ตรวจ · P8 เป็นคนแรกที่เปิดไฟล์** — ผ่านสองคนก่อนถูกจับ

> 🎯 **รูปเดียวกับ `B6` เป๊ะ: `PLACES` รับประกัน *"มีคำตอบทันที ไม่มีสถานะกำลังโหลด"* ให้ฟรี**
> ย้ายไปคลังจากฐาน = เปลี่ยน **sync → async** ซึ่ง `TEAM.md §3.4` เตือนไว้ตรง ๆ
> · **และไม่มีบรรทัดไหนในโค้ดพูดถึงการรับประกันนี้เลย** — เพราะไม่มีใครต้องเขียนมันตอนที่มันฟรี

## 3. ข่าวดี — ตัวแปลงมีอยู่แล้ว ไม่ต้องออกแบบใหม่

`hooks/useCatalogPlaces.ts` มี `toPlace(row): Place` **ครบทั้ง 11 ฟิลด์**
และคีย์ตรงกันอยู่แล้ว: **`catalog_places.legacy_slug` = พื้นที่คีย์เดียวกับ `PLACES.id`**
(API `/stops` คืน `place_id` เป็น `legacy_slug` อยู่แล้ว)

⚠️ **แต่รูปคำถามไม่ตรงกัน** — `useCatalogPlaces` โหลด **ต่อเมือง** ขณะที่ `resolvePlace` ค้น **ตาม id ข้ามทุกอย่าง**

## 4. สามทาง

### (ข) ให้ `/stops` ส่งข้อมูลสถานที่มาด้วย ← **P3 เชียร์ · P1 เอนตาม**
- 🎯 **รูปเดียวกับ `StopDto.event?` ที่เพิ่งทำสำเร็จ** (`1156f6f`) — ไคลเอนต์ไม่ต้องรู้จักตารางต้นทาง
- route join `catalog_places` อยู่แล้ว (`{ legacy_slug }`) → **ขยาย select เป็นงานเชิงกล**
- 🔴 **แต่ห้ามแปะรายฟิลด์ลงทุกแถว** — จุดแวะหลายแถวชี้สถานที่เดียวกันได้
  → **ส่งเป็น side-map `places: Record<slug, Place>` ในคำตอบเดียวกัน** (ทริปนี้ 62 จุดแวะ → แมปเล็กมาก)
- **ราคา:** `resolvePlace` ต้องรับแมปเข้ามา — **แตะ 10 จุดเรียก**

### (ก) provider โหลดคลังล่วงหน้า แล้ว `resolvePlace` ค้นในแมปนั้น
- รักษา `sync` ไว้ได้ **แต่ต้องรู้ว่าทริปอ้างถึงสถานที่ไหนบ้าง *ก่อน* เรนเดอร์**
  → ย้อนกลับไปปัญหาเดิม (ต้องอ่าน stops ก่อนถึงจะรู้ว่าจะโหลดอะไร)

### (ค) คงสภาพปัจจุบัน
- ใช้ได้เฉพาะทริปเกาหลี · **ตายทันทีที่มีทริปประเทศอื่นที่มีจุดแวะจากคลัง**

## 5. 🔴 สามข้อที่ต้องตัดสิน **ไม่ว่าจะเลือกทางไหน**

1. **`TRANSFER_POINTS` กับ `hotel@` ไม่ได้มาจากคลัง** — สองอันนี้อยู่ต่อแน่นอน
   → **`AC1` ไม่ได้แปลว่า `data/` ว่างเปล่า** · อย่าเขียนเกณฑ์รับที่อ่านได้แบบนั้น
2. ~~**`app/api/place-name/route.ts` เรียก `resolvePlace` ฝั่งเซิร์ฟเวอร์**~~ **ถอนทั้งข้อ 30 ส.ค. — เท็จ**
   **ความสัมพันธ์จริงกลับด้าน: route นั้นคือ *ตัวแก้ที่มีอยู่แล้ว* สำหรับจุดอ่อนของ `resolvePlace`**
   ```
   resolvePlace fallback  name_en ?? name_th
   → เอกสาร ตม./K-ETA มีชื่อไทยปน ("ตลาดปลาจากัลชิ" ที่ผู้ใช้เจอจริง)
   → /api/place-name จึงถูกสร้างขึ้นมาดึงชื่ออังกฤษจาก Google แทน
   ```
   · ✅ **ถอดออกจากขอบเขตงาน (ข)** — ไม่ใช่จุดเรียกที่มีอยู่จริง อย่าประดิษฐ์งาน
   · 🔴 **แต่เก็บเป็นข้อควรรู้:** ตอนรื้อ `resolvePlace` **ห้ามพา `name_en ?? name_th` กลับเข้าเส้นทางหน้า ตม.**
3. 🔴 **`Place["city"]` / `Place["category"]` เป็น union ที่ `useCatalogPlaces` `cast` ค่าจากฐานเข้าไป**
   คือคลาสบั๊กที่ทีมไล่กันทั้งวัน 29–30 ส.ค.
   → **ถ้าจะรื้อ `resolvePlace` อยู่แล้ว นี่คือจังหวะเดียวที่ถูกที่จะแก้ชนิดพร้อมกัน** ไม่ใช่แก้ทีหลัง

# 7. ✅ คำตัดสิน (P1 · 30 ส.ค. 2026) — **ผ่าเป็นสองงาน และลำดับสำคัญ**

P3 เสนอให้แก้ชนิดข้อมูล *พร้อมกับ* งานท่อ (*"จังหวะเดียวที่ถูก"*) — **ผมไม่รับ และไม่ใช่ด้วยเหตุผลเรื่องขอบเขต**

## 🔴 เหตุผลที่ต้องแยก — และทำไมต้อง *ชนิดก่อน ท่อทีหลัง*

```ts
// lib/resolvePlace.ts:52-53 วันนี้
city:     custom.city     as Place["city"],
category: custom.category as Place["category"],

// data/places.ts:29 — ชนิดปลายทาง
city: "hanoi" | "busan" | "sokcho" | "gangneung" | "seoul" | "suwon" | "bangkok" | "hcmc"
```
🎯 **`Place["city"]` เป็นยูเนียนปิดของ 8 เมือง — สถานที่ในโตเกียว *พิมพ์ไม่ได้ตามนิยาม***
· วัดแล้ว: **cast 13 จุด · จุดที่ index ด้วยค่าพวกนี้ 17 จุด**
· 🔴 **และงานท่อจะ *เพิ่ม* จุด cast เป็นจุดที่ 14** — เพราะ side-map ต้องประกอบ `Place` จากแถว `catalog_places`
  ซึ่งเป็นขอบเดียวกับที่ cast เกิดขึ้นพอดี → **ทำท่อก่อน = ทำให้ปัญหาแย่ลงหนึ่งจุดก่อนจะไปแก้**
· ✅ **ทำชนิดก่อน = ตอนทำท่อ ไม่มี cast ให้เพิ่มเลย** งานท่อกลายเป็นงานเชิงกลจริง ๆ

### 🔴 แก้ทันที — P3 ตรวจแล้วพบว่า *เหตุผลข้างบนอ่อนกว่าความจริง* (30 ส.ค. · ข้อสรุปไม่เปลี่ยน)

ผมเขียนว่า *"งานท่อจะ **เพิ่ม** จุด cast เป็นจุดที่ 14"* — **ของจริงแรงกว่านั้น**
```
hooks/useCatalogPlaces.ts:60-61   toPlace()   city: (row.citySlug ?? "") as Place["city"]
                                              category: row.category as Category
```
**จุดนั้นมีอยู่แล้ว** · งานท่อไม่ได้เพิ่มจุดที่ 14 — มันสร้าง **เส้นทางประกอบใบที่สองที่ cast แบบเดียวกัน**
```
วันนี้    catalog row → Place  ที่ toPlace()             (cast 2 จุด)
หลังท่อ   catalog row → Place  ที่ side-map ของ /stops    (cast 2 จุด แบบเดียวกัน)
```
🎯 **นั่นคือ *สองแหล่งความจริงของการแปลงเดียวกัน* ไม่ใช่ *หนึ่ง cast เพิ่ม*** — และเป็นรูปที่ทีมจ่ายราคาไปแล้ววันเดียวกันนี้ (`buildDayBridge` 4 ใบ · `E6-AC11`)
· **ผลต่อการตัดสิน:** ทำท่อก่อน = สร้างจุดที่ต้องซิงก์ **แล้วงานชนิดต้องไปแก้สองที่แทนที่จะแก้ที่เดียว**
· 📌 P3 ระบุเองว่า **ไม่ได้ไล่นับซ้ำเลข 13/17 ของผม** — เขายืนยัน *รูป* ไม่ใช่ *จำนวน*

## 📌 และมันไม่ใช่ "รื้อครั้งเดียวได้สองเรื่อง" อย่างที่ P3 มอง
สองงานนี้**แตะโค้ดคนละกอง**: งานท่อแตะ *จุดเรียก* `resolvePlace` · งานชนิดแตะ *ทุกที่ที่อ่าน `Place.city`*
→ รวมกันแล้วรีวิวไม่ได้ ไม่ใช่ประหยัดแรง

## (ก) 🔴 ทำก่อน — `Place["city"]`/`["category"]` เลิกเป็นยูเนียนปิดที่ cast มาจากฐาน

**หัวใจไม่ใช่ "เปลี่ยนชนิดเป็น `string`" — หัวใจคือ *ทุก lookup ที่ใช้ค่านั้นเป็นคีย์ ต้องมีพฤติกรรมที่นิยามไว้เมื่อค่าไม่รู้จัก***
· นั่นคือคลาสบั๊กเดียวกับที่ทีมไล่ปิดกันทั้งสัปดาห์ (*lookup คืน `undefined` เงียบ ๆ*)
· **เกณฑ์รับต้องมีเคสที่ป้อนเมืองที่ไม่รู้จักเข้าไป แล้วยืนยันพฤติกรรม — ไม่ใช่ cast ให้ผ่าน**

🔴 **ของแถมที่ต้องแก้ไปพร้อมกัน** (`lib/resolvePlace.ts:19`):
```ts
city: "seoul",  // ไม่ได้ใช้จริง — แถวที่พักไม่เคยถูกกรองตามเมือง แต่ type บังคับให้ใส่
```
**โรงแรมที่โตเกียวจะประกาศตัวว่าอยู่โซล** · คอมเมนต์บอกว่า "ไม่ได้ใช้จริง" ซึ่ง**ตรวจไม่ได้และหมดอายุได้เงียบ ๆ**

🔴 **P3 ชี้ว่ามันเป็นรูปเดียวกับที่กัดเขาวันนี้เป๊ะ** — `hotelLegs` อ่าน `noHotel` ที่ *"ไม่มีใครส่งมา"* แล้วนับวันบินเป็นคืนที่ต้องมีโรงแรม
> **ทั้งสองใบคือค่าที่ถูกใส่ไว้เพราะ type บังคับ แล้วมีคนอ่านมันจริงในภายหลัง**

**✅ เกณฑ์เพิ่มที่ P3 เสนอ และผมรับ — เป็นครึ่งที่ผมเขียนขาดไป:**
> ให้ค่านั้นเป็น **"ไม่รู้" ที่ระบบรับได้ ไม่ใช่ค่าที่ดูเหมือนคำตอบ** · ถ้า `city` ยอม `null` ได้
> โรงแรมสังเคราะห์ต้องเป็น `null` **ไม่ใช่ `"seoul"`**
>
> 🔴 **และค่าสังเคราะห์ต้อง *เดินผ่านเส้นทาง "ไม่รู้"* ด้วย — ไม่ใช่หลบด้วยการใส่ค่าที่ผ่าน type**

· 🎯 **ต่างจากเกณฑ์เดิมของผมตรงนี้:** ผมเขียนแค่ *"lookup ต้องมีพฤติกรรมเมื่อค่าไม่รู้จัก"* ซึ่ง
  **ผ่านได้โดยที่ไม่มีใครเดินเส้นทางนั้นเลย** ถ้าทุกผู้ผลิตค่ายังใส่ค่าที่ผ่าน type เหมือนเดิม
