### 3.1 ✅ **นิ่งแล้ว · ยิงพิสูจน์แล้ว** — ทิศแดงต้องยิงใน `git worktree` แยก

> 🔴 **ทิศแดงต้องยิงผ่าน *เส้นทางจริง* — และยิงใน `git worktree` แยก ไม่ใช่ทรีร่วม**
>
> ป้อนสตริงละเมิดเข้าตัวจับ พิสูจน์ว่า **ตัวจับ** ทำงาน · ไม่ได้พิสูจน์ว่า *เดินไฟล์ → อ่าน → ตัดคอมเมนต์ → จับ* ต่อกันติด
> — **ด่านที่ตัวจับดีแต่เดินไฟล์ไม่เจอ เขียวเหมือนด่านที่ผ่านทุกประการ**
>
> ```bash
> SHA=$(git rev-parse HEAD); W=<scratchpad>/probe
> git worktree add --detach "$W" "$SHA" && ln -s <ทรีจริง>/node_modules "$W/node_modules"
> cd "$W" && npx vitest run <ไฟล์ด่าน>              # ① ต้องเขียวก่อน
> printf '<ของละเมิด>' > <พาธในโซนสแกน> && ls <พาธ>   # ls = หลักฐานว่าของถูกวางจริง
> npx vitest run <ไฟล์ด่าน>                          # ② ต้องแดง และข้อความต้องระบุพาธที่วาง
> cd <ทรีจริง> && git worktree remove --force "$W" && git worktree prune
> ```
> · ⚠️ **"ต้องแดง" ไม่พอ ต้อง *แดงแล้วเรียกชื่อไฟล์ที่เราวางถูก*** — ไม่งั้นแยกไม่ออกจากด่านที่แดงด้วยเหตุอื่น
> · 🔴 **ต้องเขียวรอบแรกก่อนวางของละเมิด** — ด่านที่แดงอยู่แล้วด้วยเหตุอื่น ทำให้รอบสองไม่มีความหมาย
> · ✅ **`ln -s node_modules` พอสำหรับ `vitest`** — `cp -al` 508M เป็นราคาของ `build`/`tsc` เท่านั้น
> · 🎯 **ไม่มีขั้น "ลบไฟล์โพรบ" ให้ข้าม** — `worktree remove --force` พาไปเอง
>   **ท่าทรีร่วมมีขั้นนั้น และขั้นที่ข้ามได้จะถูกข้ามสักวัน** (รูปเดียวกับที่ `push` จาก worktree ชนะท่า `$SHA`)

### 3.4 ✅ **นิ่งแล้ว · วัดแล้ว** — `git worktree lock` แทนการห้าม `prune` (P7 เสนอ · P1 รับ · ถอนข้อเสนอเดิมของ P1)

**✅ ถ้อยคำที่เสนอลง `TEAM.md §3.3`:**
> เมื่อกาง worktree เพื่อยืนยัน/push ให้ `git worktree lock <พาธ>` **ทันทีหลังกาง** · ปลดล็อกตอนจะลบเท่านั้น
> **`git worktree prune` ไม่ต้องห้าม** — ใบที่ถูกล็อกรอดตามนิยาม · ใบที่ไม่ถูกล็อกคือใบที่เจ้าของบอกว่าทิ้งได้

🎯 **เปลี่ยนคำถามจาก *"ใบนี้ของใคร"* (git ตอบไม่ได้) เป็น *"ใบนี้ถูกล็อกไหม"* (git ตอบเอง)**
— รูปเดียวกับ *push จาก worktree* และ *`Partial<Record>`* ที่ P3 เสนอวันเดียวกัน · **สามใบในวันเดียว**

### 3.6 ⏳ **ยังโตอยู่** — ท่าโพรบที่แก้ไฟล์ในทรีร่วมแล้วคืนสภาพ (P3 เสนอ · แล้ว P3 หักมันเองในรอบถัดมา)

ท่า: ก๊อปไฟล์ไปนอกทรี → แก้ → รัน `tsc` → **คืนจากสำเนา ไม่ใช่ `git checkout`** (ซึ่งกติกาห้ามอยู่แล้ว)
🔴 **รอบสอง P3 ย่อรายชื่อไฟล์เป็นตัวแปร แล้วมันพังเงียบ:**
```bash
FILES="a.ts b.ts c.tsx"
for f in $FILES; do cp "$f" "$S/"; done     # zsh **ไม่ word-split** → $f = ทั้งสตริง → cp ล้ม
                                            # → restore() ไม่ถูกนิยาม → trap ไม่มีอะไรให้เรียก
```
· ทรีค้างสภาพโพรบ 4 ไฟล์ · **รอดเพราะบังเอิญมีสำเนาจากโพรบรอบก่อน ไม่ใช่เพราะ `trap`**
· ⚠️ **ใน `bash` โค้ดนี้ทำงานถูก** — ท่าล้มเพราะ *ความต่างของเชลล์* ไม่ใช่เพราะตรรกะผิด
· 📌 **P1 เจอกับดักเดียวกันในเซสชันเดียวกันวันนี้** (`PSQL="psql -h …"` แล้วเรียก `$PSQL` → `command not found`) — **สองครั้ง คนละคน วันเดียว เชลล์เดียวกัน**

**ถ้าจะยกเป็นท่ามาตรฐาน ต้องยกพร้อมสามข้อนี้ (P3 กำหนด):**
① **เขียนรายชื่อไฟล์เป็น literal ในลูป ห้ามใส่ตัวแปร** — ตรวจด้วยตาได้ ไม่ต้องรู้กฎ word-split ของเชลล์
② **หลัง `cp` สำรอง ให้ `ls` แล้วยืนยันจำนวนไฟล์ก่อนเริ่มแก้** — สำรองไม่สำเร็จต้องรู้ *ก่อน* แก้
③ `trap` ยังมี **แต่ห้ามพึ่งเป็นชั้นเดียว** — มันพึ่งฟังก์ชันที่อาจไม่ถูกนิยาม

### 3.20 ⏳ **ยังโตอยู่ · เกิดจริง 30 ส.ค. 2026 (P1 ทำเอง)** — สคริปต์วัดหน้าจอต้องยึด *anchor ที่พังดังได้* ไม่ใช่ตำแหน่ง

**ข้อเสนอ:** สคริปต์ที่อ่านค่าจาก DOM เพื่อใช้เป็นหลักฐาน ต้องยึดจุดยึดที่ *หาไม่เจอแล้วล้ม* —
`closest('[data-…]')` / selector ที่ระบุตัวจริง · **ห้าม `parentElement` จำนวนชั้นคงที่ · ห้าม regex lazy ยิงทั้ง `body`**
และเวลาสงสัยหน้าจอ ให้ **dump ข้อความทั้งชุดมาอ่านก่อน** แทนการ regex เอาเลขที่อยากได้ออกมาตัวเดียว

**เกิดจริง:** ผู้ใช้แจ้ง "เซฟไม่ผ่าน" · ผมวัดหน้าจอด้วยสองสคริปต์ **ผิดทั้งคู่**
```js
/ต้องจอง\s*(\d+)[\s\S]*?ซื้อหน้างาน\s*(\d+)/    // จับ "ต้องจองล่วงหน้า 1-2 สัปดาห์" ในกล่องหมายเหตุ → 4/4
let n = el; for (let i=0;i<5;i++) n = n.parentElement;   // ตกที่การ์ด Express Bus ไม่ใช่ KTX
```
→ รายงานผู้ใช้ว่า *"ฐานถูก · หน้าจอค้าง"* · **ของจริง: ฐาน `3/5` · แคช `3/5` · จอ `3/5` ตรงกันหมด · PATCH 200 ทั้ง 4 ครั้ง — ไม่มีบั๊ก**

🎯 **ทั้งสองตัวไม่ throw ไม่คืน `null` ไม่คืนค่าว่าง — คืน *ตัวเลข* และ *ข้อความไทยที่อ่านรู้เรื่อง***
โหมดล้มเหลวที่เราจับได้ทุกอันคือโหมดที่ *ไม่ให้คำตอบ* · อันนี้ให้คำตอบครบถ้วน แค่ของผิดจุด
· และผมมีสมมติฐานอยู่ก่อนแล้ว (`§3.4` เรื่อง sync→async ทำแคชทับของสด) — **เลขที่ออกมาเข้าทางพอดี จึงไม่มีอะไรสะกิด**

**ข้อจำกัดของข้อเสนอนี้ (เขียนเอง อาจฆ่ามันเอง):**
① **หน้าเว็บทริปไม่มี `data-*` ให้ยึดเลยสักจุด** — กฎนี้จึงเรียกร้องให้ไปเติม attribute ในโซน P2 ก่อนถึงจะทำตามได้
   · ถ้าไม่เติม กฎจะกลายเป็น *"พยายามระวังนะ"* ซึ่งตรวจไม่ได้ และเราปฏิเสธกฎแบบนั้นมาตลอด
② **ส่วน "ห้าม regex lazy" ตรวจด้วยตาได้ทันที** (รูปเดียวกับ *ห้ามมี `rev-parse` หลังตั้ง `SHA=`*)
   → ครึ่งนี้ยืนได้เดี่ยว ๆ แม้ครึ่งแรกจะติดข้อ ① · **ถ้าจะรับแค่ครึ่งเดียว รับครึ่งนี้**
③ ไม่ครอบเคสที่ *anchor ถูก แต่หน้ายังไม่ render เสร็จ* — นั่นคือคนละเรื่อง (เวลา ไม่ใช่ตำแหน่ง)

**🔴 ใบที่สองในชั่วโมงเดียวกัน — คนละคน คนละเครื่องมือ ข้อเดียวกัน (P3 · 30 ส.ค. 2026):**
P3 รายงานว่าแถบ 🚧 หายไป โดยอ่านจาก `get_page_text` · **เครื่องมือนั้นประกาศเองว่า `Source element: <main>`**
และแถบเรนเดอร์จาก provider ที่อยู่ **นอก `<main>`** → *มันไม่เคยอยู่ในสิ่งที่เขาดูเลยสักครั้ง*
```

```
🎯 **ทั้งคู่ไม่ได้ "วัดแล้วอ่านผิด" — ทั้งคู่ *สรุปเรื่องพื้นที่ที่การวัดไม่ครอบ*** และผลลัพธ์คือ "ไม่พบ" เหมือนกันเป๊ะ

### 3.28 ⏳ **ยังโตอยู่ · เกิดกับ 3 คนพร้อมกัน 30 ส.ค. 2026** — ไม่มีใครเช็คว่า *เงื่อนไขที่บั๊กต้องการ* มีอยู่จริงในข้อมูล

**เรื่องที่เกิด:** P2 ไล่โค้ดเจอว่า `atIndex` นับรวมแถว `event` → วาดภาพ `[E, E, S1, S2, S3]` แล้วสรุปว่าแทรกผิดตำแหน่ง
· P1 อ่านโค้ดแล้วเห็นด้วย **แก้และ commit** (`4f825fa`) · P4 ยิงเคสยืนยัน **และเขียนว่า *"ผู้ใช้เห็นแน่"***
· **ทั้งสามคนถูกเรื่องโค้ด · ไม่มีใครถามว่ารูปข้อมูลนั้นมีอยู่จริงไหม**

**วัดจริง (ฐาน dev · ทริปเกาหลี · Plan A):**
```
ทุกวันที่มีทั้งสองชนิด   event เรียง *ท้าย* จุดแวะทั้งหมด   anyEventBeforeStop = false
เพราะ rank ของ event = 'E0000V'…  ซึ่ง > '0000V'… ของจุดแวะเสมอ (ASCII '0' < 'E')
```
จำลองทุก `atIndex` → **เพื่อนบ้านซ้ายเป็นตัวเดียวกันทั้งสองทาง** → จุดแวะลงตำแหน่งเดิมในหมู่จุดแวะ
🎯 **ค่าที่ `rank` ได้ต่างกันจริง แต่ *ลำดับที่ผู้ใช้เห็น* เหมือนกันเป๊ะ — ไม่มีอาการวันนี้**

**Why นี่ถึงหลุดสามชั้น:**
- 🔴 **หลักฐานทุกชิ้นเป็นเรื่อง *โค้ด* — ไม่มีชิ้นไหนเป็นเรื่อง *ข้อมูล*** · โค้ดผิดจริง จึงตรวจกี่รอบก็ยังผิดจริง
- เคสของ P4 สร้างลิสต์ `[E,E,S1,S2,S3]` **ด้วยมือ** → พิสูจน์ว่าโค้ดจัดการรูปนั้นถูก **ไม่ได้พิสูจน์ว่ารูปนั้นเกิดขึ้น**
- ⚠️ **การมีเคสเขียวทำให้ทุกคนมั่นใจขึ้น ทั้งที่เคสไม่เคยตอบคำถามที่ยังไม่มีใครถาม**

**How to apply:**
- ก่อนเขียนว่า *"ผู้ใช้เห็น"* / *"บั๊กนี้กัดจริง"* — **ต้องมีการวัดฝั่ง *ข้อมูล* หนึ่งชิ้น** ว่ารูปที่บั๊กต้องการมีอยู่
- ✅ **ยังควรแก้อยู่** — `rank` ของ event ที่สอร์ตท้ายเสมอเป็น *คุณสมบัติของข้อมูลที่ `E7` ใส่มา ไม่มีอะไรบังคับ*
  → ตัวแก้เป็น **การกันล่วงหน้า** · **แต่ต้องเขียนว่าเป็นการกันล่วงหน้า ไม่ใช่การซ่อมของที่พัง**
- 🎯 ญาติกับ `§3.27` กลับด้าน: อันนั้นคือ *ไม่เจอของแล้วคิดว่าสะอาด* · **อันนี้คือเจอของแล้วคิดว่ามันกำลังกัดอยู่**

## 🔴 รอบสอง — P4 ค้านกลับ · **เขาถูกเรื่องหลักการ ผิดเรื่องเส้นทาง · และหลักการของเขาสำคัญกว่า**

**หลักการที่รับเต็ม ๆ:**
> **สแนปช็อตของ store ที่เปลี่ยนได้ ตอบว่า *"ตอนนี้เป็นยังไง"* — ไม่ได้ตอบว่า *"ใช้งานปกติแล้วจะเป็นยังไง"***
> · รูปที่บั๊กต้องการ **ไม่จำเป็นต้องมีอยู่ก่อน — มันถูกสร้างโดยการกระทำที่บั๊กนั้นอยู่ในเส้นทาง**
· 🎯 ญาติกับ *"เขียวที่ `<sha>`"* — อันนั้นข้าม **เวลาในประวัติ** · อันนี้ข้าม **เวลาในการใช้งาน**
· ⚠️ **ข้อนี้ทำให้การวัดของ P1 ไม่พอ ถึงจะวัดฝั่งข้อมูลแล้วก็ตาม** — วัดถูกชั้น แต่วัดที่จุดเวลาเดียว

**แต่เส้นทางที่เขาเดินสลับเวอร์ชันกลางทาง — รันจริงแล้วได้:**
```
ท่าที่แก้แล้ว   #1 rank=V   #2 rank=k   #3 rank=s    ลำดับจุดแวะถูก **ทุกครั้ง**  (event ไม่อยู่ท้ายแล้ว)
ท่าก่อนแก้      #1 rank=7   #2 rank=A   #3 rank=C    ลำดับจุดแวะถูก **ทุกครั้ง**  (event ยังอยู่ท้าย)
rankBetween('0002V', null)     = "V"     ← ท่าที่แก้แล้ว  · 'V' > 'E' → ข้าม event
rankBetween('0002V', 'E0000V') = "7"     ← ท่าก่อนแก้     · '7' < 'E' → รักษา invariant
```
🔴 **`"V"` ในก้าวแรกของ P4 เป็นผลของ *ท่าที่แก้แล้ว* แล้วเขาเอาไปประเมินก้าวสองด้วย *ท่าก่อนแก้*** — สภาพผสมที่ไม่เกิดถ้าเดินเวอร์ชันเดียวตลอด
· **เดินแยกกันคนละเวอร์ชันจนจบ ไม่มีเวอร์ชันไหนวางจุดแวะผิดลำดับเลย**

## ✅ เหตุผลที่ตัวแก้ยังควรอยู่ — และมันแข็งกว่าทั้งสองคำอธิบายก่อนหน้า
```
ท่าก่อนแก้     ถูก **โดยอาศัย** invariant "rank ของ event > rank ของจุดแวะเสมอ"  ← ไม่มี constraint ไหนบังคับ
ท่าที่แก้แล้ว  ถูก **โดยไม่ต้องอาศัย** invariant นั้นเลย
```
🎯 **ตัวแก้ไม่ได้ *ซ่อมของที่พัง* และไม่ใช่แค่ *กันล่วงหน้า* — มันถอด *การพึ่งพาสมมติฐานที่ไม่มีใครบังคับ* ออก**
· นั่นคือถ้อยคำที่ควรใช้ · และเป็นเหตุผลที่ **ไม่ต้องรู้ว่าอนาคตจะมี event แทรกกลางไหม** ถึงจะรู้ว่าควรแก้

## 🔬 รอบสาม — P4 ทำให้เงื่อนไข *ตรวจได้* และหักเคสที่ P1 เสนอทิ้ง (รันยืนยันแล้วทั้งคู่)

**P1 เสนอเคส *"บังคับ event ให้ rank แทรกกลาง แล้วยืนยันลำดับ"* → รันแล้ว *แยกแยะไม่ได้***
```
จุดแวะ 0000V · 0000X   event 0000W (กลางพอดี)   at=1
  ใหม่ = 0000W  ช่อง 1        เก่า = 0000VU  ช่อง 1        เหมือนกัน → เคสนี้เขียวทั้งสองท่า
```

**เคสที่แยกแยะได้จริง — เงื่อนไขแคบกว่าที่ทั้งสองคนคิด**
```
จุดแวะ A(0000A) M(0000M) Z(0000Z)  ·  event 0000F (rank มาก่อน M)
  at=0  ใหม่ 00004 ช่อง 0   เก่า 00004 ช่อง 0    เหมือนกัน
  at=1  ใหม่ 0000G ช่อง 1   เก่า 0000C ช่อง 1    เหมือนกัน
  at=2  ใหม่ 0000S ช่อง 2   เก่า 0000I ช่อง 1    🔴 ผิดช่อง
  at=3  ใหม่ V     ช่อง 3   เก่า 0000S ช่อง 2    🔴 ผิดช่อง
```
🎯 **ท่าเก่าเลื่อนตำแหน่งแทรกเร็วไป *เท่ากับจำนวน event ที่ rank มาก่อนตำแหน่งนั้น*** — จึงผิดเฉพาะเมื่อ `at` เลยตำแหน่งของ event

**✅ ถ้อยคำสุดท้ายที่ตรวจได้ (แทนคำว่า "กันล่วงหน้า"):**
> **ท่าเก่าถูก *ก็ต่อเมื่อ* ไม่มี event ตัวไหนมี rank มาก่อนจุดแวะเลย**
> วันนี้จริง (`'0' < 'E'` ใน `COLLATE "C"`) · **และไม่มี constraint ไหนบังคับ** → นั่นคือเหตุผลที่ตัวแก้ต้องอยู่

🔴 **บทเรียนของรอบสามเอง:** P1 เสนอเคสด้วยการ *ให้เหตุผล* ว่ามันควรแยกแยะ · P4 **รันแล้วพบว่าไม่**

· ✅ P4 **เก็บ `at=0,1` ไว้ในไฟล์เป็นเคสที่ *ประกาศว่าตัวเองแยกไม่ได้*** — กันคนหลังมาเพิ่มแล้วคิดว่าได้ความคุ้มครอง
· ✅ และ **จดความพยายามที่ล้มเหลวทั้งสามใบไว้ในหัวไฟล์** (`[E,E,S…]` ที่ไม่มีในฐาน · การสลับเวอร์ชัน · เคส `at=1`)
  → **ไม่งั้นคนถัดไปจะเดินสามทางนั้นซ้ำ และมันดูสมเหตุสมผลทั้งสามทาง**

เช้านี้ P1 อ้าง sha ที่ไม่มีอยู่จริง 2 ตัว แล้ว**ตั้งกฎเอง**ว่า:
> *"ห้ามใส่ sha ในข้อความที่ส่งใน tool block เดียวกับ commit ที่สร้างมัน"*

**รอบนี้ทำตามกฎนั้นครบ** — commit อยู่คนละ block กับข้อความ · **แล้วยังแต่ง sha อยู่ดี**
```
git commit … && echo committed          ← จบด้วยคำว่า "committed" ไม่ใช่ sha
                                          → sha ไม่เคยเข้ามาในบริบทเลยสักครั้ง
```
🎯 **กฎเดิมคุม *จังหวะ* (คนละ block) · ความล้มเหลวจริงอยู่ที่ *ความมีอยู่* (ไม่เคยถูกพิมพ์)**
· ⚠️ **และการทำตามกฎเดิมได้ครบ ให้ความมั่นใจผิด ๆ** — รู้สึกว่าปลอดภัยแล้วเพราะไม่ได้ละเมิดข้อห้าม

**How to apply:**
- `git commit … && git log --oneline -1` **ทุกครั้ง** — ตรวจด้วยตาได้ว่าคำสั่งจบด้วยอะไร (รูปเดียวกับ *ห้ามมี `rev-parse` หลังตั้ง `SHA=`*)
- 🔴 **หลักทั่วไปที่กว้างกว่า sha:** *ตัวระบุที่ไม่เคยปรากฏในผลลัพธ์ของเครื่องมือ ห้ามเขียน* — ครอบ sha · ชื่อไฟล์ · slug · เลขบรรทัด
- ✅ **ฝั่งผู้รับก็มีท่าที่ถูก และ P8 ใช้จริงรอบนี้:** หา sha ไม่เจอ → **ยึดเนื้อไฟล์แทน แล้วรายงานว่าหาไม่เจอ**
  · **ไม่หยุดงาน และไม่เชื่อ sha** — ถ้าเขาเงียบ ผมจะไม่มีวันรู้ว่าตัวเองแต่ง

### 3.30 ⏳ **ยังโตอยู่ · P3 เจอกับตัว 30 ส.ค. 2026** — เครื่องมือวัดที่ **สร้างสิ่งที่มันกำลังวัด**

```js
indexedDB.open('plan-korea:v1')   // ← สร้างฐานถ้ายังไม่มี
```
P3 โพรบว่า "แอปเคยเขียนแคชไหม" ด้วย `open()` → ได้ `NotFoundError: object store 'kv' was not found`
**ซึ่งอ่านเหมือน *"แอปไม่เคยเขียนแคชเลย"*** · ของจริงคือ ***"โปรไฟล์นี้ไม่มีแคช และตอนนี้มีฐานเปล่าที่โพรบสร้างเอง"***
· ✅ เขาลบทิ้งแล้วและยืนยัน `databases()` กลับมาเหลือใบเดียว

🎯 **การวัดเปลี่ยนสิ่งที่ถูกวัด — และผลลัพธ์ยัง *อ่านได้* เหมือนคำตอบปกติ**
· ต่างจาก `§3.20`/`§3.23` (*วัดในขอบเขตที่ไม่ครอบ*) — **อันนั้นมองไม่เห็นของ · อันนี้สร้างของขึ้นมาใหม่แล้วรายงานว่าไม่มี**

**How to apply:**
- **อ่านก่อนเปิดเสมอ:** `await indexedDB.databases()` (อ่านอย่างเดียว) → `open()` เฉพาะเมื่อชื่อโผล่ในรายการ
- 🔴 **หลักทั่วไป: ก่อนใช้ API ในการวัด ถามว่ามันมี side effect ไหม** — `open`/`create`/`ensure`/`getOrCreate`
  ตระกูลนี้ **ออกแบบมาให้สร้าง** · ใช้วัดไม่ได้ตามนิยาม
- ⚠️ และถ้าเผลอสร้างไปแล้ว **ต้องลบและยืนยันว่าลบแล้ว** ไม่งั้นการวัดครั้งถัดไปจะเจอของที่ตัวเองทิ้งไว้

### 3.31 ⏳ **ยังโตอยู่ · P1 ทำ · P3 หักด้วยการวัด · 30 ส.ค. 2026** — อนุมานโหมดล้มเหลวจาก *การมีคำขอเน็ต* โดยไม่อ่าน *กิ่งที่มันล้ม*

**P1 เขียนว่า:** *"ด่านยิงเน็ตเอง → ออฟไลน์ล้ม → **ตอบผิดฝั่ง** → หน้าขึ้น 'ยังแสดงไม่ได้' ทั้งที่ข้อมูลอยู่ครบ"*
**ของจริง** (`hooks/useTripDaysGate.ts:44-53`):
```ts
if (!res.ok) { setState("ready"); return; }   // เช็คไม่สำเร็จ → fail-open
} catch { setState("ready"); }                // เน็ตหลุด    → fail-open
```
🎯 **ออฟไลน์มันตอบ `ready` — ไม่บล็อกอะไรเลย · ทิศตรงข้ามกับที่ P1 เขียน**

**Why:** P1 เห็น `fetch(` ในไฟล์ที่ชื่อว่า *gate* แล้ว**เติมโหมดล้มเหลวที่สมเหตุสมผลที่สุดเข้าไปเอง** (ด่าน + ล้ม = บล็อก)
· 🔴 **ไม่ได้เดาว่ามันทำอะไร — เดาว่ามัน *ล้มยังไง* ซึ่งเป็นคนละบรรทัดกับที่อ่าน**
· ⚠️ และข้อสรุปนั้น**อธิบายอาการที่กำลังหาสาเหตุอยู่พอดี** → ยิ่งน่าเชื่อ · ตระกูลเดียวกับ `§3.14` (*แดงที่ชี้ผิดทาง แพงกว่าไม่แดง เมื่อมาพร้อมคำอธิบายที่น่าเชื่อ*)

**How to apply:**
- **จะอ้างโหมดล้มเหลว ต้องอ่านกิ่ง `catch`/`!ok` ก่อนเสมอ** — `fail-open` กับ `fail-closed` อยู่บรรทัดเดียวกันเสมอ ไม่ต้องเดา
- 🔴 **และเช็คว่ามันมีผู้เรียกไหมก่อนอ้างว่ามันกระทบอะไร** — `useLegacyDayPlanGate` ที่ P1 อ้างว่าเป็นสาเหตุ **มี 0 call site** (ตายไปกับ `B6`) · **ด่านที่ไม่มีใครเรียก กระทบอะไรไม่ได้ตามนิยาม**
