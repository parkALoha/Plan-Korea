## 1. native คุ้มกว่า PWA ที่มีอยู่ตรงไหน

**คำตอบตรงๆ ก่อน: สำหรับทริปเกาหลี 11 วันที่กำลังจะบิน — ไม่คุ้มเลย ไม่มีข้อไหนคุ้ม**
PWA ที่มีอยู่ผ่านสนามจริงแล้ว (ผู้ใช้ทดสอบ airplane mode 13 ส.ค. 2026) และ `public/sw.js` 124 บรรทัด
แก้โจทย์ "อุโมงค์รถไฟใต้ดิน + ซอรัคซาน" ได้ครบตามที่ `PLAN.md §1` ตั้งไว้ · **ห้ามเอา native มาแทนของนี้**

สำหรับ**แพลตฟอร์ม**มีอยู่ 4 ข้อที่ผมยืนยันว่าเว็บทำไม่ได้จริง เรียงตามค่าที่ได้จริง:

### 1.1 notification ที่ยิงได้ตอน "ไม่มีเน็ต" — ข้อเดียวที่คุ้มที่สุด

นี่คือข้อที่แข็งที่สุดและเป็นข้อที่ทำให้ผมเปลี่ยนใจว่า native มีค่าจริง

Web Push **ต้องวิ่งผ่านเซิร์ฟเวอร์เสมอ** — เซิร์ฟเวอร์ยิงไป push service ของ Apple/Google แล้วส่งต่อลงเครื่อง
ถ้าเครื่องไม่มีเน็ต **notification ไม่มา** และมาช้าตอนเน็ตกลับ (บางเคสไม่มาเลยถ้าคิวหมดอายุ)
ส่วนเว็บ**ไม่มี API สำหรับตั้งเวลาแจ้งเตือนไว้ในเครื่อง** — Notification Triggers ไม่เคยออกจากสถานะทดลอง

แล้วดูว่าโจทย์จริงของแอปนี้อยู่ตรงไหน: `PLAN.md §1` บอกเองว่าจุดที่เน็ตหลุดคือ**อุโมงค์รถไฟใต้ดินโซล/ปูซาน
และเขาซอรัคซาน** — ซึ่งเป็น**นาทีเดียวกัน**กับที่ต้องเตือน "ถึงเวลาออกจากที่นี่แล้วถ้าจะทันเครื่อง"
→ **Web Push จะเงียบพอดีในวินาทีที่มันมีค่าที่สุด** นี่ไม่ใช่ข้อจำกัดทางทฤษฎี มันคือเคสหลักของแอป

Native ตั้ง **local notification** ไว้ในเครื่องล่วงหน้าได้ OS ยิงเองตามเวลา **ไม่ต้องมีเน็ต ไม่ต้องมีเซิร์ฟเวอร์**
และตรรกะเวลาที่ต้องใช้**มีอยู่แล้วครบ ไม่ต้องเขียนใหม่**:
- `lib/departureAdvice.ts:42-76` `computeDepartureAdvice()` คืน `shouldLeaveBy` — เวลาที่ควรออกให้ทันเครื่อง
  (คำนวณย้อนจากเวลาบิน − เผื่อเช็คอิน − เวลาเดินทางจริง − เผื่อความเสี่ยง 30 นาที)
- `lib/bookingDeadline.ts:18-23` `bookByDate()` คืนวันครบกำหนดจองตั๋ว
- ทั้งสองเป็น pure function มีเทสต์คุม (`lib/__tests__/departureAdvice.test.ts`, `bookingDeadline.test.ts`)

**นี่คือของที่ย้ายลง native แล้วได้ค่าเพิ่มทันทีโดยไม่ต้องคิดตรรกะใหม่เลย**

> ⚠️ ข้อควรระวังที่ต้องออกแบบด้วย: local notification ถูก "นัด" ไว้กับสถานะแผน ณ ตอนนัด
> ถ้าอีกคนแก้แผนหลังจากนั้น การเตือนจะผิด → ต้อง **ยกเลิกและนัดใหม่ทั้งชุดทุกครั้งที่ข้อมูลวันนั้นเปลี่ยน**
> (ทั้งจาก realtime และจากการแก้ในเครื่อง) · iOS มีเพดาน ~64 การนัดที่รอยิงต่อแอป → นัดล่วงหน้าแค่ 48 ชม.
> ไม่ใช่ทั้งทริป แล้ว re-schedule ตอนเปิดแอป

### 1.2 พื้นที่เก็บข้อมูลในเครื่อง — เพดาน 5 MB คือกำแพงจริงของแพลตฟอร์ม

ทุกอย่างที่ดูออฟไลน์ได้ตอนนี้อยู่ใน **localStorage** (`lib/localCache.ts:10` prefix `trip-cache:` ·
8 hooks ใช้อยู่: `useStops` `useBookings` `useHotels` `useCustomPlaces` `useDaySettings` `usePlans`
`usePlaceNotes` `useOvernightOverrides`) และ `lib/localCache.ts:23-30` **กลืน quota error เงียบๆ โดยตั้งใจ**

ทริปเดียว 11 วันอยู่ในโควตา ~5 MB สบาย แต่แพลตฟอร์มที่มีหลายทริป + ตั๋ว PDF + รูปหน้างาน
(`trip_stops.photo_url`, `bookings.file_url`) **ชนเพดานแน่นอน** และเมื่อชน โค้ดนี้จะเงียบ =
เปิดแอปตอนไม่มีเน็ตแล้วข้อมูลหายไปดื้อๆ โดยไม่มีใครรู้ว่าทำไม

Native ใช้ **SQLite + ไฟล์ในเครื่อง** ไม่มีโควตาแบบนั้น เก็บตั๋ว/รูปออฟไลน์ได้จริง
และได้ index/query ที่ localStorage (ซึ่งเป็น key→string ล้วน) ให้ไม่ได้ — ซึ่งจำเป็นพอดีสำหรับ §3

### 1.3 รับไฟล์ตั๋วจาก share sheet

ท่าที่เกิดจริง: ตั๋ว KTX มาทางอีเมล/KakaoTalk → อยากกด "แชร์ → แพลนเที่ยว" แล้วมันเด้งเข้าโมดัลตั๋วเลย

"จุดถัดไป · ออกกี่โมง · เหลือกี่นาที" อยู่บนหน้าล็อกโดยไม่ต้องปลดล็อกเครื่อง — ตรงกับหน้า `/today` เป๊ะ

### 2.2 monorepo หรือแยก repo

**เสนอ: monorepo** ด้วย npm workspaces (มีอยู่ใน npm แล้ว ไม่ต้องเพิ่มเครื่องมือ)

```
plan-korea/
├── apps/
│   ├── web/        ← ของเดิมทั้งดุ้น ย้ายมาแบบไม่แก้อะไร
│   └── mobile/     ← Expo
└── packages/
    ├── core/       ← 26 ไฟล์ pure + เทสต์ 13 ไฟล์ ย้ายมาทั้งก้อน
    └── data/       ← DAL ของ E3 + type จาก lib/supabase.ts:15-178
```

เหตุผลที่ต้องเป็น monorepo ไม่ใช่แยก repo: **`packages/core` คือกฎการคำนวณเวลาของทริป
ถ้าเว็บกับมือถือคำนวณเวลาไม่ตรงกันแม้แต่นาทีเดียว ผู้ใช้ 2 คนจะเห็นแผนคนละอย่างและเชื่อแอปไม่ได้อีกเลย**
แยก repo แล้ว sync ด้วยมือ = เรื่องนี้เกิดแน่นอน แค่เรื่องเวลา

⚠️ **ความเสี่ยงที่ต้องบอกล่วงหน้า:** การย้าย `plan-korea/` → `apps/web/` แตะทุก path ในโปรเจกต์

## 3. Offline data sync — จุดตัดสินของงานนี้

### 3.1 ตอบคำถามที่ P1 ถามตรงๆ ก่อน

> "2 คนแก้ลำดับจุดแวะวันเดียวกันพร้อมกันตอนออฟไลน์ แล้วออนไลน์พร้อมกัน ผลลัพธ์คืออะไร"

**ถ้าเอาโมเดลปัจจุบันไปใช้ตรงๆ: ผลลัพธ์คือลำดับที่ไม่ใช่ของใครทั้งคู่ และ 2 เครื่องอาจเห็นไม่ตรงกันถาวร**

ดู `hooks/useStops.ts:402-422` — `reorderStops()` เขียน `order_index = i` ทับ **ทุกแถวทั้งวัน**
เป็นเลขหนาแน่น 0..n-1 ทีละแถวแยกคำขอ (`Promise.all` ของ `.update().eq("id", …)`)

สมมติวันหนึ่งมี 4 จุด `[A,B,C,D]`
- คนที่ 1 ออฟไลน์ ลากเป็น `[B,A,C,D]` → คิวไว้: A=1 B=0 C=2 D=3
- คนที่ 2 ออฟไลน์ ลากเป็น `[A,B,D,C]` → คิวไว้: A=0 B=1 C=3 D=2
- ทั้งคู่ออนไลน์ คำขอ 8 อันวิ่งไปปนกัน **ไม่มีใครรับประกันลำดับการมาถึงต่อแถว**

ผลที่เป็นไปได้จริง: `A=1 B=1 C=3 D=3` — **เลขซ้ำกัน** จากนั้น `sortStops` (`hooks/useStops.ts:13-17`)
เรียงด้วย `a.order_index - b.order_index` ล้วน **ไม่มี tie-break** → `Array.sort` ตัดสินคู่ที่เท่ากัน
ตามลำดับที่ข้อมูลเข้ามา ซึ่ง**ต่างกันได้ระหว่าง 2 เครื่อง** = คนละลำดับถาวรจนกว่าจะมีคนลากใหม่

นี่ไม่ใช่ทฤษฎี — มันคือ **บั๊ก 8.1 ที่เคยเกิดแล้วและถูกแก้ไปแล้ว** (`hooks/useStops.ts:424-427`
เขียนบันทึกไว้เอง: "ทำให้ sortStops ตัดสินลำดับไม่ได้ = 2 เครื่องเห็นลำดับไม่ตรงกัน")
ตอนนี้หน้าต่างความเสี่ยงคือหลัก**มิลลิวินาที** (2 คนต้องลากพร้อมกันเป๊ะ) · **offline editing จะขยายหน้าต่างนั้นเป็นหลักชั่วโมง**

> **นี่คือเหตุผลที่ `PLAN.md §1` ตัด offline editing ทิ้ง และเหตุผลนั้นถูกต้อง 100% บนโมเดลข้อมูลปัจจุบัน**

### 3.2 เหตุผลใหม่ที่ผมขอแย้ง

ผมไม่ได้แย้งว่า "conflict resolution ไม่ยาก" — มันยากจริง
ผมแย้งว่า **ความยากทั้งกองนั้นมาจากดีไซน์ข้อเดียว คือการที่ลำดับเป็น integer หนาแน่น**
และเปลี่ยนข้อเดียวนั้นทำให้ทั้งกองหายไป ไม่ใช่เบาลง

**เปลี่ยนอะไร:** `order_index integer` → **rank key เป็นสตริงเรียงได้ (fractional / lexicographic rank)**
เช่น `"a0"` `"a1"` `"a0V"` — แทรกระหว่าง 2 ค่าได้เสมอโดยไม่ต้องแตะแถวอื่น

**ได้อะไรกลับมา — นี่คือทั้งหมดของข้อโต้แย้ง:**

| | `order_index` integer (วันนี้) | rank key |
|---|---|---|
| ลากจุดแวะ 1 จุด | เขียน **ทุกแถวทั้งวัน** (`reorderStops` :402-422) | เขียน **แถวเดียว** |
| แทรกจุดกลางวัน | ต้อง `shiftForInsert` ดันทุกแถวหลังจากนั้น (`:142-155`) | เขียนแถวเดียว ไม่แตะใคร |
| 2 คนลากคนละจุดพร้อมกัน | เขียนทับกันทั้งวัน → พังตาม 3.1 | **คนละแถว = ไม่ชนกันเลย ทั้งคู่ได้ผลที่ตั้งใจ** |
| 2 คนลาก **จุดเดียวกัน** | พังแบบเดาไม่ได้ | ชนแถวเดียว → LWW ตัดสิน ผลลัพธ์เดียวกันทั้ง 2 เครื่องแน่นอน |
| ต้องมี CRDT ไหม | — | **ไม่ต้อง** |

พอ "การลากจัดลำดับ" กลายเป็นการเขียนแถวเดียว **ทุก operation ในแอปนี้ก็กลายเป็นการเขียนแถวเดียวเหมือนกันหมด**
(เพิ่ม/ลบจุดแวะ · แก้โน้ต · แก้ dwell · ติ๊กมาถึง · ติ๊ก checklist · แก้ตั๋ว)
→ **conflict resolution ที่เหลือคือ per-field LWW ธรรมดา ไม่ใช่ "ปัญหาทั้งกอง" อีกต่อไป**
CRDT เต็มรูป (RGA/Yjs) **ไม่จำเป็นและผมไม่เสนอ** — มันแก้ปัญหา collaborative text editing ซึ่งแอปนี้ไม่มี

**และของอีก 2 อย่างที่แอปนี้มีอยู่แล้วโดยบังเอิญ ซึ่งเป็นเงื่อนไขที่ขาดไม่ได้ของ offline sync:**
1. **id สร้างฝั่ง client อยู่แล้ว** — `hooks/useStops.ts:9-11` `makeStopId()` = `stop-` + random + timestamp
   → **สร้างแถวใหม่ตอนออฟไลน์ได้เลย ไม่ต้องรอ id จากเซิร์ฟเวอร์ ไม่มีทางชนกัน**
   (ปกตินี่คือของที่ต้องรื้อ schema ทั้งระบบเพื่อให้ได้มา — ที่นี่มีอยู่แล้ว)
2. **optimistic write เป็นค่าเริ่มต้นทุกจุดอยู่แล้ว** — ทุก mutation ใน 10 hooks อัปเดต state ก่อนเขียน DB เสมอ
   → UI ไม่ต้องแก้เลยเพื่อรองรับออฟไลน์ มัน "รู้สึกออฟไลน์" อยู่แล้ว ต่างแค่ปลายทางที่เขียนลง

### 3.3 ข้อเสนอ — แบ่ง 2 ระยะ ตัดสินแยกกัน

#### E8a — offline อ่านอย่างเดียว (ทำแน่นอน ความเสี่ยงต่ำ)

ย้ายที่เก็บจาก localStorage → SQLite ในเครื่อง เพราะเหตุผล §1.2

- 1 ตารางต่อ 1 entity สะท้อน schema ใหม่ของ E2 ตรงๆ + `synced_at`
- **invalidate:** ไม่ใช้ TTL · ใช้ท่าเดียวกับที่เว็บใช้อยู่แล้วและพิสูจน์แล้วว่าเวิร์ก —
  hydrate จากเครื่องทันที → fetch ของสด → ทับ (`hooks/useStops.ts:58-72`)
  ต่างกันแค่ต้องเพิ่ม **full refetch ตอนกลับ foreground** (websocket ตายไปแล้วตอน background — §2.3)
- ตั๋ว/รูปโหลดเก็บเป็นไฟล์จริงในเครื่อง ไม่ใช่ base64 ใน DB

#### E8b — offline editing (ทำต่อเมื่อเงื่อนไขครบ)

🔴 **เงื่อนไขที่ขาดข้อใดข้อหนึ่งแล้วยกเลิกทั้งหมด:**
1. **E2 ต้องส่ง rank key ไม่ใช่ integer** — ถ้าไม่ได้ ให้จบที่ E8a และปิดเรื่องนี้ถาวร
2. ทุกตารางต้องมี `updated_at` ที่**เซิร์ฟเวอร์เป็นคนเขียน** ไม่ใช่ client (ปัจจุบันทุก mutation ส่ง
   `new Date().toISOString()` จากเครื่องผู้ใช้ — เห็นได้ทั้ง 20 จุดใน `hooks/useStops.ts`)
   **นาฬิกาเครื่องที่ตั้งผิดจะชนะ LWW ตลอดกาลอย่างเงียบๆ** และเคสนี้เป็นไปได้จริงพอดี เพราะ
   `lib/localDate.ts:12-15` บันทึกไว้เองว่าเจอมือถือที่ตั้งเวลาไว้ผิด timezone ระหว่างทริป
3. ทุกตารางต้องมี **soft delete (`deleted_at`)** ไม่ใช่ `DELETE` จริง (เหตุผลในตารางล่าง)

**โมเดล:** op log ในเครื่อง (append-only) + per-field LWW ตอน merge

- ทุก mutation ตอนออฟไลน์ = 1 แถวใน `pending_ops` (entity, id, field, value, hlc)
- ใช้ **HLC (hybrid logical clock)** ไม่ใช่ wall clock ล้วน: `(server_time_ล่าสุดที่เห็น, counter, device_id)`
  → เครื่องที่นาฬิกาเพี้ยนไม่ชนะฟรี และตัดสินได้แน่นอนเหมือนกันทุกเครื่อง
- merge ตอนออนไลน์: ส่ง op ตามลำดับ → เซิร์ฟเวอร์รับเฉพาะ op ที่ hlc ใหม่กว่าค่าปัจจุบัน**ของฟิลด์นั้น**
- **per-field ไม่ใช่ per-row** — A แก้โน้ต B แก้เวลาที่อยู่ ของจุดเดียวกัน → **ได้ทั้งคู่** ไม่มีใครเสีย

**ตารางผลลัพธ์ที่ต้องเป็นจริง (ใช้เป็น acceptance criteria ส่งให้ P8):**

| เคส | ผลลัพธ์ |
|---|---|
| A ลากจุด X, B ลากจุด Y (วันเดียวกัน) | ✅ ได้ทั้งคู่ คนละแถว ไม่ชน |
| A กับ B ลาก **จุดเดียวกัน** | HLC ใหม่กว่าชนะ · 2 เครื่องเห็นตรงกันแน่นอน · คนที่แพ้เห็น banner "ลำดับที่คุณจัดไว้ถูกทับโดย <ชื่อ>" + ปุ่มเลิกทำจาก op log · 🔴 **AC ข้อนี้สคีมารองรับไม่ได้จนกว่าจะมี `updated_by_user` — ดู §11.4** |
| A กับ B แทรกจุดใหม่ตำแหน่งเดียวกัน | ✅ **ได้ทั้ง 2 จุด** เรียงกันตาม `(rank, id)` — สำหรับแอปวางแผนทริป "เก็บไว้ทั้งคู่" คือคำตอบที่ถูก ไม่ใช่ทิ้งอันหนึ่ง |
| A ลบจุด · B แก้โน้ตจุดนั้น | soft delete: `deleted_at` เป็นฟิลด์หนึ่ง → LWW ตัดสิน · ถ้า B แก้ทีหลัง จุดกลับมาพร้อมโน้ต **ซึ่งกู้คืนได้** · ถ้าเป็น hard delete จะได้แถวผี insert กลับมาไม่มีที่มา = **นี่คือเหตุผลที่ต้องมีเงื่อนไข 3** · 🔴 **ข้อยกเว้น: `trip_hotels` ฟื้นคืนไม่ได้เสมอไป เพราะ exclusion constraint ของ `D51` — ดู §11.7** |
| A แก้ตอนออฟไลน์ 6 ชม. · B แก้ออนไลน์ตลอด | B ชนะเกือบทุกฟิลด์ (HLC ใหม่กว่า) — **ถูกต้องตามที่ควรเป็น** คนที่เห็นข้อมูลสดกว่าควรชนะ |
| วันนั้นถูกล็อก (`is_locked`, `TripDaySettings:177`) | ปฏิเสธ op ตั้งแต่ในเครื่อง ไม่ต้องรอเซิร์ฟเวอร์ |

**เพดานที่ต้องยอมรับและเขียนลงสเปกให้ชัด:** LWW **ทำข้อมูลหายได้** เมื่อ 2 คนแก้ฟิลด์เดียวกัน
ไม่มีทางเลี่ยง (CRDT ก็แค่เลือกให้แทน) · สิ่งที่ทำได้คือ **ไม่ให้หายเงียบ** — op log เก็บของที่แพ้ไว้
แล้วบอกผู้ใช้พร้อมปุ่มเลิกทำ · ถ้าทีมรับข้อนี้ไม่ได้ ก็ต้องจบที่ E8a **ซึ่งเป็นคำตอบที่ใช้ได้เหมือนกัน**

### 3.4 rebalance ของ rank key — ตอบข้อที่ P1 เติมมาใน D6

> P1 เติมมา 2 ข้อ: ① แทรกซ้ำที่เดิมทำให้คีย์ยาวขึ้นเรื่อยๆ ต้องมี rebalance ② แทรกพร้อมกันตำแหน่งเดียวกัน
> ลำดับสลับกันได้ (เขารับได้แล้วเพราะไม่ใช่ข้อมูลสูญหาย)
>
> **ข้อ ② ตอบสั้น:** ยืนยันว่ารับได้ และเพิ่มให้อีกชั้นว่า tie-break ต้องเป็น **`(rank, id)` ไม่ใช่ `rank` เดี่ยว**
> ถ้ามีแค่ `rank` แล้วบังเอิญได้คีย์เท่ากัน จะกลับไปเป็นบั๊ก 8.1 รูปแบบเดิมทันที (2 เครื่องเรียงไม่ตรงกัน)
> มี `id` ต่อท้าย → ลำดับอาจไม่ใช่ที่ใครตั้งใจ **แต่เหมือนกันทุกเครื่องเสมอ** ซึ่งเป็นคุณสมบัติที่ต้องการจริงๆ
>
> **ข้อ ① ยาวกว่านั้น** — และตอนไล่ดูผมพบว่ามันไม่ใช่แค่ปัญหาความยาวคีย์อย่างที่ดูตอนแรก

#### rebalance คือ operation ที่ย้อนกลับไปทำสิ่งที่ rank key เพิ่งกำจัดทิ้ง

rebalance = เขียน rank ใหม่ **ทุกแถวของวันนั้น** ซึ่งคือ `reorderStops` แบบเดิมเป๊ะ
ตอนออนไลน์ล้วนไม่มีปัญหา (ทำใน transaction เดียว) แต่ตอนมี offline editing มันสร้างเคสนี้:

1. เครื่อง A ออฟไลน์ ลากจุด X ไปไว้ระหว่าง P กับ Q → คำนวณได้ `rank = "a0V"` เก็บไว้ใน op log
2. ระหว่างนั้นเครื่อง B ออนไลน์ แทรกจุดรัวๆ จนคีย์ยาวเกินเกณฑ์ → **เซิร์ฟเวอร์ rebalance วันนั้นทั้งวัน**
   ตอนนี้ P กับ Q ไม่ได้อยู่แถว `"a0V"` อีกแล้ว
3. A กลับมาออนไลน์ ส่ง op "ตั้ง rank ของ X = `a0V`" → **X ไปโผล่ตำแหน่งที่ไม่มีความหมายอะไรเลย**

ไม่ใช่ข้อมูลหาย แต่เป็น **"จุดแวะเด้งไปอยู่มั่วๆ โดยไม่มีใครสั่ง"** ซึ่งผู้ใช้อ่านว่าแอปพัง

#### ทางแก้: op ของการเรียงลำดับต้องเป็น "ระหว่างใคร" ไม่ใช่ "ค่าอะไร"

**เก็บ op เป็น `{stop_id, prev_id, next_id}` ไม่ใช่ `{stop_id, rank: "a0V"}`**
แล้วให้ฝั่งรับ**คำนวณ rank ใหม่จากเพื่อนบ้าน ณ เวลาที่ merge** ไม่ใช่ใช้ค่าที่เครื่องคำนวณไว้ตอนออฟไลน์

ท่านี้แก้ทั้ง 3 ปัญหาพร้อมกันด้วยกลไกเดียว:
- **rebalance ระหว่างทาง** — เพื่อนบ้านยังเป็นแถวเดิม แค่ rank เปลี่ยน → คำนวณใหม่ได้ผลถูกต้องเสมอ
- **มีคนแทรกจุดใหม่คั่นระหว่างทาง** — X ยังไปอยู่ "หลัง P" ตามที่ผู้ใช้ตั้งใจ (จุดใหม่ไปอยู่ถัดไป)
  ซึ่งตรงกับเจตนามากกว่าการยึดตัวเลข
- **rank ยาวผิดปกติจาก op เก่า** — ไม่มีทางเกิด เพราะไม่เคยเอาค่าที่คำนวณตอนออฟไลน์มาใช้จริง

**เคสที่ต้องมีกฎรองรับ: เพื่อนบ้านถูกลบไปแล้วตอน merge**
→ ไล่ออกจากตำแหน่งนั้นทีละขั้นตาม snapshot ที่เครื่อง A มีตอนลาก จนเจอแถวที่ยังอยู่จริง
(soft delete ตามเงื่อนไข 3 ช่วยตรงนี้พอดี — แถวที่ถูกลบยังอ่านตำแหน่งเดิมได้ ไม่ได้หายไปเฉยๆ)
→ ถ้าไม่เหลือเลย = ทั้งวันถูกล้าง → ต่อท้ายวันแล้วแจ้งผู้ใช้ ไม่ใช่เงียบ

⚠️ **ผลข้างเคียงที่ต้องยอมรับ:** merge ของ op เรียงลำดับ **ต้องทำฝั่งเซิร์ฟเวอร์ใน transaction**
ไม่ใช่ยิง `update` ตรงจาก client เหมือนวันนี้ — แต่ E3 ทำ DAL/Server Action อยู่แล้ว จึงไม่ใช่งานเพิ่ม
**ตราบใดที่ E3 ยังทำตามแผน** · ถ้า E3 เปลี่ยนใจให้ client เขียนตรง ข้อนี้พังทันที ต้องรู้ล่วงหน้า

#### เกณฑ์ rebalance ที่เสนอ

| หัวข้อ | ค่าที่เสนอ | เหตุผล |
|---|---|---|
| ตัวอักษรที่ใช้ | base-62 `0-9A-Za-z` | แบ่งครึ่งได้ 62 ทางต่อ 1 ตัวอักษร คีย์โตช้ากว่า base-36 มาก |
| เกณฑ์กระตุ้น | คีย์ใหม่ยาวเกิน **20 ตัวอักษร** | worst case คือแทรกซ้ำที่เดิม ≈ +1 ตัวอักษร/ครั้ง · วันหนึ่งมีจุดแวะ 3-12 จุด การลากซ้ำจุดเดิม 20 ครั้ง**ในตำแหน่งเดียวกันเป๊ะ**คือพฤติกรรมที่แทบไม่เกิด → เกณฑ์นี้แปลว่าปกติ**ไม่ rebalance เลยตลอดอายุทริป** |
| ขอบเขต | 🔴 **แก้แล้วที่ §11.6 — ต้องเป็น `(day_id, plan_id)` ไม่ใช่ `day_id` เดี่ยว** (เขียนข้อนี้ตอนยังไม่รู้ `D36`) | ไม่ใช่ทั้งทริป — จำกัดจำนวนแถวที่เขียนและจำกัดความเสียหายถ้าพลาด |
| จังหวะ | ใน transaction เดียวกับ write ที่กระตุ้นมัน | async/cron จะได้สภาวะที่บางแถว rebalance แล้วบางแถวยัง |
| ค่าเริ่มต้นหลัง rebalance | เว้นช่วงเท่าๆ กัน คีย์สั้นสุด | ให้ที่ว่างแทรกรอบหน้ามากที่สุด |

**ไม่ต้องเพิ่มคอลัมน์ใดๆ ใน E2 เพื่อรองรับเรื่องนี้** — ภาระทั้งหมดอยู่ที่รูปแบบ op ในเครื่อง ซึ่งเป็นของผมเอง
(`rank_epoch` ต่อวันช่วยได้ในฐานะ fast path — ถ้า epoch ตรงก็ข้ามการคำนวณใหม่ไปเลย
**แต่เป็นการ optimize ไม่ใช่เงื่อนไขความถูกต้อง ผมจึงไม่ขอ**)

## 5. แผนที่บนมือถือ

**คำตอบ: ใช่ — deep-link ออกไป Naver/Kakao เหมือนเว็บ และให้ผู้ใช้เลือกเองเหมือนเดิม**

`lib/mapLinks.ts:1-9` ตัดสินใจข้อนี้ไว้แล้วด้วยเหตุผลที่ยังใช้ได้ทุกข้อบน native: กฎหมายแผนที่เกาหลี
ไม่ได้เปลี่ยนเพราะเราเปลี่ยนแพลตฟอร์ม และคนเกาหลีก็ยังใช้ Naver/Kakao อยู่ดี

**สิ่งที่ native ทำได้ดีกว่าเว็บตรงนี้จริงๆ มีข้อเดียว แต่เป็นข้อที่ดี:**
`lib/mapLinks.ts:75-84` `openNaverMap()` ต้องเดาว่ามีแอปหรือเปล่าด้วย timer 1300 ms แล้วเช็ค
`document.hidden` — และ `:60-61` เขียนไว้เองว่า**ยังไม่เคยยืนยันบนเครื่องที่ลงแอปจริง** เพราะ `nmap://`
ไม่คืน response ให้เช็ก · บน RN ใช้ `Linking.canOpenURL("nmap://")` **ถามได้ตรงๆ ว่ามีแอปไหม**
→ ซ่อนปุ่มที่กดไปก็ไม่มีอะไรเกิดขึ้นได้เลย ไม่ต้องเดา ไม่ต้องมี fallback timer

**แผนที่ในแอป** ใช้แค่ *แสดง* เส้นทางของวัน (หมุด + เส้นเชื่อม) ไม่ใช่นำทาง
⚠️ **ต้องทดสอบจริงก่อนเลือก SDK** — คุณภาพข้อมูลของ Google/Apple Maps ในเกาหลีต่างกันมากและผม
**ยืนยันเองไม่ได้จากที่นี่** · เทสต์ที่ต้องทำ: เปิดแผนที่ที่พิกัดหาดแฮอึนแด (ปูซาน) แล้วดูว่ามีชื่อถนน/POI
ภาษาเกาหลีขึ้นครบไหม เทียบ 3 เจ้า (Google SDK / Apple MapKit / MapLibre) · ของที่ยืนยันแล้วมีข้อเดียวคือ
**Routes API ไม่คืน DRIVE/WALK ในเกาหลี** (`PLAN.md §2` ทดสอบจริงแล้ว) ซึ่งเป็นเรื่องของ *เส้นทาง* ไม่ใช่ *แผนที่*

⚠️ ไม่เสนอเพิ่ม ODsay/Kakao/Naver API ตามที่ `PLAN.md §2` และ `docs/engine/README.md:78-79` ตัดสินไว้แล้ว

   ⚠️ ต้องกำหนดที่ **คอลัมน์** ไม่ใช่หวังพึ่ง collation ของ DB เพราะ Supabase local (Docker) กับ

### 10.1 ปัญหาให้ชัดก่อน — ไม่ใช่ "กล่องเล็กไป" อย่างเดียว

`lib/localCache.ts` มี 3 ปัญหาที่แยกกันคนละเรื่อง และ **ข้อ 2 ร้ายกว่าข้อ 1**:

| # | ปัญหา | หลักฐาน |
|---|---|---|
| 1 | โควตา ~5 MB ต่อ origin ทั้งหมดรวมกัน | ข้อจำกัดของ localStorage เอง · เดิมมีทางออกคือ SQLite บน native **ซึ่งหายไปพร้อม D14** |
| 2 | 🔴 **เต็มแล้วเงียบสนิท** | `lib/localCache.ts:23-30` `catch {}` เปล่าโดยตั้งใจ · ผลจริง: เขียนแคชไม่ลงแต่หน้าจอปกติทุกอย่าง → **ไปรู้ตอนเปิดแอปในอุโมงค์แล้วข้อมูลไม่มี** ซึ่งคือนาทีที่แก้อะไรไม่ได้แล้ว |
| 3 | sync + `JSON.parse` บน main thread | `localStorage.getItem` เป็น synchronous · ก้อน `stops` ทั้งทริปถูก parse ตอน mount ทุกครั้ง |

**ข้อ 2 แก้ได้ทันทีโดยไม่ต้องย้ายไป IndexedDB เลย** และควรแก้ก่อนด้วยซ้ำ (ดู 10.6)

### 10.2 ทำไมการย้ายถูกกว่าที่คิด — ผมไปนับ call site มาแล้ว

ข้อกังวลปกติของการย้ายไป IndexedDB คือ **"API เป็น async แต่โค้ดเดิมเรียกแบบ sync"**
ผมไล่ดูทั้ง 8 hooks แล้ว — **ปัญหานั้นไม่มีอยู่จริงในโค้ดเบสนี้**

- `readCache` **8 จุด** · `writeCache` **13 จุด** รวม **21 จุดใน 8 hooks** (ไม่มีใน `components/` เลยสักจุด)

> 🔴 **ตัวเลขนี้ grep ตรงๆ ไม่ได้ — มีกับดัก 2 ชั้นที่ชี้คนละทาง และทั้งคู่ให้ผลที่ "ดูน่าเชื่อ"**
> (ชั้นที่ 2 P1 เหยียบเข้าจริงตอนตรวจงานผม 17 ส.ค. 2026 · ผมรันซ้ำยืนยันแล้วทั้งคู่)
>
> | คำสั่ง | ได้ | ความจริง |
> |---|---|---|
> | `grep -rn 'readCache(' hooks/` | **0** | ผิด — **ทุก call site เขียน `readCache<TripStop[]>(` มี generic คั่นก่อนวงเล็บ** จึงไม่มีสตริง `readCache(` อยู่ในโค้ดเบสนี้เลยสักที่ |
> | `grep -rn 'readCache' hooks/` | **10** | ผิด — เกินมา 2 เพราะไปโดน `hooks/usePlaceNamesEn.ts:15` ที่มีฟังก์ชันชื่อ `readCached()` ของตัวเอง (in-memory `Map` **คนละเรื่องกับ `lib/localCache.ts` ไม่ต้องแตะ**) |
> | นับจาก call site จริง | **8** | ✅ |
>
> **ชั้นที่อันตรายที่สุดคือความไม่สมมาตร:** `grep 'writeCache('` คืน **13 ซึ่งถูก** เพราะ `writeCache`
> ไม่มี generic → คนตรวจจะได้ผล "writeCache ใช้ 13 จุด · readCache ใช้ 0 จุด" ที่**ดูสอดคล้องกันพอจะเชื่อ**
> แล้วสรุปว่า **"`readCache` เป็นโค้ดตาย ลบทิ้งได้"** ซึ่งผิดสนิทและเป็นการลบทาง hydrate ออฟไลน์ทั้งระบบทิ้ง
>
> **คนทำ E6 ต้องเปิดไฟล์ทั้ง 8 ดูเอง ไม่ใช่เชื่อเลขจาก grep** — และถ้าจะ grep ให้ใช้
> `grep -rn 'readCache' hooks/ | grep -v readCached` แล้วยังต้องไล่ดูอยู่ดี
- **ทุกจุดอยู่ใน `async function init()` หรือ async callback อยู่แล้ว** เช่น `hooks/useStops.ts:60`,
  `useBookings.tsx:50`, `useDaySettings.ts:29`, `useHotels.tsx:61`, `usePlans.ts:29`,
  `usePlaceNotes.ts:36`, `useOvernightOverrides.ts:28`, `useCustomPlaces.tsx:26`
- **ไม่มีสักจุดเดียว**ที่เรียกใน `useState(() => readCache(...))` หรือระหว่าง render
  (เช็คแล้ว — `useState` ทุกตัวใน 8 ไฟล์ initialize ด้วย `!supabaseConfigured` หรือค่าว่าง)

→ **การย้ายคือการเติม `await` 21 จุด** ไม่ใช่การรื้อ data flow · เป็นงานที่ประเมินได้และย้อนกลับได้

### 10.3 API ที่เสนอ — เปลี่ยนให้น้อยที่สุด

คงชื่อและรูปร่างเดิมไว้ทั้งหมด เปลี่ยนแค่คืน `Promise`:

```
readCache<T>(key: string): Promise<T | null>
writeCache(key: string, value: unknown): Promise<void>
```

เพิ่มอีก 3 ตัวที่โมเดลใหม่ต้องใช้ (ดู 10.5–10.7):

```
dropTripCache(tripId: string): Promise<void>     // ลบทั้งทริปทีเดียว
cacheHealth(): Promise<{usage: number; quota: number; persisted: boolean}>
readBlob/writeBlob(key, Blob)                    // ไฟล์ตั๋ว/รูป
```

**object store เดียว** key เป็นสตริงเหมือนเดิม แต่**ต้องขึ้นต้นด้วย `tripId`** — `"<tripId>:stops"`
ไม่ใช่ `"stops:<planId>"` แบบวันนี้ (`hooks/useStops.ts:34`) เพราะแพลตฟอร์มต้องลบ/นับทีละทริปได้
· ทำ index บน `tripId` เพื่อให้ `dropTripCache` เป็น range delete ไม่ใช่การไล่สแกนทุกคีย์

### 10.4 เขียนเองหรือใช้ไลบรารี — เขียนเอง ตามบรรทัดฐานของโปรเจกต์นี้เอง

`public/sw.js:7` ตัดสินเรื่องเดียวกันนี้ไปแล้วและเขียนเหตุผลไว้ชัด:
*"เขียนเองไม่ใช้ Workbox — กฎที่ต้องการมีแค่ 3 ข้อ ไม่คุ้มกับการเพิ่ม dependency"*

ที่นี่ก็เหมือนกัน — สิ่งที่ต้องใช้จริงมีแค่ `get` / `put` / `delete` / `deleteRange` บน object store เดียว
IndexedDB API ดิบน่าเกลียดเพราะเป็น event-based แต่**ห่อเป็น Promise ครั้งเดียวจบใน ~40 บรรทัด**
· ไลบรารีอย่าง `idb` ทำงานได้ดีและเล็ก แต่ที่นี่มันคือ dependency ที่แลกมาด้วยของที่เขียนเองได้ในครึ่งชั่วโมง
**ถ้าจะแย้งข้อนี้ ต้องแย้งด้วยเหตุผลเดียวกับที่จะแย้ง `sw.js` ไม่ใช่คนละมาตรฐาน**

### 10.5 🔴 กล่องใหญ่ขึ้นไม่ได้แปลว่าไม่ต้องมีนโยบายลบ

**นี่คือข้อที่ผมคิดว่าจะถูกมองข้ามมากที่สุด** — พอย้ายไป IndexedDB แล้วโควตาขึ้นเป็นหลักร้อย MB
คนจะเลิกคิดเรื่องขนาด แล้วแคชทุกทริปที่เคยเปิดไว้ตลอดกาล จนกลับไปเจอกำแพงเดิมในอีกรูปแบบหนึ่ง
(ช้าลงเรื่อยๆ · เครื่องผู้ใช้เต็ม · เบราว์เซอร์ล้างทั้ง origin ทิ้งเองแบบไม่บอก)

**นโยบายที่เสนอ:**
- เก็บแคชเต็มรูปเฉพาะ **ทริปที่กำลังเปิดอยู่ + 2 ทริปที่เปิดล่าสุด** (เก็บ `lastOpenedAt` ต่อทริป)
- ทริปที่จบไปแล้ว (วันสุดท้าย < วันนี้) → เก็บแค่ metadata ไว้โชว์ในลิสต์ ไม่เก็บ stops/ตั๋ว/รูป
- ผู้ใช้กด "เก็บทริปนี้ไว้ใช้ออฟไลน์" ได้เอง = ปักหมุดไม่ให้ถูกลบ **ตัดสินใจโดยผู้ใช้ ไม่ใช่เดาให้**
- เรียก **`navigator.storage.persist()`** ตอนผู้ใช้ปักหมุดทริปแรก — ขอไม่ให้เบราว์เซอร์ล้างทิ้งเองตอนเครื่องเต็ม
  (ถ้าไม่ขอ ข้อมูลออฟไลน์อาจหายไปเงียบๆ ตอนที่ต้องใช้พอดี ซึ่งคือปัญหาเดิมในชื่อใหม่)

### 10.6 เลิกกลืน error เงียบ — แก้ก่อนได้เลย ไม่ต้องรอ IndexedDB

**ทำสองชั้น เพราะชั้นเดียวไม่พอ:**

1. **ชั้นดักหลังพลาด** — `lib/localCache.ts:23-30` ที่ `catch {}` เปล่า ให้ยิง `showToast("error", …)`
   จาก `lib/toast.ts` ที่มีอยู่แล้ว · ข้อความต้องบอกผลที่ตามมา ไม่ใช่บอกอาการ:
   ไม่ใช่ *"บันทึกแคชไม่สำเร็จ"* แต่เป็น **"พื้นที่ในเครื่องเต็ม — ทริปนี้จะเปิดดูตอนไม่มีเน็ตไม่ได้"**
   ⚠️ ต้อง throttle ไม่งั้นเต็มแล้วจะเด้ง toast ทุกครั้งที่ fetch (`writeCache` ถูกเรียก 12 จุด)
2. **ชั้นเตือนก่อนถึง** — `navigator.storage.estimate()` คืน `{usage, quota}`
   → เตือนตอนใช้ไปเกิน ~80% **ก่อน**ที่จะเขียนไม่ลง · localStorage ไม่มีทางรู้ล่วงหน้าแบบนี้เลย
   **นี่คือข้อได้เปรียบของ IndexedDB ที่ผมคิดว่าสำคัญกว่าเรื่องขนาดด้วยซ้ำ**

### 10.7 ของที่ localStorage ทำไม่ได้เลย ไม่ใช่แค่ทำได้น้อย — ไฟล์

IndexedDB เก็บ **`Blob` ตรงๆ** ได้ (structured clone) และ**ไม่ต้อง `JSON.stringify`** ทั้งก้อน
- ตั๋ว PDF / รูปหน้างาน (`bookings.file_url` · `trip_stops.photo_url`) เก็บออฟไลน์ได้จริง
  · บน localStorage ต้องเป็น base64 ในสตริง JSON = **บวมขึ้น ~33% แล้วยัดลงกล่อง 5 MB** = ทำไม่ได้ตั้งแต่ต้น
- ผลพลอยได้: เลิก `JSON.parse` ก้อนใหญ่บน main thread ตอน mount (ปัญหาข้อ 3 ใน 10.1 หายไปเอง)

**และนี่คือจุดที่ D17 เชื่อมกลับไปหา D14** — "เปิดตั๋วดูตอนอยู่หน้าเคาน์เตอร์ที่ไม่มีเน็ต"
เคยเป็นเหตุผลหนึ่งของ native (§1.2) · **บน IndexedDB มันทำได้บนเว็บ** → ข้อนั้นถูกกู้กลับมาด้วย
**เหลือเคสที่ native เท่านั้นทำได้จริงๆ แค่เคสเดียวตาม §9.2 คือการเตือนตอนไม่มีเน็ต**

### 10.8 ลำดับการย้าย + ทางถอย

| ขั้น | ทำอะไร | ถอยได้ไหม |
|---|---|---|
| 1 | เพิ่ม toast + `estimate()` ลง `localCache.ts` เดิม (10.6) | ✅ **ทำได้ทันทีในระยะ 2 ไม่ต้องรออะไร ไม่แตะโครงสร้าง** |
| 2 | เขียน IndexedDB wrapper + เทสต์ **โดยยังไม่มีใครเรียก** | ✅ ไม่มีผลกับของเดิม |
| 3 | เติม `await` 21 จุด สลับไปเรียกตัวใหม่ | ✅ กลับได้ด้วยการสลับ import |
| 4 | ย้ายข้อมูลเก่า: อ่านคีย์ `trip-cache:` ทั้งหมดครั้งเดียว → เขียนลง IDB → ลบทิ้ง | ⚠️ **ทำครั้งเดียวและต้อง idempotent** |
| 5 | เปิดใช้ Blob + นโยบายลบทริปเก่า (10.5 · 10.7) | ✅ |

**ทางถอยที่ต้องมีตั้งแต่ขั้น 2:** เครื่องที่ IndexedDB ใช้ไม่ได้ (Safari private mode, ผู้ใช้ปิด storage)
ต้อง **ตกกลับไปเป็น in-memory เงียบๆ แล้วแอปยังทำงานได้ปกติแบบออนไลน์**
— แบบเดียวกับที่ `lib/localCache.ts:12-21` ทำอยู่วันนี้ (คืน `null` ไม่โยน)
**ห้ามให้ IndexedDB พังแล้วแอปพังตาม** เพราะตอนนี้แอปยังทำงานได้ 100% โดยไม่มีแคชเลย

### 10.9 ที่ผมยืนยันเองไม่ได้

- **ตัวเลขโควตา IndexedDB จริงบน iOS Safari** — ผมรู้ว่ามันสูงกว่า localStorage หลายสิบเท่าและ
  Apple ขยายเพดานมาหลายรอบ **แต่ตัวเลขเป๊ะๆ และเงื่อนไข "เว็บที่ติดตั้งโฮมสกรีน" ต้องวัดเองบนเครื่องจริง**
  · เทสต์ที่ต้องทำ: เรียก `navigator.storage.estimate()` บน iPhone จริงทั้งใน Safari และในแอปที่ติดตั้งโฮมสกรีน แล้วเทียบ
- **`navigator.storage.persist()` ให้ผลอย่างไรบน Safari** — บน Chromium/Firefox พฤติกรรมชัด
  ฝั่ง Safari ผมไม่ยืนยัน · ต้องเช็คว่าคืน `true` จริงไหมหรือเงียบๆ ปฏิเสธ
- ทั้งสองข้อ **วัดได้ในครึ่งวันตอนเริ่ม E6** และควรวัดก่อนตัดสินนโยบายใน 10.5 ไม่ใช่หลัง

⚠️ **ความเร่งด่วนอยู่ที่ trigger ไม่ใช่ที่คอลัมน์ — และนี่คือเหตุผลที่ต้องตัดสินตอนนี้จริง ๆ**
เพิ่มคอลัมน์ทีหลังถูกมาก (nullable add) **แต่แถวที่ถูกแก้ไปแล้วก่อนคอลัมน์มีอยู่จะเป็น `NULL` ตลอดกาล
backfill ไม่ได้** = เสีย**ข้อมูล** ไม่ใช่เสียเวลา

📌 **DDL:** `updated_by_user uuid references profiles(id)` · เขียนโดย **trigger เดียวกับ `updated_at`**
ด้วย `auth.uid()` · 🔴 **ห้ามรับค่าจาก client** (เหตุผลของ `D7` บวก `D38` — ค่าที่ client ส่งมาไม่ได้ผ่านการตรวจสิทธิ์)

✅ **และเพราะ soft delete คือ `UPDATE` ไม่ใช่ `DELETE` เราได้ "ใครลบ" มาฟรีจากคอลัมน์เดียวกัน**
**ไม่ต้องมี `deleted_by_user`** — เป็นข้อดีของ `D7` ที่ยังไม่มีใครนับ และเป็นของที่ hard delete ให้ไม่ได้เลย

### 11.5 คำถามข้อ 2 (tombstone อยู่นานแค่ไหน) — **ข้อเสนอ: ไม่ purge เลย**

**tombstone อยู่ถาวรตลอดอายุทริป · ลบพร้อมทริปเท่านั้น (cascade) · ไม่มีนโยบาย retention**

1. **ขนาดไม่ใช่ปัญหาตั้งแต่แรก** — ทริปหนึ่งมีจุดแวะหลักสิบถึงหลักร้อยแถว ไม่ใช่หลักล้าน
   · ตารางที่โตจริงคือแคช (`place_details_cache` · `place_photo_cache` · `travel_time_cache`)
   ซึ่ง `column-map.md` ระบุแล้วว่า **"ไม่ได้กฎร่วม"** = ไม่มี `deleted_at` ตั้งแต่แรก **จึงไม่มีอะไรให้ purge**
2. 🔴 **ทุกนโยบาย purge สร้างบั๊กคลาสเดียวกันหมด** — เครื่องที่ไม่ได้เปิดนานกว่า retention
   จะ**ไม่มีทางรู้ว่าแถวถูกลบ** → แถวผีอยู่ต่อไม่มีกำหนด · การกำหนด retention จึงต้องมาคู่กับกลไก
   *"ถ้าเก่ากว่า N ให้ล้างทั้งก้อนแล้วโหลดใหม่"* ซึ่งเป็นระบบทั้งระบบ — **เพื่อประหยัดพื้นที่ที่ไม่ได้เปลืองอยู่แล้ว**

⚠️ **ราคาที่ต้องจ่ายและลดไม่ได้:** `deleted_at is null` ต้องอยู่ใน **ทุก policy ทุก query ทุก predicate**
ไม่งั้นแถวที่ลบแล้วโผล่ใน UI · เป็นราคาที่ `E2-AC12` ตั้งไว้แล้ว ผมแค่ยืนยันว่าไม่มีทางเลี่ยง

**คำถาม "ลบตอน offline แล้วอีกเครื่องแก้แถวเดิม — ใครชนะ":** `deleted_at` เป็นฟิลด์หนึ่งที่ LWW ตัดสิน
ตามตาราง §3.3 เดิม **ยกเว้น `trip_hotels` ซึ่งมีข้อยกเว้นจริง — ดู 11.7**

### 11.6 คำถามข้อ 3 (rank tie-break + rebalance) — ยืนยัน `(rank, id)` และ **ผมขอแก้เอกสารตัวเอง 3 จุด**

**ยืนยัน:** tie-break = **`(rank, id)`** ตาม §3.4 · rank ที่ซ้ำกัน**ถูกกฎหมาย**

🔴 **แก้ที่ 1 — ห้ามมี unique constraint บน rank**
คนเขียน DDL จะอยากใส่ `unique (day_id, plan_id, rank)` เพราะมันดูเป็นสุขอนามัยที่ดี
**ถ้าใส่: 2 คนแทรกจุดตำแหน่งเดียวกันพร้อมกัน คนหลังได้ error แทนที่จะได้จุดของตัวเอง**
ซึ่งขัดกับบรรทัดในตาราง §3.3 ที่เขียนว่า *"✅ ได้ทั้ง 2 จุด"* โดยตรง — และ "ได้ทั้งคู่" คือคำตอบที่ถูกสำหรับแอปวางแผนทริป
📌 **rank ไม่ unique โดยเจตนา — ต้องเขียนคอมเมนต์กำกับใน DDL ไม่งั้นมีคนมาเติมทีหลังด้วยความหวังดี**

🔴 **แก้ที่ 2 — ขอบเขตของ rank และ rebalance คือ `(day_id, plan_id)` ไม่ใช่ `day_id`**
§3.4 ผมเขียนว่า *"ต่อวัน (`trip_day_id`) เท่านั้น"* — **เขียนตอนยังไม่รู้ `D36`** ซึ่งให้ `trip_stops`
คง `plan_id` ไว้คู่กับ `day_id` · ถ้า rebalance ต่อวันล้วน มันจะเขียนแถวของแผน A และแผน B พร้อมกัน
ทั้งที่ผู้ใช้แก้อยู่แผนเดียว = สร้าง conflict ข้ามแผนขึ้นมาเองโดยไม่มีใครสั่ง
📌 **index ต้องเป็น `(day_id, plan_id, rank)`** ไม่ใช่ `(trip_day_id, rank)` ตามที่ §7 ข้อ 5 เขียนไว้ — **§7 ข้อ 5 ผิด**

🔴 **แก้ที่ 3 — index นี้ต้อง _ไม่_ เป็น partial `where deleted_at is null`**
สวนทางกับ 11.5 โดยตั้งใจ · กฎ *"เพื่อนบ้านถูกลบไปแล้วตอน merge"* ใน §3.4 **ต้องอ่านแถวที่ถูกลบไปแล้ว**
เพื่อไล่หาตำแหน่ง → partial index ทำให้ query นั้นตกไป seq scan **เงียบ ๆ ไม่มีอะไรฟ้อง**

**และ `id` ต้องเทียบได้ตรงกันระหว่าง JS กับ Postgres** (ไม่งั้น tie-break เรียงไม่ตรงกันสองฝั่ง = บั๊ก 8.1 ทางประตูหลัง)
- วันนี้ `trip_stops.id` เป็น **`text primary key`** ที่ไคลเอนต์สร้างเอง (`0006_trip_stops.sql:3` · `makeStopId()`)
- ถ้า `E2` เปลี่ยนเป็น `uuid` → ตรงกัน (uuid ตัวพิมพ์เล็ก เทียบสตริงได้ผลเดียวกับเทียบ byte)
- **ถ้ายังเป็น `text` ต้อง `COLLATE "C"` เหมือน `rank`** ตาม §7 ข้อ 4
- ⚠️ ข้อจำกัดที่ต้องรู้: `COLLATE "C"` = เทียบ byte ของ UTF-8 · JS เทียบ UTF-16 code unit
  **ให้ผลเดียวกันตราบใดที่คีย์เป็น ASCII ล้วน** ซึ่ง rank (base-62) และ id ทั้งสองแบบเป็น ASCII ล้วน ✅
  **แต่ถ้าวันหนึ่งมีใครเอาคีย์ที่ไม่ใช่ ASCII มาใช้ ข้อตกลงนี้ตายทันทีโดยไม่มีสัญญาณ**

### 11.7 คำถามข้อ 3 (`D51`) — **มีผล และเป็นข้อเดียวที่เจาะรูโมเดลของผม**

`D51` ถูก · ผมไม่ได้แย้ง **แต่ exclusion constraint ทำให้ `trip_hotels` เป็นตารางเดียวในระบบที่ merge "ล้มเหลวได้"**

โมเดลทั้งหมดใน §3 ตั้งอยู่บนคุณสมบัติเดียว:
**ทุก op คือการเขียนแถวเดียวที่สำเร็จเสมอ · ที่เหลือให้ LWW ตัดสิน**
`exclude using gist (trip_id with =, daterange(check_in, check_out) with &&) where (deleted_at is null)` ทำลายคุณสมบัตินั้น:

- A เลื่อน `check_out` ของใบจอง 1 · B เลื่อน `check_in` ของใบจอง 2
  **แต่ละคนถูกต้องเมื่ออยู่คนเดียว · รวมกันแล้วซ้อน** → คนที่มาทีหลังได้ `23P01`
- **LWW ตัดสินไม่ได้** เพราะไม่มี "ฟิลด์" ให้เลือกผู้ชนะ — มันคือ constraint **ข้ามแถว** ไม่ใช่ค่าในแถว

🔴 **และรูที่ใหญ่กว่า: กฎ "ฟื้นแถวคืน" ของผมใช้กับ `trip_hotels` ไม่ได้**
§3.3 เขียนว่า *"A ลบ · B แก้ทีหลัง → จุดกลับมาพร้อมโน้ต ซึ่งกู้คืนได้"* โดยถือว่า `deleted_at`
เป็นแค่ฟิลด์หนึ่งที่ LWW ตัดสิน · **แต่ `deleted_at` อยู่ใน predicate ของ constraint**
→ การ "ฟื้น" ใบจองคือการ**เพิ่มแถวกลับเข้ามาในขอบเขตของ constraint**
ถ้าระหว่างนั้นมีคนจองคืนเดียวกันไปแล้ว **การฟื้นจะถูกปฏิเสธ ไม่ใช่ทับกัน**

📌 **ข้อกำหนดที่ต้องเขียนลงสเปก (เป็นกฎของ E3 ไม่ใช่ DDL):**
1. เขียน `trip_hotels` ต้องผ่าน server path ที่ **ดัก `23P01` แล้วบอกผู้ใช้ว่า "ช่วงวันชนกับใบจองอื่น"**
   · **ห้ามเป็น optimistic write แบบยิงแล้วลืม** เหมือนตารางอื่นทั้งหมดในแอปนี้วันนี้
2. ตาราง §3.3 ของผมต้องมีบรรทัดใหม่: **`trip_hotels` ไม่รับประกัน "ฟื้นคืนได้"** — เป็นข้อยกเว้นเดียวของโมเดล
3. ⚠️ **ปฏิสัมพันธ์ระหว่าง `D7` กับ `D51` ที่ยังไม่มีที่ไหนเขียนไว้:** soft delete ของตารางนี้
   **เปลี่ยนพฤติกรรมของ constraint** ไม่ใช่แค่ซ่อนแถว

✅ **ส่วนที่ไม่มีผลเสียเลย — `check_in`/`check_out` แทน `leg_id` ดีกับ sync ล้วน ๆ**
`leg_id` เป็นค่าที่**คำนวณและขยับตามแผน** แปลว่า op ที่คิวไว้จะชี้ไป leg ที่ไม่มีอยู่แล้วตอน merge
ซึ่งคือ **ปัญหาเดียวกับ rebalance ของ rank เป๊ะ** (§3.4) และต้องแก้ด้วยกลไก "อ้างเพื่อนบ้าน ไม่ใช่อ้างค่า" แบบเดียวกัน
**`D51` ฆ่ามันทิ้งก่อนที่ผมจะต้องออกแบบทางแก้**

### 11.8 ⚠️ ของแถม — อย่าใช้ `updated_at` เป็นเคอร์เซอร์ delta sync (เป็นกฎ ไม่ใช่คอลัมน์)

เขียนไว้เพราะมันจะถูกเสนอแน่ ๆ ตอน `E6`/`D17` (IndexedDB) และตอนนั้นจะสายเกินกว่าจะเถียง

`now()` ใน Postgres = **เวลาเริ่ม transaction ไม่ใช่เวลา commit**
→ tx ที่เริ่มก่อนแต่ commit ทีหลัง ได้ `updated_at` **เก่ากว่า** แถวที่คนอื่นเพิ่ง commit ไป
→ ใครดึงด้วย `updated_at > cursor` แล้วเลื่อน cursor **จะข้ามแถวนั้นถาวร เงียบสนิท ไม่มี error**

📌 ถ้าจะทำ delta pull จริง: ดึงด้วย **`updated_at > cursor - ช่วงกันชน`** (กว้างกว่า transaction ที่ยาวที่สุด)
แล้ว apply แบบ idempotent · **หรือ**ใช้ Realtime เป็นช่องทางหลักแล้วให้ `updated_at` ทำแค่ cold start
ซึ่งคือสิ่งที่เว็บทำอยู่แล้ววันนี้ (`hooks/useStops.ts:58-72`) **และเป็นเหตุผลที่บั๊กนี้ยังไม่เคยเกิด**

### 11.10 🔴 ตรวจของที่ลงจริงแล้ว — trigger ครอบครึ่งเดียวของพื้นผิว (25 ส.ค. 2026)

> P1 ถามซ้ำเรื่อง `updated_at` ตอน `trip_days` ลง `engine-dev` แล้ว (`7f985e3`) และกำลังจะก๊อป
> trigger ตัวเดียวกันลงอีก ~10 ตาราง · ผมไปอ่าน DDL ที่ลงจริงแทนที่จะตอบจากเอกสาร **แล้วเจอรูนี้**

**ที่ลงจริง** (`20260825110903_e2_trip_days.sql:172` · `20260824043822_identity.sql:442`):
```sql
create or replace function app.touch_updated_at() ... begin new.updated_at := now(); return new; end;
create trigger trip_days_touch before update on public.trip_days ...
grant select, insert, update on public.trip_days to authenticated;
```

🔴 **`before update` ไม่ยิงตอน `INSERT` · และ `default now()` ใช้ก็ต่อเมื่อไคลเอนต์ *ไม่ส่ง* คอลัมน์นั้นมา**
ตรวจแล้วทั้ง repo: **ไม่มี `before insert` trigger สักตัว · ไม่มี column-level grant/revoke สักบรรทัด**
→ `grant … insert …` เป็นระดับตาราง = **ไคลเอนต์ตั้ง `created_at` และ `updated_at` เองได้เต็มที่ตอนสร้างแถว**

**ผลที่เป็นจริงวันนี้ ไม่ต้องรอ offline ไม่ต้องรอ mobile:**
- แถวที่เกิดจากเครื่องนาฬิกาผิด **เกิดมาพร้อม `updated_at` ที่ผิด** → **ชนะ LWW ตั้งแต่วินาทีแรกจนกว่าจะมีคนแก้แถวนั้น**
  (ถ้ามีคนแก้ trigger จะซ่อมให้ · **ถ้าไม่มีใครแก้ มันผิดตลอดไป**)
- `created_at` **ไม่มีอะไรซ่อมเลยสักชั้น** — เชื่อมกับ §11.3: `useChecklist.ts:14` เรียงด้วยค่านี้

⚠️ **เคสสดที่ P1 รันยืนยัน (client ส่งปี 2000 แล้วถูกทับ) เป็นเคส `UPDATE`** — ด้านที่ trigger ครอบอยู่แล้ว
**ด้าน `INSERT` ยังไม่มีใครลอง** · เป็นรูปแบบเดิมของทีมนี้: ของที่ผ่านเพราะทดสอบด้านที่มันครอบ

📌 **แม่แบบมีอยู่แล้วในไฟล์ของ P1 เอง** — `app.freeze_created_by()` (`identity.sql:378`) คือท่าเดียวกันเป๊ะ
📌 **ราคาของการแก้ตอนนี้ = 1 ฟังก์ชัน · ราคาหลังก๊อปไป 10 ตาราง = 10 migration + backfill ที่คำนวณย้อนหลังไม่ได้**

`service_role` ยังตั้งค่าเองได้ ส่วน `authenticated` แตะไม่ได้ โดยไม่ต้องมี `if` สักบรรทัด
· ลำดับ `revoke` ระดับตารางก่อน `grant` ระดับคอลัมน์ **ตรวจแล้วถูกต้องทั้ง 6 ตาราง**

🔴 **แต่มันสร้างข้อผูกมัดเรื่องลำดับที่ยังไม่มีที่ไหนเขียนไว้ — `E3` ต้องเสร็จก่อน `E7` cutover**

`E2-AC9` เปลี่ยนจาก *"ส่งมาได้ แต่ถูกทับ"* → *"ส่งมาแล้วถูกปฏิเสธ `42501`"* ซึ่งดีกว่าจริง
**แต่วันนี้ไคลเอนต์ส่งมาอยู่ 40 จุด** (`grep 'updated_at: '` = **31** · `'created_at: '` = **9** · 7 hooks)
→ **วินาทีที่แอปชี้ไปสคีมาใหม่ ทางเขียน 40 เส้นตายพร้อมกันทั้งหมด ไม่ใช่ทีละเส้น**

📌 **ลำดับที่บังคับ: `E3` ต้องเลิกส่ง `created_at`/`updated_at` จากไคลเอนต์ให้ครบ *ก่อน* ที่ `E7` จะ cutover**
· กลับลำดับ = แอปเขียนอะไรไม่ได้เลย · ⚠️ และถ้าเกิดใกล้ทริปจริง (11–21 ต.ค.) **นี่คือแอปที่ใช้ระหว่างทริปไม่ได้**

🔴 **กับดักที่ P1 จดไว้ ขยายข้ามไฟล์ได้และจะไม่มีอะไรฟ้อง**
P1 จดว่า *"ต้อง `revoke` ระดับตารางก่อน column-level revoke ถึงมีผล"* — ถูก **แต่ข้อเดียวกันแปลว่า
migration ไฟล์ไหนก็ตามที่เขียน `grant insert/update on <t> to authenticated` ระดับตารางในอนาคต
จะเปิดรูกลับทันทีเงียบ ๆ** · `20260825120856_e2_trip_plans.sql:175` เขียนแบบนั้นไว้แล้ว (รอดเพราะไฟล์ freeze รันทีหลัง)
· อีก ~10 ตารางข้างหน้าจะมีบล็อก `grant` แบบนี้ทุกไฟล์

📌 **ทางกันที่ทนต่อเวลา: ยืนยันสภาพปลายทาง ไม่ใช่ grep ข้อความใน migration**
`has_column_privilege('authenticated', '<t>', 'created_at', 'INSERT') = false` ทุกตารางเนื้อหา
— แบบเดียวกับที่ `E2-AC1` ยืนยันสิทธิ์ ไม่ใช่ยืนยันว่ามีบรรทัด policy อยู่

### 11.12 `D70` (FK ประกอบ) กระทบ merge rule ไหม — **ตัว `trip_id` ไม่กระทบ · `on delete cascade` ที่ห้อยกับมันกระทบ** (25 ส.ค. 2026)

**คำตอบตรง ๆ ก่อน: merge rule ของ `§3.4` รอด ไม่ต้องแก้อะไร**
`trip_id` เป็นค่าที่ผูกกับพ่อ ไม่ใช่ค่าอิสระ — P1 มองถูก · และ FK ประกอบยัง **ช่วย** โมเดลด้วยซ้ำ
เพราะมันทำให้ขอบเขต rank `(day_id, plan_id)` ของ `§11.6` **บังคับได้ที่ฐาน** — จุดแวะจะมีวันของทริป X
กับแผนของทริป Y พร้อมกันไม่ได้อีก ซึ่งเดิมเป็นเงื่อนไขที่มีแต่ในเอกสาร

📌 **ข้อเดียวที่ขอ: `trip_id` ต้องไม่อยู่ใน `grant update (...)` ของ `trip_stops`**
ทุก op ในโมเดลคือการเขียน**ฟิลด์เดียว** · op ที่เขียน `trip_id` เดี่ยว ๆ ไม่ใช่ no-op แต่คือ**ย้ายแถวข้ามทริป**
· deny-by-default จาก column grant ของ `a9f49c6` ทำให้ข้อนี้ฟรี — แค่ **ไม่ใส่ชื่อมันลงลิสต์**
⚠️ `trip_day_plan_settings` วันนี้ `grant update (trip_id, plan_id, trip_day_id, …)` = ให้ไคลเอนต์เขียนคอลัมน์ที่เป็น
ตัวระบุตัวตนของแถวเองได้ · ไม่ใช่โซนผม แต่เป็นรูปแบบที่ไม่อยากให้ถูกคัดลอกไป `trip_stops`

#### 🔴 ของจริงอยู่ที่ cascade — และมันคือคำถาม tombstone ที่ P1 ถาม แต่มาจากทิศที่ไม่ได้มอง

`D70` จะให้ `trip_stops` ห้อย `(trip_id, day_id) → trip_days(trip_id, id)` **`on delete cascade`**
ตามแบบที่ `trip_day_plan_settings` ใช้อยู่ (`20260825120856_e2_trip_plans.sql:120-122`)

**สภาพวันนี้ 3 ข้อ ซึ่งแต่ละข้อไม่มีปัญหา แต่รวมกันแล้วมี:**
1. `trip_days` **ไม่มี `deleted_at` และไม่มี policy `DELETE`** — P1 ยกไปตัดสินพร้อม `E3` ที่เขียนตัวปรับช่วงวัน
2. `E3` ตัวนั้นคือของที่จะ**ลบแถว `trip_days`** เวลาผู้ใช้ย่นช่วงวันของทริป
3. **RLS ไม่มีผลกับ cascade** — P1 เขียนไว้เองที่ `trip_plans.sql:16`

→ ผู้ใช้แก้ `end_date` จาก 21 เป็น 19 ต.ค. → `E3` ลบ 2 วันนั้น → **cascade ลบจุดแวะของ 2 วันนั้นทิ้งทั้งหมด
รวมทั้งแถวที่เป็น tombstone อยู่แล้ว** · ไม่มีบันทึกว่าเคยมีอะไรอยู่ ไม่มีทางกู้ ไม่มีอะไรส่งเสียง

🎯 **ทำไมนี่ต่างชั้นจาก "ลบทริป/ลบแผน" ที่ผมยอมรับไว้ใน `§11.5`:**
ลบทริปกับลบแผนเป็น**การกระทำที่ผู้ใช้ตั้งใจทำลาย** และรู้ตัว · **ย่นช่วงวันเป็นการแก้แผนธรรมดา**
ที่ผู้ใช้ทำระหว่างวางแผนตามปกติ **โดยไม่รู้เลยว่ามันลบข้อมูล**

⚠️ **และการเลื่อนตัดสินใจของ `trip_days` กลายเป็นของที่แบกน้ำหนัก โดยที่ตอนเลื่อนมันยังไม่แบก**
ตอน P1 เลื่อน (ในคอมเมนต์ของ `20260825110903_e2_trip_days.sql`) **`trip_stops` ยังไม่มี** — ลบวันทิ้งจึงไม่ทำลายอะไร
**วินาทีที่ `trip_stops` ลงพร้อม cascade การเลื่อนอันเดิมเริ่มลบข้อมูลผู้ใช้** โดยไม่มีใครกลับไปอ่านมันใหม่

📌 **ข้อเสนอ (โซน P1/P3 ตัดสิน ผมแค่ชี้):** เลือกอย่างใดอย่างหนึ่ง **ก่อน**เขียน `trip_stops`
- ให้ `trip_days` มี `deleted_at` ด้วย แล้ว `E3` ทำ soft delete → cascade ไม่ยิง · หรือ
- ให้ตัวปรับช่วงวันของ `E3` **ปฏิเสธที่จะลบวันที่ยังมีจุดแวะอยู่** แล้วถามผู้ใช้ก่อน

**ส่วน merge rule เองไม่ต้องแก้:** `§3.4` มีทางลงอยู่แล้วสำหรับเคส "ทั้งวันหายไป"
(*"ถ้าไม่เหลือเลย = ทั้งวันถูกล้าง → ต่อท้ายวันแล้วแจ้งผู้ใช้ ไม่ใช่เงียบ"*) — ข้อนี้ยังใช้ได้ตามเดิม

### 11.13 ค้าน `D73` — ด่านชี้ผิดประตู · และแบบที่มีอยู่แล้วคัดลอกมาตรง ๆ ไม่ได้ (25 ส.ค. 2026)

> P1 เลือกทางที่สาม: ไม่แตะ cascade แต่เพิ่มเคสที่**แดงตอนมีคนเพิ่ม policy `DELETE` บน `trip_days`**
> เหตุผล: *"ปัญหาไม่ใช่ cascade ผิด แต่คือการเลื่อนตัดสินใจเริ่มแบกน้ำหนักโดยไม่มีใครกลับไปอ่าน"*
> · และขอให้ค้านถ้าไม่พอ · **วิธีคิดถูก ผมเห็นด้วยกับการไปแก้ที่ตัวการกลับไปอ่าน — แต่ด่านวางผิดประตู**

#### รูที่ 1 — `DELETE FROM trip_days` ไม่ต้องมี policy ก็เกิดได้

cascade ยิงตอนแถวหาย **ไม่ได้ยิงตอนไคลเอนต์มีสิทธิ์** · ประตูที่เดินผ่านด่านนี้ได้โดยไม่แตะ policy เลย:

| ประตู | ทำไมด่านไม่เห็น |
|---|---|
| **`service_role`** | **BYPASSRLS โดยนิยาม** — policy ไม่เกี่ยวตั้งแต่ต้น |
| **RPC `security definer`** | ไม่ต้องมี policy `DELETE` สักตัว · 🔴 **และนี่คือวิธีที่โปรเจกต์นี้สร้างของแทบทุกชิ้น** — `app.can_write_trip` · `create_trip_rpc` · `unsafe_state_set_clear_rpc` |
| **migration ที่แก้ข้อมูล** | รันเป็น owner |

🎯 **ตัวปรับช่วงวันของ `E3` มีโอกาสสูงที่สุดที่จะเป็น RPC `security definer`** เพราะมันต้องแก้หลายแถวใน transaction เดียว
— **ซึ่งคือประตูที่ด่านนี้มองไม่เห็นพอดี** · ด่านเฝ้าประตูฝั่งไคลเอนต์ ส่วนของจริงจะเดินเข้าประตูฝั่งเซิร์ฟเวอร์

(ผมไม่ได้ค้านด้วยเหตุผลที่ P1 เดาไว้ — เรื่อง*จังหวะ*ที่แดง · จังหวะนั้นดีอยู่แล้ว **ประตูต่างหากที่ผิด**)

#### รูที่ 2 — 🔴 แบบ `app.assert_trip_has_plan()` คัดลอกมาที่นี่แล้ว **เขียวตลอดกาล**

ท่าที่ควรใช้คือบังคับที่ฐาน ซึ่ง P1 มีแบบอยู่แล้ว (`trip_plans.sql:186-204`) **แต่ก๊อปตรง ๆ ไม่ได้** เพราะโจทย์คนละชนิด:

| | `trip_plans` (ของที่มีอยู่) | `trip_days` (ของที่ต้องการ) |
|---|---|---|
| ถามอะไร | *"ลบแล้ว**เหลือ**อย่างน้อย 1 ไหม"* | *"ลบแล้วมันจะ**พาลูกตายไปด้วย**ไหม"* |
| ต้องดูตอนไหน | **หลัง** ลบ → `after` + `deferrable` ถูกต้อง | 🔴 **ก่อน** ลบ |

**ถ้าใช้ `after delete` แบบเดียวกัน: ตอน trigger ทำงาน cascade ลบจุดแวะไปหมดแล้ว**
→ `exists (select 1 from trip_stops where day_id = old.id)` คืน **false เสมอ** → **ไม่ raise สักครั้งเดียวตลอดกาล**
→ ได้ด่านที่หน้าตาถูกทุกอย่างและไม่เคยจับอะไรได้ — **อาการเดียวกับ `expect(true).toBe(true)` ที่ P4 เพิ่งถอน
และเดียวกับที่ `client_writable_timestamps()` เกือบเป็นเมื่อชั่วโมงก่อน**

#### สิ่งที่เสนอ — `before delete` + `pg_trigger_depth() = 0`

```sql
create or replace function app.assert_day_has_no_stops()
returns trigger language plpgsql set search_path = '' as $$
begin
  if exists (select 1 from public.trip_stops where day_id = old.id) then
    raise exception 'ลบวันที่ยังมีจุดแวะอยู่ไม่ได้ — ย้ายหรือลบจุดแวะก่อน (cascade จะลบทิ้งเงียบ ๆ)';
  end if;
  return old;
end; $$;

create trigger trip_days_no_orphan_stops
  before delete on public.trip_days
  for each row
  when (pg_trigger_depth() = 0)          -- ลบทริปทั้งใบ = cascade = depth > 0 → ไม่ขวาง
  execute function app.assert_day_has_no_stops();
```

- **`before`** → จุดแวะยังอยู่ตอนตรวจ · **นี่คือข้อที่ทำให้มันต่างจากแบบของ `trip_plans`**
- **`pg_trigger_depth() = 0`** → FK cascade ของ Postgres ทำงานผ่าน internal trigger บนตารางพ่อ
  ลบทริปทั้งใบจึงมี depth ≥ 1 **ไม่ถูกขวาง** · ลบวันตรง ๆ มี depth 0 **ถูกขวาง**
  🔴 **นี่คือ `when` ที่คอมเมนต์ของ `trip_plans.sql:184` บอกว่าใส่ไว้ แต่ในโค้ดจริงไม่มี `when` เลย**
  (ที่นั่นใช้ *"ทริปยังอยู่ไหม"* ในตัวฟังก์ชันแทน ซึ่งได้ผลเหมือนกันสำหรับโจทย์นั้น) —
  ⚠️ **คอมเมนต์ค้างอยู่ ควรแก้ ก่อนมีคนก๊อปคำอธิบายไปใช้กับ trigger ที่พึ่ง `when` จริง ๆ**
- **ยิงทุกประตู** — trigger ไม่ถูก BYPASSRLS ข้าม · `service_role` · RPC `security definer` · migration ติดหมด
  🔴 **ข้อความบรรทัดบนนี้ไม่จริง แก้ 25 ส.ค. 2026 — ดู `§11.21`** · `TRUNCATE` **ไม่ยิง row trigger เลย** จึงเดินผ่านด่านนี้ทั้งบาน
- **`E3` ยังลบวันได้** ถ้าลบจุดแวะในคำสั่งเดียวกันจริง ๆ — เจตนาที่ชัดผ่าน อุบัติเหตุไม่ผ่าน

**ทำไมข้อนี้ตอบข้อค้านของ P1 ทั้งสองข้อพร้อมกัน:**
- ค้านทาง *"ให้ `E3` ปฏิเสธ"* ว่า **เจตนาอยู่ในโค้ดที่ยังไม่มีอยู่** → ✅ ท่านี้เจตนาอยู่ใน **FK layer วันนี้** ไม่ใช่ในโค้ดของ `E3`
- ค้านทาง *soft delete* ว่าต้องมี `deleted_at is null` ทุก policy ทุก query → ✅ ท่านี้ **ไม่ต้องมี `deleted_at` เลยสักตัว**

📌 **เขียนพร้อม `trip_stops` ในไฟล์เดียวกัน ไม่เลื่อน** — ถ้าเลื่อน มันคือ `D73` ที่กำลังพูดถึงตัวมันเอง
🔴 **แก้ข้อบกพร่องของข้อเสนอตัวเอง (25 ส.ค. 2026):** ฉบับข้างบนตรวจเฉพาะ `trip_stops`
**แต่ `bookings` ก็ห้อยกับ `trip_days` ด้วย** (`column-map.md` — `bookings.day_id → trip_days(id)`)
→ เขียนตามตัวอักษร = ลบวันที่ไม่มีจุดแวะแต่**มีใบจอง** ผ่านฉลุย และใบจองหายเงียบ
· **มันคือ "ผิดประตู" ของผมเองในระดับที่แคบลงหนึ่งขั้น** — ด่านที่ครอบลูกไม่ครบ
📌 **ตรวจให้ครบทุกตารางลูกที่เป็นข้อมูลของผู้ใช้: `trip_stops` **และ** `bookings`**
· ⚠️ `trip_day_plan_settings` **ไม่ต้องนับ** — เป็นค่าตั้งของวัน ไม่มีความหมายเมื่อวันหายไป ต่างจากจุดแวะกับใบจองซึ่งเป็นของที่ผู้ใช้สร้างเอง
· 🔴 **และทุกครั้งที่มีตารางใหม่ห้อยกับ `trip_days` ด่านนี้ต้องโตตาม ไม่งั้นมันจะครอบไม่ครบเงียบ ๆ** — เขียนไว้ในคอมเมนต์ของ trigger

📌 **และเทสต์ต้องพิสูจน์ว่ามัน _ยิง_** (ลบวันที่มีจุดแวะ → ต้อง raise) **ไม่ใช่แค่พิสูจน์ว่ามันมีอยู่** — สองทิศ ตามที่ P1 เพิ่งตั้งเป็นบรรทัดฐานเอง

### 11.16 บานที่ห้า — **`force row level security`** · และช่องว่างที่มีตัวอย่างอยู่ในทรีแล้ว (25 ส.ค. 2026)

> P1 ถามหาทางที่หกที่ `table_exposure` ยังมองไม่เห็น · และสงสัยเองว่าคือ `security definer` function

#### 🔴 กลไก: **เจ้าของตารางข้าม RLS ของตัวเองโดยค่าเริ่มต้น**

นี่คือรากของประตู `security definer` ทั้งบาน — ไม่ใช่เรื่อง grant เลยสักนิด:
- `security definer` รันด้วยสิทธิ์**เจ้าของฟังก์ชัน** ซึ่งตามปกติคือ role เดียวกับที่เป็น**เจ้าของตาราง**
- **เจ้าของตารางไม่ถูก RLS บังคับ** เว้นแต่ตั้ง `force row level security` (ค่าเริ่มต้นคือ **ไม่**)
→ definer function จึงอ่านแคชได้ **แม้แคชจะมี 0 policy และ `revoke all` ครบทุก role** — `revoke` ไม่เกี่ยวเลย

📌 **ลูกกุญแจ 1 บรรทัดต่อตาราง:**
```sql
alter table public.place_details_cache force row level security;   -- และอีก 3 ใบ
```
- 0 policy + `force` = **definer function ได้ 0 แถว**
- `service_role` **ยังทำงานได้เหมือนเดิม** เพราะมี **BYPASSRLS** ซึ่ง `force` ไม่แตะ (`TEAM.md` ระบุเอง)
- 🎯 **และมันมีคุณสมบัติที่ดีกว่าการปิดประตู: ถ้า `force` ทำอะไรพัง สิ่งที่พังคือประตูนั้นเอง**
  → เปลี่ยน **`Q3`** (*ใครเป็นคนเขียนแคช*) จากคำถามที่รอคนตอบ **เป็นคำถามที่ฐานตอบเอง**

⚠️ **ขอบเขตของลูกกุญแจ ต้องรู้ ไม่งั้นเชื่อผิด:** `force` ปิดเฉพาะกรณีที่ฟังก์ชันมีเจ้าของเป็น role ที่**ไม่มี BYPASSRLS**
· ถ้ามีใครสร้าง definer function โดยมีเจ้าของเป็น role ที่มี BYPASSRLS **`force` ช่วยไม่ได้เลย**
· → กติกาคู่กัน: **`security definer` ห้ามมีเจ้าของเป็น role ที่มี BYPASSRLS**

#### 🔴 ช่องว่าง "ตรวจที่ไฟล์ ไม่ใช่ที่ฐาน" — มีตัวอย่างอยู่ในทรีวันนี้แล้ว

📌 **ขยาย probe ไปที่ฟังก์ชัน ถามฐานแบบเดียวกับ `table_exposure`:**
```
prosecdef = true
  and has_function_privilege('anon'|'authenticated', oid, 'EXECUTE')
  and prosrc ~ '<ชื่อตาราง>'
```
**1 แถว = 1 ฟังก์ชันที่ผู้ใช้เรียกได้และแตะตารางนั้น**

🔴 **และกติกาที่ทำให้ probe นี้ไม่เป็นละคร: `security definer` + dynamic SQL = ห้าม**
`prosrc ~ '…'` คือการจับข้อความ · `execute format(…)` ทำให้จับไม่ได้เลยโดยสิ้นเชิง
**ถ้าไม่ห้าม probe จะคืน 0 แถวที่แปลว่า "มองไม่เห็น" ไม่ใช่ "ปิด"** — อาการเดียวกับที่ `table_exposure`
เกือบเป็นตอนยังไม่ได้ตรวจ grant ระดับคอลัมน์

#### 🟡 เพิ่มอีก 1 ตัวอักษรในสาขาที่มีอยู่แล้ว: `relkind = 'f'`

`table_exposure` ตรวจ view/matview อยู่แล้ว · **foreign table** (`relkind = 'f'`) เป็นภาชนะเดียวกัน
และชี้กลับมาที่ฐานเดิมได้ผ่าน `postgres_fdw`/`dblink` · โอกาสต่ำ แต่ราคาคือหนึ่งตัวอักษร

#### 🟡 probe ต้องรันทุก migration ไม่ใช่รันครั้งเดียว

`ALTER DEFAULT PRIVILEGES` และการกดเพิ่มตารางเข้า publication จากหน้า dashboard
**ติดอาวุธให้ของที่สร้างทีหลังโดยไม่ผ่านไฟล์สักไฟล์** — คุณค่าของ `table_exposure` มาจาก**ความถี่** ไม่ใช่จากการมีอยู่

✅ **matview ที่ P1 เติมเองถูก และผมคิดไม่ถึง** — มันไม่มี RLS ตามนิยาม จึงตั้ง `security_invoker` ไม่ได้
= **ประตูที่ล็อกไม่ได้ ต้องห้ามไปเลย** ไม่ใช่ควบคุม

### 11.18 `preserve_authorship` ทำลาย `updated_by_user` ของคนที่ไม่ได้ลาออก (25 ส.ค. 2026)

**คำตอบข้อที่ P1 ถาม (`legacy_updated_by` จำเป็นไหม): ไม่จำเป็น · ผมไม่ขอ · `merge ไม่เคยอ่านตัวตน`**
LWW ตัดสินด้วยเวลา · `updated_by_user` เป็นข้อมูลแสดงผลล้วน — คำตอบเดิมของ `§11.17` ไม่เปลี่ยน
**แต่ระหว่างตรวจ เจอของที่กระทบ `updated_by_user` จริง และมันเป็นบั๊ก ไม่ใช่ช่องว่างของสคีมา**

#### กลไก

`app.preserve_authorship()` (`20260825214436:121-124`) รัน:
```sql
update public.%I set %I = $1 where %I = $2 and %I is null
```
การ `update` นั้น **เปลี่ยนแถวจริง** → `when (old.* is distinct from new.*)` **เป็นจริง**
→ `app.touch_updated_at()` ยิง → **`new.updated_at := now()` และ `new.updated_by_user := auth.uid()`**
(`20260825123214:84-85`) · ตรวจแล้วตารางที่มันเขียน — `trip_stops` `bookings` `checklist_items`
`custom_places` `place_notes` — **มี touch trigger ครบทุกใบ**

#### 🔴 เคสที่พัง

1. **A** สร้างจุดแวะ X
2. **B** (ยังอยู่ ไม่ได้ลาออก) แก้ X ทีหลัง → `updated_by_user = B` ✅
3. **A** ลบบัญชี → `preserve_authorship` เขียน `legacy_added_by = 'A'` ลง X
4. → touch ยิง → **`updated_by_user := auth.uid()`**
   · ลบผ่าน admin API / `service_role` → `auth.uid()` เป็น **`null`** → **B ถูกลบทิ้ง**
   · ลบด้วย JWT ของ A เอง → ได้ `A` → FK `on delete set null` ตามมาทันที → **`null` อยู่ดี**

🎯 **trigger ที่เขียนขึ้นเพื่อ*รักษา*ความเป็นเจ้าของ ไป*ทำลาย*บันทึกความเป็นเจ้าของอีกชนิดหนึ่ง
ของคนที่ไม่ได้ลาออก** — และมันคือคอลัมน์ที่เราเพิ่งเถียงกันว่า **backfill ไม่ได้**

**ผลข้างเคียงที่สอง:** `updated_at` ของทุกแถวที่คนนั้นเคยสร้าง **กระโดดมาเป็นเวลาที่ลบบัญชี**
→ Realtime/delta sync เห็นเป็น "หลายร้อยแถวเพิ่งเปลี่ยน" · และแถวโกหกว่าเพิ่งถูกแก้ ทั้งที่ไม่มีใครแก้
· ตรงกับที่ `§11.2` เตือนเรื่อง `updated_at` ที่ขยับโดยไม่มีการแก้จริง **แต่รอบนี้เกิดทีเดียวเป็นก้อน**

📌 **ข้อกำหนด: `preserve_authorship` ต้องไม่แตะ `updated_at`/`updated_by_user` เลย**
ทางที่เป็นไปได้ (โซน P1 เลือกเอง):
- `when` ของ touch trigger เทียบ**เฉพาะคอลัมน์ที่ไคลเอนต์เขียนได้** ไม่รวม `legacy_*_by` — ตรงความหมายที่สุด
- หรือเติม `and pg_trigger_depth() = 1` ใน `when` ของ touch — สั้นกว่า **แต่กว้างกว่าที่ตั้งใจ**
  (จะข้ามการ touch ที่มาจาก trigger ตัวอื่นด้วยทุกตัว ซึ่งอาจไม่ใช่สิ่งที่ต้องการ)
📌 **เทสต์ต้องเป็นเคสข้อ 1-4 ข้างบนตรง ๆ: B แก้ · A ลบบัญชี · `updated_by_user` ต้องยังเป็น B**

### 11.19 แก้กติกาของตัวเองจาก `§11.16` — dynamic SQL ใน definer **ห้ามไม่ได้ ต้องกำหนดรูปแทน**

ผมเสนอไปเมื่อข้อความก่อนว่า **`security definer` + dynamic SQL = ห้าม** เพราะ `prosrc ~ '<ตาราง>'` จับไม่ได้
· **`app.preserve_authorship` ที่เพิ่งลงวันเดียวกันเป็น definer + `execute format(…)` พอดี** —
`prosrc` มีแต่ `public.%I` **ไม่มีชื่อตารางสักตัว** → **probe ที่ผมออกแบบมองมันไม่เห็นเลยแม้แต่ใบเดียว**

🎯 **แต่ฟังก์ชันนี้ *ต้อง* ใช้ dynamic SQL** เพราะมันวนรายชื่อตาราง — **กติกาของผมผิด ไม่ใช่ฟังก์ชันผิด**

📌 **ฉบับแก้:** dynamic SQL ใน definer **อนุญาต ถ้าชื่อวัตถุมาจากแหล่งที่ประกาศไว้และ probe อ่านได้**
**ห้ามเมื่อชื่อวัตถุมาจากพารามิเตอร์ของผู้เรียก**
· `preserve_authorship` **ผ่านเกณฑ์นี้อยู่แล้ว** — ชื่อมาจาก `public.authorship_columns()` ซึ่งเป็นแหล่งที่ query ได้
· → probe ต้อง**ตามไปอ่านแหล่งนั้น** ไม่ใช่ยอมแพ้ที่ `prosrc`
· ✅ `revoke execute … from public, anon, authenticated` มีครบ และเป็น trigger function จึงเรียกตรงไม่ได้ — **ไม่ใช่ประตูที่เปิด เป็นประตูที่ probe มองไม่เห็น** ซึ่งเป็นคนละปัญหาและต้องแยกให้ออก

### 11.20 ช่องว่าง "คนที่ตั้งใจ" — **ปิดไม่ได้ และการอ้างว่าปิดได้คืออันตรายกว่า**

P1 ถามว่ามีท่าปิดช่องที่ *"คนเพิ่ม definer แล้วไปเติมรายชื่อในด่านเอง"* ไหม หรือรับว่านั่นคือขอบของกลไก

**ตอบ: ปิดไม่ได้ และไม่ควรเขียนกติกาที่อ้างว่าปิดได้**
> **ด่านกันอุบัติเหตุ ไม่ได้กันอำนาจ** · ใครเขียน migration ได้ ก็เขียนอะไรก็ได้ — นั่นคือนิยามของการมีสิทธิ์เขียน
> **กติกาที่อ้างว่ากันอำนาจได้ จะทำให้เราเชื่อผิดว่ากันแล้ว** ซึ่งเป็นความล้มเหลวรูปเดียวกับด่านที่เขียวโดยไม่ได้ตรวจอะไร

**แต่เปลี่ยน *ราคา* ได้ 2 ทาง — และทั้งคู่กันตัวเราเองตอนตีสอง ซึ่งคือของจริงที่ต้องกัน:**

1. **ให้ด่านตรวจ *คุณสมบัติ* ไม่ใช่ *รายชื่อ*** — เช่น definer ทุกตัวที่ `authenticated` เรียกได้
   ต้องมี `comment on function` ที่ระบุค่าคงที่ที่มันบังคับ **พร้อมเลข `D`**
   · เติมชื่อลง array = **1 บรรทัดที่ไม่มีใครอ่าน** · เขียนคำอธิบายเท็จ = **ของที่มีคนอ่าน**
   · 📌 P1 ทำข้อนี้ไปแล้วโดยไม่รู้ตัวกับ `preserve_authorship` (คอมเมนต์ 3 บรรทัดอ้าง `P-55/D78/Q4`) — **แค่ยังไม่ได้บังคับ**
2. **ยืนยัน *จำนวน* ไม่ใช่สมาชิก** — `N → N+1` เป็น diff บรรทัดเดียวที่มองเห็นเสมอ
   ต่างจากการแทรกชื่อกลาง array เรียงตัวอักษรใน diff 200 บรรทัด

🔴 **และขอบที่เหลือ ต้องเขียนไว้ว่ามันคือขอบ:** สิ่งเดียวที่ทานอำนาจได้คือ **บันทึกไปอยู่ในที่ที่ผู้เขียนไม่ได้ควบคุม**
— remote history · CI log · อีกเซสชันหนึ่ง · **ซึ่ง `D72` ข้อ 3 (บอกว่า push ถึง commit ไหน) ทำอยู่แล้ว**
ไม่ต้องสร้างกลไกใหม่ ต้อง**เขียนให้ชัดว่านั่นคือกลไกสุดท้าย ไม่ใช่ด่านในไฟล์**

### 11.21 `TRUNCATE` ทำให้คำอ้าง "ยิงทุกประตู" ของ `§11.13` เป็นเท็จ (25 ส.ค. 2026)

#### รับการแก้ของ P1 ก่อน — กลไกที่ผมวิเคราะห์ไม่ใช่ราก

ผมรายงานว่า `preserve_authorship` `update` แถวแล้ว touch ยิงตาม · **P1 พิสูจน์ด้วยแถวควบคุม
(ตั้ง `legacy_added_by` ไว้ล่วงหน้าให้ลูปข้ามแน่นอน) ว่าแถวนั้น *ยังโดนลบ* อยู่ดี**
🎯 **ตัวยิงจริงคือ `on delete set null` ของ FK เอง** — FK action คือ `UPDATE` แถว → touch ยิง
→ **บั๊กเก่ากว่า `D78` และกว้างกว่าที่ผมรายงาน:** ใครลบบัญชี **ทุกแถวที่เขาเคยสร้าง** จะลบ
*"ใครแก้ล่าสุด"* ของ**คนอื่น**ทิ้ง · `D78` แค่ทำให้เห็นง่ายขึ้น
· ทางที่ผมชี้ก็มีอยู่จริง **แต่ไม่ใช่ตัวเดียวและไม่ใช่ราก** — และ `pg_trigger_depth() > 1` ปิดทั้งสองทางด้วยกลไกเดียว
· ✅ ผมค้าน `pg_trigger_depth` ไว้ว่ากว้างเกิน · **หลักฐานเปลี่ยนน้ำหนัก: ของที่ต้องกันมาจาก FK ซึ่งไม่มีจุดให้ติดธงเจตนา**
  กติกาคู่ที่ P1 จด (*trigger ที่ต้องการ stamp ต้องเขียน `updated_by_user` เอง*) คือส่วนที่ทำให้ข้อค้านนั้นถูกใช้จริง

#### 🔴 แก้คำอ้างของตัวเอง

`§11.13` เขียนว่าด่าน `trip_days_no_orphan_stops` *"ยิงทุกประตู · `service_role` · RPC definer · migration ติดหมด"*
**คำนั้นเป็นเท็จ** · `TRUNCATE`:
- **ไม่ยิง row-level trigger เลย** (ยิงเฉพาะ statement-level `BEFORE/AFTER TRUNCATE` ซึ่งเราไม่มี)
- ข้าม RLS · ข้าม policy · **ข้าม `force row level security` ที่ผมเพิ่งเสนอไปเอง**
- ไม่เขียน `deleted_at` · **ไม่เหลือ tombstone**

→ `truncate public.trip_days cascade` **ลบจุดแวะทั้งฐานโดยด่าน `D73` ไม่ทำงานสักครั้ง**
· และ `service_role` **มี `TRUNCATE` อยู่จริงบน 18 ตารางรวม `trip_stops`** (P1 วัดได้จาก probe ตัวใหม่)

📌 **ทางแก้ที่ถูกคือของ P1: `revoke truncate`** — ไม่ใช่ไปเพิ่ม statement trigger
`grant` เป็นการ **เพิ่ม** ไม่ใช่ **กำหนด** → ต้อง `revoke … from service_role` ก่อนเสมอ
· statement-level truncate trigger เป็นของเสริมได้ **แต่ไม่ใช่ด่านหลัก** — ด่านหลักคือไม่ให้สิทธิ์ตั้งแต่แรก

🎯 **บทเรียนที่ตรงกับ `§11.20` พอดี และผมเป็นฝ่ายโดนรอบนี้:** ผมเขียนคำว่า *"ทุกประตู"*
โดยไล่ประตูที่**นึกออก** ไม่ใช่ไล่ประตูที่**มีอยู่** — เป็นการวัดความตั้งใจ ไม่ใช่วัดของจริง
**คำที่ปลอดภัยกว่าคือรายชื่อ verb ที่ตรวจแล้ว ไม่ใช่คำว่า "ทุก"**

#### 🟡 ผลข้างเคียงของการแก้ ที่ต้องรู้: `updated_at` เลิกเป็นบันทึกการเปลี่ยนแปลงที่ครบ

หลัง `pg_trigger_depth() > 1` แล้ว **FK `set null` เปลี่ยน `added_by_user` จริง โดย `updated_at` ไม่ขยับ**
→ ไคลเอนต์ที่ดึงด้วย `updated_at > cursor` **จะไม่มีวันเห็นการเปลี่ยนนั้น** และแสดง *"เพิ่มโดย B"* ต่อไปตลอดกาล

**ถูกต้องแล้วสำหรับวันนี้** (Realtime ส่ง UPDATE ให้อยู่ดี ไม่เกี่ยวกับ `updated_at`)
🔴 **แต่มันทำให้ `§11.8` เลื่อนจาก *คำแนะนำ* เป็น *ข้อบังคับ*** — เดิมผมค้าน `updated_at`-as-cursor ด้วยเหตุผล
เรื่อง `now()` = เวลาเริ่ม transaction · **ตอนนี้มีเหตุผลที่สองที่แข็งกว่า: มีการเปลี่ยนแปลงจริงที่ `updated_at` ไม่บันทึกเลยโดยตั้งใจ**
📌 `E6`/`D17` ห้ามสร้าง delta sync บน `updated_at` — ใช้ Realtime เป็นช่องทางหลัก + full refetch ตอน cold start

1. **ของเดิมให้ผลที่ *แน่นอน* อยู่แล้ว** — `where deleted_at is null order by rank, id` ทำให้ทุกเครื่องเห็นตรงกัน

2. **มันไม่ได้ตัด dependency ฝั่งอ่านอย่างที่หวัง** — ฝั่งอ่าน**ต้อง**ระวัง `deleted_at`/`order by` อยู่แล้วไม่ว่ายังไง

3. **ความถี่ต่างกันมาก** — 2 คนลากจุดแวะพร้อมกันคือเคสประจำวัน · 2 คนตั้งขอบปลายวันพร้อมกันแทบไม่เกิด

📌 **ทางที่ผมแนะนำแทน — ฟรี ไม่แตะสคีมา:** ให้ฝั่งอ่าน **แสดงว่ามีขอบเกิน ไม่ใช่เงียบ ๆ หยิบตัวแรก**
> *"วันนี้มีขอบปลายวัน 2 อัน — ใช้อันแรกอยู่"* + ปุ่มเอาอันที่ไม่ต้องการออก

**ผู้ใช้เห็นแล้วแก้ได้ใน 2 วินาที · ส่วนการเงียบแล้วหยิบตัวแรกคือของที่ไม่มีใครรู้ว่าเกิดขึ้น**
🎯 **เป็นหลักเดียวกับ `§3.3`: LWW ทำข้อมูลหายได้และเลี่ยงไม่ได้ — สิ่งที่ทำได้คือ *ไม่ให้หายเงียบ*** ไม่ใช่การไล่ให้ conflict เป็นศูนย์

#### ④ 🔴 ของที่ยังไม่มีใครพูดถึง และแพงกว่าทั้งสามทางรวมกัน: **แคชในเครื่องไม่มีเวอร์ชัน**

`lib/localCache.ts:11` — `const PREFIX = "trip-cache:"` · **ไม่มีเลขสคีมาในคีย์เลย**
และแอป **hydrate จากแคชก่อน fetch เสมอ** (`useStops.ts:58-72`)

`day_id` เป็น `"d0"` · `order_index` เป็น int (สคีมาใหม่มี `rank`) · `file_url` ที่กลายเป็น `file_path` · ไม่มี `deleted_at`


### 11.27 สองข้อที่รอสวิตช์ cutover — **ทั้งคู่ไม่ต้องรอ และลงตอนนี้ได้ปลอดภัยกว่า** (26 ส.ค. 2026)

P1 เลื่อน 2 ข้อไปลงพร้อมสวิตช์ เพราะ *"เขียนข้อความ 'ระบบกำลังย้ายข้อมูล' ตอนนี้ก็ไม่มีอะไรจุดมันได้"*
**เหตุผลถูกสำหรับ *ถ้อยคำเฉพาะของ cutover* · แต่ผิดสำหรับ *ตัวกลไก* ทั้งสองข้อ**

#### ① ข้อความ "ลองใหม่อีกครั้ง" — แก้ได้วันนี้ **โดยไม่ต้องรู้จัก cutover เลย**

📌 **แยกชนิดของความล้มเหลว ไม่ใช่เพิ่มโหมด:**

(`lib/writeGuard.ts:17,29,38`) → ต้องส่ง error ผ่านเข้าไปก่อน · เล็กแต่ไม่ใช่ศูนย์

#### ② rollback — **ดีไซน์มีอยู่แล้วและถูกเขียนไว้ในหัวไฟล์ · ที่ขาดคือการเอาไปใช้ ไม่ใช่การออกแบบ**

`lib/writeGuard.ts:12-13` เขียนสัญญาไว้เอง:
> *"คู่กับ `reload()` ของแต่ละ hook: เขียนไม่ผ่าน → บอกผู้ใช้ + **ดึงของจริงจาก DB มาทับ state ที่เดาไว้**
> ตรงไปตรงมากว่าการเขียน rollback รายฟิลด์ให้ครบทุก action และไม่มีทาง state ค้างเพี้ยน"*

**และหัวไฟล์เดียวกันบรรยายอาการที่ผมกับ P1 เพิ่งคุยกันเป๊ะ:** *"หน้าจอโชว์ว่าสำเร็จค้างไว้จนกว่าจะรีโหลดแล้วค่าเด้งกลับ"*

📌 **จึงไม่ต้องสร้าง rollback — ต้องเอาสัญญาที่มีอยู่ไปใช้ให้ครบ** · ตรวจแล้วมันใช้ไม่ทั่ว:

- 🔴 **`usePlans.ts` ไม่มีทั้งสองครึ่ง** — `writeGuard` 8 จุด · **ไม่มี `reload`/`refetch` ในไฟล์เลย**
  และ `:107` `:118` `:127` **ทิ้งค่าที่คืนมาทั้งดุ้น** (`await writeGuard(...)` เปล่า ๆ)
  → *"ก๊อปจุดแวะมาแผนใหม่"* ล้มได้โดยแอปเดินต่อเหมือนสำเร็จ = **แผนที่ก๊อปมาไม่ครบ โดยไม่มีทางกู้**
- ⚠️ **ผมเช็คด้วย grep แบบเดียว — ตัวเลขนี้ใช้ชี้ที่ให้ไปดู ไม่ใช่ใช้เป็นข้อสรุป** ต้องไล่เองอีกรอบ

#### 🔴 และเหตุผลที่ทั้งสองข้อควรลง **ก่อน** สวิตช์ ไม่ใช่พร้อมกัน

**ระหว่าง cutover ทางเขียน *ทุกเส้น* ล้มพร้อมกัน** → เส้นที่ทิ้งค่าที่คืนมาจะโผล่**พร้อมกันหมดในนาทีเดียว**
🎯 **ถ้าลงพร้อมสวิตช์ แปลว่าการทดสอบจริงครั้งแรกของสวิตช์ ก็เป็นการทดสอบจริงครั้งแรกของมันด้วย**
— ซึ่งเป็นสิ่งเดียวกับที่ทีมนี้หลีกเลี่ยงมาทั้งวัน · **ลงก่อน แล้วสวิตช์จะเจอพื้นที่พิสูจน์แล้ว**

### 11.28 `E3-AC7` — ข้อกำหนดฉบับที่เอาไปเขียนโค้ดได้ · **และเกณฑ์ข้อนี้ล้าสมัยแล้ว** (26 ส.ค. 2026)

📌 **เกณฑ์ยังเขียนว่า "คิวออฟไลน์" · P1 รับการแก้กรอบไปแล้วรอบก่อน** (*"ผมสร้างตาราง 3 ทางบนของที่ไม่มีอยู่"*)
**แต่ตัวเกณฑ์ไม่ได้ถูกแก้ตาม** → P8 กั้นงานไว้ว่า *"คำถามนี้ต้องถูกถามจริง"* → **ตอนนี้คำถามที่ล้าสมัยกำลังขับงาน**
🔴 **ของที่ต้องแก้คือเกณฑ์ ไม่ใช่การไปตอบมันตามที่เขียน** · แต่ 3 ใน 4 ข้อ **มีคำตอบจริงเมื่อเปลี่ยนประธานเป็น *แท็บที่เปิดค้าง***

#### ① แยก `42501` สองชนิด — **แยกจากตัว error ไม่ได้เลย และนี่คือเหตุผล**

ชั้นบังคับคือ **`revoke`** → `42501` มาจากระบบสิทธิ์ของ Postgres เอง
**มันไม่มีที่ให้แนบอะไรทั้งนั้น** — ไม่มี `code` เฉพาะ ไม่มี header ไม่มี status ที่ต่างออกไป
· (ถ้าเป็น trigger/policy จะแนบ `errcode` เองได้ · **`revoke` แนบไม่ได้ตามนิยาม**)

📌 **สัญญาณต้องมาแยกทาง — ธงที่ไคลเอนต์อ่านได้**
🎯 **และแบบมีอยู่แล้วในโปรเจกต์: `app.unsafe_state` + `public.unsafe_state_reason()`**
· ⚠️ **แต่ฉบับปัจจุบัน `revoke execute … from public, anon, authenticated` → `service_role` เท่านั้น** = ธงของ harness
· 📌 **cutover ต้องมีพี่น้องของมันที่ `authenticated` อ่านได้** — รูปเดียวกัน คนละสิทธิ์
· 🔴 **และ `P-50` ในไฟล์นั้นคือเหตุผลของข้อนี้ ที่ P1 เขียนไว้เอง: *"ธงที่อ่านไม่ได้ ไม่ใช่ธง"***
· ⚠️ ข้อบังคับที่มาคู่กัน: ระหว่างโหมดนี้ **`select` ต้องยังไม่ถูก revoke** ไม่งั้นธงเองก็อ่านไม่ได้
  (ดีไซน์ 2 ชั้นของ P1 ถอนเฉพาะสิทธิ์*เขียน* จึงยังถูก — **แต่ต้องเขียนเป็นข้อบังคับ ไม่ใช่ผลพลอยได้**)

#### ② เพดานลองใหม่ — **ไม่มีคิว จึงไม่มีเพดาน · และไม่ควรมี auto-retry เลยแม้แต่ครั้งเดียว**

ไม่มี op ค้าง 2 ชั่วโมง เพราะไม่มีที่ให้ค้าง · **ผู้ใช้เป็นคนลองใหม่ ไม่ใช่แอป**
· ✅ ทำให้ *"หายเงียบ"* ที่ `E9-AC2` กลัว **ไม่มีทางเกิดจากทางนี้** — ทุกความล้มเหลวมี toast ตาม `writeGuard`

#### ③ ผู้ใช้เห็นอะไร — 🔴 **ธงต้องขับ banner ตอน *โหลด* ไม่ใช่ตอน *เขียนพลาด***

**นี่คือข้อที่เป็นของผมจริง ๆ และเป็นข้อที่สำคัญที่สุดใน 4 ข้อ**
คนที่ปิดแอปไปแล้วกลับมาระหว่าง cutover **ต้องรู้ก่อนเริ่มพิมพ์ ไม่ใช่หลังจากพิมพ์โน้ตยาว ๆ แล้วกดบันทึกไม่ได้**
📌 อ่านธงตอน hydrate → banner ค้างไว้ + ปิดปุ่มเขียน
· ⚠️ **ปิดปุ่มไม่ใช่การบังคับ** (P1 พูดถูกแล้ว) — มันคือ**การสื่อสาร** · ต้องมีทั้งสองชั้นด้วยเหตุผลคนละข้อ

#### ④ op ที่แก้ของเดิม ควรลองใหม่ไหม — **ไม่ · ไม่ว่ากรณีใด**

ไม่มีคิวจึงไม่เกิดในทางปฏิบัติ **แต่หลักการต้องเขียนไว้เพราะมันจะกลับมา:**
> **การเขียนที่ประกอบขึ้นจาก snapshot เก่า ห้ามถูกเล่นซ้ำทีหลัง** — ระหว่างนั้นอาจมีคนแก้แถวเดียวกันไปแล้ว
> เป็นเหตุผลเดียวกับที่ `§3.4` เก็บ op เป็น **ความสัมพันธ์ ไม่ใช่ค่า**

#### 🎯 ข้อของ P1 เอง — **เห็นด้วย และมันสำคัญกว่าทั้ง 4 ข้อรวมกัน · แต่ขอให้แข็งกว่าที่เขียน**

P1 เสนอว่า *"อย่าให้ cutover เกิดตอนมีคนอยู่ในทริป"* เป็นข้อกำหนดเชิงเวลา
✅ **ถูก — คำตอบที่ดีที่สุดของ "คิวควรรับมือ cutover ยังไง" คือ *ทำให้ cutover เกิดไม่ได้ในหน้าต่างที่มันสำคัญ***

🔴 **แต่ "ข้อกำหนดเชิงเวลา" คือเจตนา และทีมนี้เพิ่งตกลงกันวันนี้ว่าเจตนาไม่ใช่กลไก**
📌 **ให้สคริปต์ cutover ตรวจตัวเองแล้วปฏิเสธ:**
```sql
-- ต้องได้ 0 แถว ไม่งั้นหยุด
select 1 from public.trips
 where current_date between start_date and end_date
   and deleted_at is null;
```
**เปลี่ยนจาก "อย่าทำตอนนั้น" เป็น "ทำตอนนั้นไม่ได้"** — ตรงกับกฎที่รับไปแล้ววันนี้ (*นับจากโลก ห้ามนับจากความคาดหวัง*)

⚠️ **และขอบของมันที่ต้องเขียนไว้:** ด่านนี้ไม่ได้ทำให้ธงในข้อ ① หมดความจำเป็น
**cutover ยังกินเวลา และคนที่ *ไม่ได้* อยู่ในทริปก็เปิดแอปอยู่ได้** · ด่านลดขนาดปัญหา ไม่ได้ลบมันทิ้ง
